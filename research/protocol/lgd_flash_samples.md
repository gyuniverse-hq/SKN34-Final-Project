> **대상:** 숙제 01 촬영에 참여하는 팀원, LGD PoC 담당자
> **목적:** 제품 사진에서 재질 맵(diffuse, specular, roughness, normal)을 추정하는 LGD PoC의 입력 사진을 찍는다.
> **상태:** PoC 준비 단계. 결과 맵은 앱에 바로 넣지 않는다. 실제로 바른 사진과 비교해서 AR이 더 비슷해질 때만 도입한다. (`docs/AR_PROGRESS.md` 결정 기록)
> **같이 볼 문서:** `docs/AR_SPEC.md` 8-A-1(숙제 01 촬영 규칙), 6-15(측정 CSV, `setupId`), `docs/PBR_DEMO_SPEC.md`

## 1. LGD 입력 조건 (확인한 것 / 확인 안 된 것)

| 항목 | 내용 | 근거 |
|---|---|---|
| 사진 수 | **재질 하나에 사진 1장** | 공식 코드 `utils/data_loading_brdf.py`: 폴더의 사진을 한 장씩 처리 |
| 크기 | **가운데 정사각형으로 자른 뒤 256×256으로 축소** | 같은 파일: 짧은 변 기준 가운데 자르기 후 `resize(img, (3, 256, 256))` |
| 색 공간 | 8비트 이미지를 읽고, 실행 옵션 `--correctGamma`, `--useLog`로 처리 | `predict.py`. README 예시는 `python predict.py --useLog --correctGamma` |
| 출력 | diffuse → specular → roughness → normal. diffuse·specular는 sRGB(감마 2.2), roughness·normal은 선형 | README |
| 사전학습 모델 | 제공됨 (Google Drive 링크) → **새로 학습하지 않는다** | README |
| 조명 | **플래시를 켜고 정면에서 찍은 사진으로 추정** | 함께 들어 있는 예시 입력(`IMG_6970-inputs.png` 등)과 렌더러 구조. **논문 원문으로 확인 필요** |
| 학습 데이터·가중치 라이선스 | **확인 안 됨** | 코드는 MIT 표시. 가중치·학습 데이터 조건은 README에 없음 |

- 라이선스를 확인하기 전에는 `research/`에서만 실행한다(AR_SPEC 1-7, 1-13). 앱에는 결과 맵만, 출처와 라이선스를 적어서 넣는다.
- 확인한 날짜: 2026-10-21. 저장소 `Xuejiao-Luo/SVBRDF-Estimation-with-Learned-Gradient-Descent`

## 2. 몇 장 찍나

| 용도 | 수량 | 이유 |
|---|---|---|
| LGD 입력 | **제품 라인(제형)당 3장** | 같은 제품 라인은 셰이드가 달라도 질감이 거의 같다. 색은 측정값(6-15)을 쓰므로 셰이드마다 찍지 않아도 된다. 3장의 결과가 비슷한지로 신뢰도를 본다 |
| 검증 (실제로 바른 사진) | **제품당 팀원 2~3명 × 정면 1장 이상** | LGD 맵을 넣은 AR이 실제로 바른 모습과 더 비슷한지 비교하는 기준. 숙제 01 사진을 그대로 쓴다 |
| PoC 범위 | **제품 3~5개**, 매트·새틴·글로시가 각각 하나 이상 | 입력 9~15장 + 검증 10~15장 |

## 3. 촬영 체크리스트

**준비**
- [ ] 무광 흰 종이나 무광 판(반사 없는 것)
- [ ] 제품 (같은 날 숙제 01에서 측정하는 제품과 같은 것)
- [ ] 휴대폰 삼각대 또는 고정대. 표면과 수직이 되게
- [ ] 촬영 기종 기록 (가능하면 숙제 01과 같은 기종)

**샘플 만들기**
- [ ] 종이 위에 **최소 3×3cm**를 고르게, 평평하게 바른다 (덩어리·빈 곳 없이)
- [ ] 바르는 횟수를 기록한다 (기본 1회. 가능하면 3회 샘플도 하나 더)

**촬영**
- [ ] **방 조명을 끄거나 최대한 어둡게** 하고 **휴대폰 플래시만 켠다**
- [ ] 휴대폰을 표면에 **수직, 정면**으로 두고 거리는 **20~30cm**
- [ ] 노출·화이트밸런스를 고정한다 (프로 모드). 고정이 안 되는 기종은 메모에 적는다
- [ ] 발색 부분이 화면 가운데에 오게, 사진 짧은 변의 절반 이상을 채우게 찍는다
- [ ] 플래시 반사로 하얗게 날아간 부분이 생겨도 그대로 둔다 (광택 정보다). 단, 화면 전체가 하얗게 날아가면 거리를 늘린다
- [ ] 같은 샘플을 **3장** 찍는다 (휴대폰을 살짝 떼었다 다시 놓기)

**하지 않는 것**
- 공식몰·판매 사이트 이미지 사용 (AR_SPEC 6-15)
- 사람 얼굴이 나오는 사진을 LGD 입력으로 사용 (얼굴은 검증 사진에만, 동의한 팀원만)
- 보정·필터 앱으로 편집

## 4. 파일 이름과 저장 위치

```text
research/data/lgd/raw/{제품}_{셰이드}_{횟수}x_{장번호}.jpg
  예: hince-moodenhancer-glow_dearrose_1x_1.jpg
research/data/lgd/raw/meta.csv
```

`meta.csv` 열:

| 열 | 설명 |
|---|---|
| `file` | 파일 이름 |
| `productId`, `shadeId` | `data/catalog/products.ts`의 id와 같게 |
| `layers` | 바른 횟수 |
| `device` | 기종 |
| `setupId` | 측정 환경 이름 (예: `room1-flash-galaxyS24`). 같은 `setupId`끼리만 비교 |
| `fixedExposure` | 노출·화이트밸런스를 고정했으면 `yes` |
| `takenAt` | 날짜 |
| `note` | 메모 |

- `research/data/`는 저장소에 올리지 않는다(`.gitignore`). 
- 256×256으로 자르는 전처리 스크립트와 LGD 실행 결과(`research/data/lgd/maps/`)는 PoC 단계에서 만든다.

## 5. 결과를 쓰는 방법 (PoC)

1. LGD로 제품마다 맵 4장을 만든다. GPU가 필요하다: RunPod, Colab, 팀원 PC 중 하나.
2. 같은 제품의 3장 결과를 비교한다. roughness·specular가 크게 다르면 그 제품은 수동 값을 쓴다.
3. diffuse는 쓰지 않는다. 색은 측정값(6-15)이 우선이다. 측정값이 없을 때만 `estimated`로 쓴다(AR_SPEC 1-1, 1-8).
4. 다음 세 가지를 실제로 바른 사진과 비교한다: ① 제형별 수동 값 ② LGD roughness·specular 값 ③ ② + normal 맵. 비교는 트랙 A(SSIM·사람 평가)와 트랙 B(ΔE2000)로 따로 한다(AR_SPEC 1-12, 8장).
5. ②나 ③이 더 가까울 때만 앱 도입을 팀에 제안한다. 맵을 AR 페이지에 넣는 방법(빌드 때 HTML에 넣기 또는 규칙 예외)은 팀이 결정한다.
