1. 문제 정의
--------------------------------------------------------------------------------
[해결하려는 문제 상황과 기존 방식의 한계]
- 온라인 뷰티 쇼핑 및 K-메이크업 탐색 시, 상세페이지의 보정된 모델 발색 사진이나 팔뚝 스와치만으로는 "내 얼굴·내 입술색·내 방 조명에서 실제로 어떻게 보일지" 알 수 없음.
- 기존 상용 AR 뷰티 앱(스노우, 뷰티플러스 등)의 한계:
  1) '스티커·필터 현상': 입술 주름, 윗입술 그늘, 아랫입술 볼륨을 무시하고 단색 불투명 막을 평평하게 덮어 인위적임.
  2) '과도한 미화·보정': 피부 블러, 턱 깎기, 얼굴 밝히기 등이 강제 적용되어 실제 제품 구매 판단용(Realism)으로 쓸 수 없음.
  3) '프라이버시 우려': 고화질 얼굴 사진을 서버로 전송해 합성하는 방식은 사용자의 사진 유출 거부감을 유발함.
  4) '영상 컨텐츠와 시착의 단절': 유튜브 K-뷰티/아이돌 메이크업 영상을 보고 따라 하고 싶어도, 어떤 제품을 내 얼굴 어느 위치에 어떻게 발라야 하는지 즉시 체험할 수 없음.

[왜 이 문제가 중요한지 / 실제 불편]
- 화장품 구매 불만족 및 반품의 핵심 원인은 '기대 불일치(기대한 발색·제형 vs 내 얼굴 위 실제 발색 차이)'에서 발생 (Oliver 기대일치 이론, Yun & Seo 2026).
- 연구 근거(arXiv 2512.21988, 한국인 965명 얼굴 5부위 측정): 스마트폰 카메라는 조명·부위별 색 편차가 평균 ΔE 10.63에 달해, 단순 색상 덮어씌우기로는 실제 발색을 재현할 수 없음.

[대상 사용자와 사용 상황]
- 대상 사용자:
  1) K-아이돌·유튜브 크리에이터의 메이크업 룩을 내 얼굴에 그대로 재현해 보고 싶은 K-뷰티 소비자 및 외국인 관광객
  2) 올리브영 등 매장 방문 전/온라인 구매 전, 내 얼굴에서 립·블러셔·아이섀도·아이라인·파운데이션·하이라이터·쉐딩이 실제로 어떻게 올라가는지 확인하고 싶은 사용자
- 사용 상황:
  - 유튜브 K-스타일/연예인 메이크업 영상을 보다가 "AR에서 입어보기"를 눌러 8~9개 부위를 한 번에 내 얼굴에 시착하고, "아이라인 강아지상으로", "오버립으로", "조금 연하게"처럼 대화형으로 조정한 뒤 대체 제품·매장 리스트까지 확인하는 상황.

2. 서비스 개요
--------------------------------------------------------------------------------
[한 문장 정의]
- "얼굴 영상 외부 전송과 피부 보정 필터 없이, 기기 내 3D 메시·PBR 광학 셰이더와 AI 레시피 추출로 내 얼굴 위 실제 메이크업 발색과 제형을 재현하고 대화로 조정하는 K-뷰티 AR 가상 시착 서비스"

[기존 방식 대비 개선점 및 구체적 수치]
1) 스티커 느낌 탈피 (층 쌓기 + PBR 제형 표현):
   - 단순 RGB 알파 블렌딩 대신 `카메라 = 조명 × 명암 × 맨입술` 물리 층 쌓기 모델 적용.
   - 오프라인 정량 평가(실제 화장 전후 20쌍 비교): 맨입술 대비 색차(CIEDE2000 ΔE) 중앙값 7.21 → 3.86으로 46.5% 오차 감소.
   - 입술 미세 결(L* 주름) 보존율: 글로시 0.87 → 0.99, 새틴 0.80 → 0.92 달성.
   - 블라인드 자연스러움 설문(v4, 쌍 사진 30장 판별): 단순/균형 정확도 86.7%, 자연스러움 점수 4.07 / 5.0 기록.
2) 전 부위(9개 존) 실시간 정밀 추적 및 흔들림·가림 해결:
   - 립, 블러셔, 아이섀도, 아이라인, 아이브로우, 파운데이션, 하이라이터, 쉐딩, 마스카라(룩 전용) 총 9개 부위 지원.
   - 앵커 분리형 One Euro 필터로 고개 흔들림(2Hz, ±60px) 최대 지연 오차 20.8px → 2.2px(89% 감소), 눈 깜박임 시 아이라인 지연 오차 6.2px → 1.2px(80% 감소).
   - 파운데이션 하단 지연 보정(`foundLowerFloor`)으로 고개 회전 시 볼·턱 맨살 띠 현상 18.7% → 1.3%로 감소.
   - 치아 오인식 방지 가드(`teethRed`/`teethBright`)로 벌린 입 치아 침범 비율 25% → 1%로 개선.
3) 대규모 실데이터 카탈로그 및 K-룩 연결:
   - 올리브영 메이크업 카탈로그 2,107개 제품(립 617개/5,189셰이드, 파운데이션 265개/1,551셰이드, 블러셔 181개/1,442셰이드, 하이라이터 55개/250셰이드, 쉐딩 28개/101셰이드 등) 연동.
   - K-연예인 영상 34건(제품 711건) + K-스타일 큐레이션 영상 73건(제품 906건) 연결 및 대표 시연 룩 6선 8부위 실시간 AR 시착.

[간단한 사용 흐름 (User Flow)]
1) 탐색: 홈/룩 탭에서 K-스타일·연예인 유튜브 메이크업 영상 확인 또는 개별 상품 선택
2) 시착: "AR에서 입어보기" 클릭 → 전면 카메라 On-Device 3D AR 렌더링 즉시 적용 (전체 화면 미러 모드, 1~4x 핀치 줌, 실시간 전후 분할 비교)
3) 맞춤 & 가이드:
   - 내 얼굴 비율 측정 기반 하이라이터(6종)·쉐딩(3종) 위치 추천 및 아이라인(6종)·아이섀도(4제형) 스타일 칩 전환
   - 카메라 위 실시간 "그리는 법" 4단계 드로잉 가이드(눈썹·섀도·아이라인·립 점선/화살표)
   - 채팅으로 "오버립 해줘", "턱선 쉐딩 진하게", "강아지 아이라인으로 바꿔줘" 등 자연어 즉시 조정
4) 구매 연결: 시착한 셰이드(또는 품절 시 ΔE2000 최근접 대체 셰이드 + 도포 횟수 안내)를 장바구니/매장 쇼핑 리스트에 일괄 담기

3. 시스템 구조 (아키텍처)
--------------------------------------------------------------------------------
[사용자 입력 → 처리 → 결과 전체 흐름]

1) [실시간 AR 시착 파이프라인 (100% On-Device, 기기 내부)]
   - 입력: 전면 카메라 영상 프레임 (`getUserMedia`, 720p~960p) + 사용자의 제품/룩/스타일 선택 상태 (`makeupStore`)
   - 처리 (WebView 내부 `faceTrackerHtml.ts`):
     ① 얼굴·가림 검출: MediaPipe Face Landmarker(478점 3D 정점, GPU) + ImageSegmenter(`selfie_multiclass_256x256`, 머리카락·손·컵 가림 및 피부 영역 분리)
     ② 시간 평활화 & 기하 보정: 부위별 One Euro 필터(눈꺼풀 고속 필터 분리) + 카메라 픽셀 기반 실제 속눈썹 경계 검출(`fitLidLine`) + 내 얼굴 비율 측정(`measureFaceShape`)
     ③ 실시간 조명 추정: 얼굴 법선 격자 기반 후보 조명 매칭(`matchLight`, US 11,030,798 원리 응용) + 배경 Gray-World/Gray-Edge 결합으로 조명 방향·색온도·노출 실시간 산출
     ④ 멀티패스 렌더링: 화면 공간 눈 캔버스(아이라인 R, 마스카라 G, 아이브로우 A) + 입술 화면 윤곽(Catmull-Rom 스플라인 + Taubin 평활 + 치아 보호 마스크) + UV 공간 마스크(섀도·블러셔·파운데이션·하이라이터·쉐딩) → WebGL PBR 프래그먼트 셰이더 합성
   - 출력: 60fps 목표 실시간 WebGL 메이크업 합성 화면 (얼굴 영상은 절대 서버로 전송되지 않음, 앱과는 Bridge 프로토콜로 숫자·상태 JSON만 통신)

2) [유튜브 K-룩 레시피 추출 및 데이터 파이프라인 (Backend Batch)]
   - 입력: 유튜브 메이크업 영상 URL 및 설명란 텍스트 (K-연예인 34건, K-스타일 73건)
   - 처리 (`backend/api`):
     ① 설명란 챕터 타임스탬프 규칙 추출(`description_recipe_service.py`) + Gemini VLM 영상 분석(`gemini_client.py`, 3회 추론 다수결 투표 `vote_recipes`)
     ② 부위(`zone`)·스타일(`style`)·시점(`timestamp`)·세기(`intensity`) 구조화 JSON 생성 → 사람 검수(`look_recipe_review.json`) → `geometry_for_style` 번역기를 통해 앱 `ZoneGeometry` 파라미터로 변환 후 PostgreSQL(`look_ar_settings.geometry`) 적재
   - 출력: 앱에서 룩 클릭 시 8~9개 부위의 색상·제형·기하 스타일이 한 번에 펼쳐지는 AR 프리셋 제공

3) [대화형 AR 조정 및 추천 파이프라인 (Client Rule + Chatbot LLM)]
   - 입력: 사용자의 자연어 발화 (예: "립 조금 더 진하게", "고양이 눈매로 바꿔줘", "콧대 하이라이터 켜줘")
   - 처리:
     ① 1차(즉시 반응): 클라이언트 규칙 엔진(`lib/arChatAdjust.ts`, 50개+ 한국어/다국어 표현 매핑)이 지연 없이 `patchGeometry` / `setIntensity` 실행
     ② 2차(복합 맥락): Envoy Gateway → `backend/chatbot`(FastAPI + Neo4j GraphRAG + OpenAI 호환 LLM)이 카탈로그 상품을 검색하고 닫힌 스타일 ID 기반 `set_geometry` / `set_intensity` AR 명령 반환 (색상 hex 환각 원천 차단)
   - 출력: AR 화면 즉시 갱신 + CIEDE2000(ΔE2000) 기반 유사 셰이드·대체 제품 추천

[사용 데이터 명확히 제시]
- 카탈로그 DB (`PostgreSQL` 원본 / `Neo4j` 챗봇 사본): 올리브영 메이크업 v29 스냅샷 2,107개 상품(수집 셰이드 HEX, 제형 7종, 카테고리 규칙 21종)
- 큐레이션 데이터: K-연예인 34개 영상(711개 제품 매핑 후보), K-스타일 73개 영상(906개 제품 매핑 후보), 대표 시연 룩 6선
- 평가·검증용 오프라인 데이터셋 (`research/data/`, Git 제외·비상업 연구용):
  - LaPa 얼굴 파싱 데이터셋 Test 2,000장 (정면·피부톤 균등 표본 200장 및 유효 1,840장 — 입술/눈 경계 IoU 측정용)
  - Makeup Detection 실제 화장 전후 비교 20쌍 (ΔE2000, 명암 폭, 하이라이트, SSIM 정량 평가용)

4. 사용 기술 스택
--------------------------------------------------------------------------------
1) 모바일 클라이언트 & AR 엔진
   - **Expo (SDK 58) + React Native + Expo Router + TypeScript**
     * 선택 이유: iOS·Android 크로스플랫폼 단일 코드베이스 운영 및 Expo Go를 통한 즉각적인 실기기 테스트.
   - **react-native-webview + WebGL (GLSL 자체 셰이더)**
     * 선택 이유: Expo Go 환경을 깨지 않고(커스텀 네이티브 C++ 빌드 없이) 3D 얼굴 메시와 픽셀 단위 물리 기반 렌더링(PBR)을 60fps급으로 구동하기 위함.
   - **MediaPipe Tasks Vision (`FaceLandmarker` + `ImageSegmenter` selfie_multiclass_256x256)**
     * 선택 이유: Apache 2.0 상업용 허용 라이선스이면서 모바일 웹/WebView GPU 가속으로 478개 3D 랜드마크와 머리카락·피부·손 가림 분할을 기기 내에서 동시 처리 가능.

2) 색과학(Color Science) & 그래픽스 알고리즘 (자체 구현)
   - **CIELAB (D65) & CIEDE2000 (ΔE2000) 색차 수식 (`lib/color/`, Sharma 2005 검증 완료)**
     * 역할: LLM 환각 없이 결정적 수식으로 피부톤-제품 매칭, 품절 시 최근접 셰이드 탐색, 도포 횟수(`1-(1-a1)^n`) 계산, 오프라인 발색 정확도 평가 수행.
   - **One Euro Filter + Catmull-Rom Spline + Taubin Smoothing**
     * 역할: 랜드마크 떨림과 지연을 동시에 잡으면서 입술·아이라인 곡선이 각지지 않고 실제 화장선처럼 매끄럽게 밀착되도록 처리.

3) 백엔드 & AI 파이프라인
   - **FastAPI (Python 3.12, uv 워크스페이스: `backend/api`, `backend/chatbot` 분리)**
     * 선택 이유: 카탈로그/추천 트래픽과 느리고 비용이 큰 LLM 트래픽을 격리(ADR-0001)하여 챗봇 장애가 쇼핑·AR로 번지지 않게 함.
   - **Gemini API (`gemini-3.6-flash`) + YouTube Data API v3**
     * 역할: 유튜브 메이크업 영상과 설명란에서 부위·순서·타임스탬프·스타일을 구조화 추출하고 3회 다수결 투표로 신뢰도 확보.
   - **PostgreSQL 17 (SQLAlchemy async + Alembic) + Neo4j AuraDB + Redis**
     * 역할: PostgreSQL은 상품·룩·AR 기하 설정(`geometry` JSONB)의 단일 원본(SSOT), Neo4j는 챗봇 GraphRAG 탐색용, Redis는 네이버 쇼핑 API 캐시 및 레이트 리밋 담당.

4) 오프라인 자동 검증 하네스 (`research/`)
   - **Playwright (Headless Chromium WebGL) + OpenCV (ECC 정렬) + scikit-image (SSIM)**
     * 역할: 앱의 실제 `faceTrackerHtml.ts` 셰이더를 수정할 때마다 20쌍/200장 얼굴에 동일 조건으로 렌더링하여 픽셀 회귀 여부(꺼진 기능 차이 0px), ΔE2000, IoU, 떨림을 자동 채점.

5. 현재까지 구현 내용
--------------------------------------------------------------------------------
[현재까지 구현 완료 및 실제 동작 가능한 핵심 기능]
1) **9개 부위 실시간 AR 렌더링 엔진 (`components/ar/faceTrackerHtml.ts`)**
   - **립 (`lip`)**: 층 쌓기 물리 발색, 7종 제형(매트·벨벳·새틴·크림·글로시·시어·쉬머), 화면 윤곽 스플라인, 입술 잔주름 반짝임 보존(`hlSparkle`) 및 골 반사 가림(`glossCavity`), 치아 오인식 방지 가드, 오버립·큐피드산 확장 지원.
   - **아이라인 (`eyeliner`)**: 6종 스타일 칩(내추럴·캣윙·강아지·스모키·갸루·언더포인트), 카메라 픽셀 기반 실시간 속눈썹 경계 맞춤(`fitLidLine`), 반 텍셀 AA 선명화(유효 농도 p90 0.45→0.89 개선), 눈 깜박임 전용 고속 필터.
   - **아이섀도 (`eyeshadow`)**: 4종 마무리 칩(매트·쉬머·글리터·글로시), 정점 UV-화면 메트릭 보정으로 늘어나지 않는 둥근 펄 입자(`lidSparkle`, 0.5px 이동 시 입자 유지율 21%→91% 개선), 투톤 그라데이션·애교살 포인트.
   - **아이브로우 (`brow`)**: 눈썹 고리 내부 2층 렌더링(1층 파우더 반투명 막 + 2층 어두운 눈썹 털 픽셀만 색도 이동), 스티커 테두리 없이 본래 눈썹 결 유지.
   - **파운데이션 (`foundation`)**: 커버력 슬라이더(불투명 안료 몫 vs 투명 필름 몫 조절), `selfie_multiclass` 기반 앞머리·머리카락 침범 제외(73,054px → 242px), 고개 회전 시 하단 볼·턱 맨살 띠 보정, 피부색 Lab 기반 셰이드 추천.
   - **하이라이터 (`highlighter`) & 쉐딩 (`contour`)**: 내 얼굴 랜드마크 비율 측정(`measureFaceShape`) 기반 하이라이터 6종·쉐딩 3종(V라인 턱선·콧대·헤어라인) 템플릿 및 추천 문구, 얼굴 법선·조명 연동 볼륨 명암.
   - **마스카라 (`mascara`)**: 연예인·스타일 룩 시착 시 영상 제품 유형(`slim`, `long_curl`, `volume_skinny`, `long`, `fine`)에 맞춘 속눈썹 렌더링.
   - **손·컵·머리카락 가림 처리 (`makeupOcclusion`)**: 입이나 눈을 손·컵·머리카락으로 가릴 때 화장 그래픽이 손 위에 붕 뜨지 않도록 부위별 피부 비율을 재서 실시간 마스킹.

2) **K-스타일 / K-연예인 룩 파이프라인 & 단계별 드로잉 가이드**
   - 유튜브 영상 내장 재생 + 영상별 사용 제품 부위별 정리 + 대표 시연 룩 6선 즉시 AR 시착.
   - 룩 상세 화면의 SVG 단계별 얼굴 일러스트 가이드("이렇게 그려요") + AR 카메라 위 실시간 따라 움직이는 4단계 점선·화살표 가이드("그리는 법", 룩마다 다른 `stepOrder` 및 각도·두께 문구 자동 조합).
   - 룩 시착 후 개별 색 칩 변경 시 룩 기하 모양(윙 각도 등)을 잃지 않고 `(수정됨)` 상태 유지 및 부위별 되돌리기, 품절/미보유 색상의 최근접 셰이드·도포 횟수·네이버 판매처 연결.

3) **대화형 메이크업 조정 & 편의 UX**
   - 자연어 채팅 입력으로 부위별 스타일·진하기 실시간 변경 (`arChatAdjust.ts` + 챗봇 `set_geometry`).
   - 전체 화면 AR 미러 모드(WebView 재시작 없이 패널 접기), 1~4x 두 손가락 핀치 줌, 실시간 원본/화장 분할 비교(Scissor), 개발용 캔버스 60초 영상 녹화·공유 기능.
   - 프론트엔드 73개 스위트 / 725개 단위 테스트, 백엔드 API 266개 / 챗봇 316개 테스트 통과.

[현재 부족한 점 / 문제점 2가지 및 선제적 해결책 (심사위원 질문 차단용)]
- **문제점 1: 발색 정확도(ΔE ≤ 1.5) 평가를 위한 '통제된 실측 데이터' 한계 및 따뜻한(노란) 실내 조명에서의 색 편차**
  * 원인: 현재 공개 데이터(Kaggle 20쌍)는 화장 전후 사진이 별도 촬영되어 화장하지 않은 입 주변 피부조차 조명·노출 차이로 ΔE 중앙값이 2.90임(따라서 ΔE ≤ 1.5 판정 불가). 또한 강한 노란 조명에서 Gray-World 보정이 입술 색에 영향을 주어 ΔE가 6.61로 상승함.
  * 해결책: ① 삼각대·노출·화이트밸런스를 고정하고 컬러체커를 포함한 자체 촬영 프로토콜(`research/protocol/hw01_capture.md`)과 피부 띠 ECC 정렬 도구(`hw01_compare.py`)를 이미 구축 완료하여 팀원 실측 촬영으로 기준선을 교체 중. ② 조명 추정 5단계(Huber IRLS 강건 회귀 + SH9 구면조화함수 램버트 적합 + Gray-Edge 결합)를 구현 완료(`TUNING` 스위치 탑재)하여 실기기 검증 후 활성화 예정.

- **문제점 2: 파운데이션·가림 분할 모델(`selfie_multiclass`) 동시 구동 시 중저가 기기 프레임 드랍 (약 15~22 fps)**
  * 원인: Face Landmarker 외에 256×256 이미지 분할이 주기적으로 돌면서 분할 호출 프레임에서 ~100ms 지연이 발생함.
  * 해결책: ① 분할 주기를 400ms로 늦추고 FPS가 20 미만일 때는 마지막 마스크를 유지하면서, 눈 아래 볼·턱은 랜드마크 윤곽 하한(`foundLowerFloor`)으로 즉시 따라가게 하여 체감 지연을 이미 크게 줄임. ② 기기 성능 단계(M9)에 따라 저사양 기기에서는 멀티클래스 분할을 가림 발생 시에만 선택적으로 켜도록 최적화 예정.

### [공통 / 기획 / 비즈니스 질문 (CEO · 기획자 심사위원)]

Q1. 이 프로젝트가 실제로 어떤 문제를 해결하나요?
- A. 온라인 화장품 구매와 K-뷰티 따라 하기에서 가장 큰 장벽인 "상세페이지 발색과 내 얼굴 위 실제 발색의 괴리"를 해결합니다. 기존 AR 앱처럼 얼굴을 깎고 뽀얗게 만드는 미화 필터가 아니라, 내 원래 피부톤·입술 주름·현재 조명 위에서 실제 제품이 어떻게 발리는지(Realism)를 구매 전에 확인시켜 주어 구매 실패와 반품을 줄입니다.

Q2. 이 서비스를 누가 사용하나요?
- A. 첫째, 유튜브의 K-아이돌·뷰티 크리에이터 메이크업을 내 얼굴에 직접 입혀보고 어울리는 제품 조합을 찾고 싶은 1030 뷰티 소비자입니다. 둘째, 한국 방문 전·올리브영 매장 방문 전에 K-뷰티 색조 제품을 미리 시착해보고 한국어 쇼핑 리스트를 만들어 가고 싶은 외국인 관광객입니다.

Q3. 기존 서비스(스노우, 뷰티플러스, 유캠 메이크업, 올리브영 등)와 차별점은 무엇인가요?
- A. 크게 세 가지입니다.
  첫째, **'No 미화 필터 · 물리 기반 층 쌓기'**입니다. 상용 앱은 입술 주름을 지우거나 템플릿 노멀맵을 덮어 스티커처럼 보이지만, 저희는 실시간 카메라에서 입술 잔주름 반짝임과 윗입술 그늘을 분리해 제품 색과 합성하므로 주름 결 보존율이 0.99에 달합니다.
  둘째, **'100% On-Device 프라이버시'**입니다. 얼굴 영상을 서버로 한 프레임도 보내지 않고 스마트폰 WebView WebGL 안에서 9개 부위를 렌더링합니다.
  셋째, **'K-유튜브 레시피 → 내 얼굴 맞춤 AR → 대화형 조정'**의 연결입니다. 영상 속 화장법을 AI로 추출해 내 얼굴 비율에 맞게 얹고, 채팅으로 "오버립으로", "강아지 아이라인으로" 즉시 수정할 수 있습니다.

Q4. 이 프로젝트가 시장에서 필요하다고 생각하나요? 수익화 가능성과 실제 기업 도입 가능성은?
- A. 올리브영·화해·다이소가 각각 "어디서 살지 / 성분이 뭔지 / 얼마인지"에 답한다면, 저희는 비어 있는 **"내 얼굴에서 실제로 어떻게 보이지?"**라는 구매 직전 확인 단계를 맡습니다.
  수익화는 ① 구매 연결 제휴 수수료(장바구니→외부 판매처 링크 전환), ② 자체 AR 엔진 구축 비용이 부담스러운 국내 중소·인디 뷰티 브랜드를 위한 경량 WebView AR 위젯(B2B SaaS) 및 셰이드 실측 등록 제휴로 확장 가능합니다. 특히 별도 네이티브 SDK 설치 없이 웹/앱 어디든 WebView 하나로 붙일 수 있어 실제 기업 도입 장벽이 매우 낮습니다.

Q5. 사용자 흐름(User Flow)을 설명해보세요.
- A. [홈/룩 탭에서 K-스타일·연예인 영상 탐색] → ["AR에서 입어보기"로 8~9개 부위 동시 시착] → [부위별 제형·스타일 칩 변경 또는 채팅("턱선 쉐딩 진하게", "오버립 해줘")으로 내 얼굴에 맞게 미세 조정] → ["그리는 법" 버튼으로 카메라 위 4단계 점선 가이드를 보며 화장법 확인] → [사용된 제품(품절 시 ΔE2000 최근접 대체 제품)을 쇼핑 리스트에 일괄 담기] 순서로 이어집니다.

Q6. 핵심 기능은 무엇이고, 왜 이 기능이 가장 중요하다고 생각했나요?
- A. 가장 핵심 기능은 **'실제 주름과 조명을 살리는 On-Device 립·메이크업 PBR 렌더링'**과 **'K-룩 레시피의 내 얼굴 맞춤 적용'**입니다. 가상 메이크업 앱에서 입술과 아이라인이 스티커처럼 붕 뜨는 순간 사용자는 결과를 신뢰하지 않고 구매로 이어지지 않기 때문에, 시각적 현실감(Track A)과 색상 재현(Track B)을 최우선으로 두고 개발했습니다.

Q7. 기능이 많은데(9개 부위, 룩, 채팅, 가이드 등), 우선순위는 어떻게 정했나요?
- A. 첫째, 사용자 시선이 가장 먼저 가고 구매 빈도가 가장 높은 **'립(Lip) 사실감'**을 P0로 두어 층 쌓기·제형 7종·치아 가드를 먼저 완성했습니다. 둘째, K-메이크업 재현에 필수적인 **'아이라인·섀도·블러셔·하이라이터·쉐딩'**으로 부위를 확장하되 모두 동일한 UV/화면 캔버스 파이프라인 위에서 동작하게 설계했습니다. 셋째, 색 계산과 매칭은 수식(CIEDE2000)으로 먼저 완성하고, LLM은 영상 레시피 추출과 자연어 명령 변환에만 배치해 개발 리스크를 통제했습니다.

Q8. 본인이 사용자라면 이 서비스를 계속 사용할까요?
- A. 네. 유튜브에서 아이돌 메이크업 영상을 볼 때마다 "저 립이랑 아이라인이 내 눈매·피부톤에도 어울릴까?"가 늘 고민이었는데, 영상을 보면서 버튼 하나로 내 얼굴에 바로 얹어보고, 안 어울리는 부위만 채팅이나 칩으로 바꿔본 뒤 대체 화장품까지 바로 찾을 수 있어 신제품 탐색할 때마다 쓰게 됩니다.


### [기술 / AI / 아키텍처 심화 질문 (실무자 · 기술 심사위원)]

Q9. 왜 LLM(및 VLM)을 사용했나요? 다른 방법으로는 안 되나요?
- A. 저희는 **"판단과 색 계산은 결정적 수식(코드)으로, 비정형 해석과 자연어 인터페이스만 AI로"**라는 엄격한 분리 원칙(원칙 1-5, 1-10)을 지켰습니다.
  - 색상 합성, 조명 보정, 제품 매칭(ΔE2000), 도포 횟수 계산에는 LLM을 절대 쓰지 않습니다(수식이 빠르고 정확하며 환각이 없기 때문).
  - 반면 ① 수많은 유튜브 영상과 설명란에서 부위·순서·시점·스타일 의도를 구조화하는 작업(VLM)과 ② 사용자의 무한한 자연어 표현("눈꼬리 좀 내려줘", "입술 도톰하게")을 정해진 기하 파라미터(`ZoneGeometry`) 명령으로 번역하는 작업(LLM)은 규칙만으로는 불가능하기 때문에 여기에만 AI를 사용했습니다.

Q10. 생성형 AI(GAN, Diffusion)로 얼굴에 화장을 입히지 않고 왜 3D 메시 + WebGL 셰이더 방식을 선택했나요?
- A. 세 가지 이유입니다.
  첫째, **실시간성(FPS)**입니다. GAN/Diffusion은 모바일 기기에서 매 프레임 구동하기 어렵고 서버로 영상을 보내면 네트워크 지연과 GPU 서버 비용이 발생합니다.
  둘째, **제품 색상 보존(무결성)**입니다. 생성형 모델은 제품 고유의 HEX 색상을 임의로 왜곡하고 피부 결까지 바꿔버려 구매 확인용으로 부적합합니다.
  셋째, **프라이버시**입니다. WebGL 셰이더 방식은 기기 안에서 카메라 픽셀의 명암과 주름을 유지한 채 수학적으로 증명된 색 혼합만 수행하므로 빠르고 안전하며 정확합니다.

Q11. RAG(GraphRAG)를 적용했다면 검색 성능과 환각 문제는 어떻게 해결했나요?
- A. 챗봇은 PostgreSQL 원본에서 동기화된 Neo4j 그래프 DB를 통해 제품-셰이드-성분-룩 관계를 탐색합니다. 특히 AR 제어에서는 LLM이 임의의 HEX 색상 코드나 숫자를 지어내지 못하도록, **닫힌 스타일 ID(enum)**만 출력하게 스키마로 강제하고 실제 `ZoneGeometry` 수치와 제품 HEX는 백엔드/클라이언트의 검증된 카탈로그에서만 매핑하도록 설계해 환각을 원천 차단했습니다.

Q12. 프롬프트와 레시피 추출 파이프라인은 어떻게 설계했나요?
- A. 유튜브 영상에서 레시피를 뽑을 때 단일 추론에 의존하지 않습니다. ① 먼저 YouTube API로 설명란 챕터 타임스탬프가 있는 영상은 규칙 기반으로 정확히 파싱하고, ② 영상 분석 시에는 Gemini에 부위별 허용 스타일 enum 스키마를 고정한 뒤 **3회 독립 추론 후 다수결 투표(`vote_recipes`)**를 거쳐 과반 이상 일치한 부위·스타일과 중앙값 시점만 채택합니다. ③ 최종적으로 사람이 검수(`approved: true`)한 레시피만 운영 DB에 반영됩니다.

Q13. 모델 선택 기준은 무엇인가요?
- A. - **얼굴/가림 추적**: 상업적 이용이 가능한 Apache 2.0 라이선스이면서 모바일 WebView GPU에서 실시간 동작하는 Google MediaPipe(`FaceLandmarker`, `selfie_multiclass_256x256`)를 선택했습니다. (비상업 라이선스인 BiSeNet/LaPa는 오프라인 연구·평가용으로만 격리했습니다.)
  - **레시피 추출**: 네이티브 비디오/멀티모달 이해와 구조화 JSON 출력이 가능하고 가성비가 높은 `gemini-3.6-flash`를 배치용으로 선택했으며, 503/429 혼잡 시 지수 백오프 재시도 로직을 구현했습니다.

Q14. 실패하거나 개선이 필요한 부분, 이 시스템의 한계는 무엇인가요?
- A. 두 가지 한계와 대응책이 있습니다.
  첫째, **스마트폰 카메라의 자동 노출·화이트밸런스 변화와 강한 유색 조명(노란 방 조명 등) 영향**입니다. 카메라 자체가 색을 왜곡하면 물리 셰이더도 영향을 받습니다. 이를 해결하기 위해 얼굴 법선 기반 3D 조명 매칭(`matchLight`)과 배경 Gray-Edge 조명 추정을 도입했고, 신뢰도가 낮거나 노출이 날아간 경우 사용자에게 조명 안내 배지(`ar.lightHint`)를 띄우도록 구현했습니다.
  둘째, **두꺼운 안경테나 극단적 측면(60° 이상)에서 랜드마크 밀림**입니다. 안경테가 눈꺼풀을 가리면 점이 테를 따라가는 한계가 있어, 카메라 픽셀에서 실제 속눈썹 어두운 경계를 찾는 `fitLidLine`과 신뢰도 기반 사전값 복귀 로직으로 방어하고 있습니다.

Q15. 성능(속도, 비용)은 어떻게 관리하고 있나요?
- A. - **속도(클라이언트 FPS)**: ① 비디오 프레임 콜백 동기화, ② 아이라인/입술 윤곽 텍스처 해상도 최적화 및 변화가 있을 때만 마스크 재렌더링(`repaintHlContour`), ③ 무거운 이미지 분할(`selfie_multiclass`)은 400ms 주기로 실행하고 20fps 미만에서는 이전 마스크를 재사용하되 하단 볼·턱은 랜드마크로 즉시 보정하여 지연을 숨겼습니다. ④ 로컬 채팅 규칙(`arChatAdjust.ts`)이 50개 이상의 표현을 0ms로 즉시 처리합니다.
  - **비용(서버/AI)**: 실시간 AR은 100% 사용자 기기 연산이므로 **서버 GPU 비용이 0원**입니다. 유튜브 레시피 추출은 실시간이 아닌 오프라인 배치 작업으로 한 번만 실행해 DB에 저장하고, 네이버 쇼핑 API는 Redis 캐시(6시간)와 분당 레이트 리밋으로 비용과 쿼터를 통제합니다.

Q16. 전체 시스템 흐름을 데이터 파이프라인 관점에서 설명해보세요.
- A. 1) **수집·정제 계층**: 올리브영 원천 DB(`raw_oy_*`)와 유튜브 영상 메타데이터에서 카테고리 규칙(21종)과 색상/제형 검증을 통과한 2,107개 상품을 `seed/catalog.json`으로 생성하고 CI(`test_seed_catalog.py`)가 무결성을 자동 검사합니다.
  2) **서빙·동기화 계층**: 병합 시 GitHub Actions가 PostgreSQL(`backend/api`)에 적재하고, `sync-graph` 잡이 API HTTP 계약을 통해 Neo4j(`backend/chatbot`)로 단방향 동기화합니다.
  3) **클라이언트·온디바이스 계층**: 앱은 React Query로 카탈로그·룩 데이터를 받아 Zustand(`makeupStore`)에 올리고, WebView AR 엔진은 카메라 프레임과 결합해 기기 내에서만 렌더링한 뒤 피부톤 추정치(Lab/ITA°)나 명령 결과만 JSON으로 주고받습니다.

Q17. 이 구조에서 가장 문제가 될 수 있는 부분(병목/장애 포인트)은 어디인가요?
- A. 가장 민감한 지점은 **'React Native 앱과 WebView 내부 WebGL 렌더러 사이의 브릿지 및 모바일 브라우저 자원 한계'**입니다.
  만약 화면 모드를 전환할 때마다 WebView가 리마운트되면 카메라 재시작과 MediaPipe 재로딩으로 2~3초간 검은 화면과 메모리 스파이크가 발생합니다. 이를 막기 위해 전체 화면 전환이나 핀치 줌, 부위 변경 시에도 WebView를 절대 언마운트하지 않고 단일 인스턴스를 유지하며, 브릿지로는 이미지 대신 수 바이트짜리 상태 JSON만 주고받도록 설계했습니다. 서버 측에서는 LLM 장애가 카탈로그/AR로 전파되지 않도록 `api`와 `chatbot` 컨테이너를 물리적으로 분리했습니다.

Q18. (예상치 못한 기술 질문 대응용 만능 템플릿)
- A. "말씀해주신 [해당 기술/방법론]은 현재 저희가 온디바이스 실시간성과 프라이버시(얼굴 영상 비전송) 원칙을 최우선으로 구현하는 과정에서는 1차 범위에서 제외되었으나, 향후 저희 프로젝트의 발색 정확도(Track B) 및 기기 호환성 목표와의 적합성을 면밀히 검토한 뒤 적절하다면 후속 고도화 단계에서 적극 반영을 고려해보겠습니다."
