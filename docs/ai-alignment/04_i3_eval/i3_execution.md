# I-3 격리 서비스 실행 연결

이 문서는 합성 계약 평가를 실제 서비스 호출에 연결하기 위한 격리·관측 조건이다. 기존 36개
시나리오, 47턴, 379개 assertion과 candidate 상태는 변경하지 않는다. 실제 LLM 호출이나 Gold
승인 기록이 아니다. 실행 결과는 실행별 기록과 보고서를 확인하며 문서의 구조를 성공 증거로
사용하지 않는다.

## 고정 대상과 격리 범위

- I-3 서비스 #229: `5a112874578069dab10bd6eaebbbd50e54d71db2`.
- 평가기 #230: `6acc98e434cb8800893f878fe3a2e061a94ee744`.
- #226 병합 이후의 develop 통합은 별도 작업이다. 두 고정 커밋으로 한 실험을 최신 develop
  또는 #226~229 통합 결과라고 부르지 않는다.
- `infra/compose/i3-evaluation.yml`은 PostgreSQL과 Redis만 만든다. API와 챗봇은 고정된 서비스
  코드로 별도 실행한다. 코드·테스트의 어느 부분을 대역으로 바꿨는지 실행마다 기록한다.
- 합성 발행·전성분·가격은 본 테스트를 위한 입력이며 실제 승인 근거가 아니다. 운영 DB,
  실제 QA 검수 DB 및 다른 작업의 컨테이너·볼륨을 연결하지 않는다.
- 이 문서의 준비 단계는 유료 LLM을 호출하지 않는다. 질문 해석 대역을 사용한 결과는 실제
  LLM 해석 성능으로 보고하지 않는다.

## 인스턴스 식별 및 쓰기 차단

`I3_EVAL_RUN_ID`는 실행마다 새로 만든 UUID를 사용한다. 격리 Compose 프로젝트 이름도 이 실행
ID를 포함하는 새 이름으로 지정한다. 기존 프로젝트가 이미 존재하면 재사용하거나 지우지 말고
중단한다. DB·Redis 컨테이너는 같은 `io.vishue.i3-eval.run-id`와
`io.vishue.i3-eval.purpose=synthetic-only` 라벨을 가진다. 컨테이너 이름을 고정하지 않는다.

Compose는 이미 로컬에 있는 `postgres:17-alpine` 및 `redis:7-alpine`만 사용하고 pull을 금지한다.
두 서비스는 `127.0.0.1`의 OS 자동 할당 포트에만 노출된다. PostgreSQL data와 Redis `/data`는
각 컨테이너의 tmpfs이고 Redis RDB·AOF는 비활성이다. DB·사용자·비밀번호 `i3_eval`은 격리
테스트 전용 값이며 운영 자격증명이 아니다. PostgreSQL 프로세스는 해당 실행의
`i3_eval.run_id` 설정을 보유한다.

어떤 쓰기·마이그레이션·fixture 발행보다 먼저, 실행기는 다음을 모두 확인해야 한다.

1. 실행기가 새로 생성한 정확한 Compose 프로젝트와 각 컨테이너 ID를 기록한다.
2. DB와 Redis가 예상 이미지·실행 ID·목적 라벨과 동일 프로젝트에 속하며 정상 상태인지
   Docker 메타데이터로 확인한다. 기존 컨테이너를 이름이나 포트 유사성으로 선택하지 않는다.
3. 실제 포트 매핑이 localhost 전용이고 DB DSN과 Redis URL이 각각 그 컨테이너의 포트와
   일치하는지 확인한다. 환경변수로 전달받은 임의 DSN을 그대로 신뢰하지 않는다.
4. DB에 연결하여 `current_database()`, `current_user`,
   `current_setting('i3_eval.run_id', true)`가 각각 `i3_eval`, `i3_eval`, 현재 실행 ID와
   정확히 일치하는지 확인한다. Redis 또한 해당 컨테이너·포트·라벨에 연결됐음을 확인한다.
5. 하나라도 누락·불일치·조회 실패하면 연결을 중단한다. 무관한 프로세스 또는 기존 DB에
   쓰거나 이를 테스트 대상이라고 추정하지 않는다.

자체 검증이 없는 독립 수동 DB 쓰기 명령은 이 절차를 대체하지 않는다. 테스트 전용 `test_only`
발행과 제한된 HTTP 노출은 격리 API에서만 허용한다. 기본 API가 비공개 합성 발행본을 숨기는
동작을 운영에서 우회하거나 운영에 테스트 플래그를 전달하지 않는다.

실행 중인 기존 Docker 컨테이너와 볼륨은 변경하지 않는다. 정리는 실행기가 생성했다고 기록한
**정확한 컨테이너 ID와 네트워크**에 한정하고, 삭제 직전에 프로젝트·실행 ID 라벨을 재확인한다.
대상이 다르거나 조회가 실패하면 정리를 중단하고 보고한다. 다른 프로젝트를 지우는 전역 정리,
이름 패턴만으로 한 일괄 삭제, 기존 볼륨 정리는 금지한다.

## 입력, 관측, 채점

합성 fixture의 논리 성분명·옵션·상품 ID와 실제 DB에 필요한 양의 정수 ID, 64자리 식약처
해시, 카탈로그 상품 ID 사이에는 사전 선언된 일대일 테스트 매핑이 필요하다. 옵션 소유권,
성분 순서·완전성·검수 버전, 가격 시각, 발행 상태는 동일 옵션의 독립 입력으로 구성한다.
출처 개정·권리·발행 조건은 테스트 DB 행으로 기록한다. 기대 assertion에서 실행 결과나 매핑을
역으로 생성하지 않는다.

기록은 다음 두 계층으로 분리한다.

1. 원본 관측: 실제 사용자 요청·HTTP 응답, 실제로 호출된 해석 계획, Catalog/근거 요청·응답,
   옵션별 판정, Redis 전후 상태 및 재시도·철회·오류. 이 기록은 응답에서 내부 계획을 역산하지
   않는다. 세션 토큰·소유자 식별자·비밀값은 저장하지 않는다.
2. 채점 입력: 사전 선언된 매핑만 적용한 별도 관측. 매핑 버전·fixture 해시·DB 스냅샷 해시·
   사전 해시·SUT SHA·실행 ID·모드·계획기의 종류를 기록한다. 매핑이 모호하거나 원본과
   대조할 수 없는 부분은 만들어 채우지 않고 NOT_OBSERVABLE로 남긴다.

Redis 세션이 없다는 것은 요청 인덱스 및 세션 상태를 실제 조회한 경우에만 `exists: false`로
기록한다. null이나 조회 실패를 세션 부재로 바꾸지 않는다. 후속 요청·재시도에서 필요한 토큰의
원본은 격리 메모리 안에서만 사용한다. 원본 및 채점 관측은 승인된 저장소 외부 파일에 둔다.

실행하지 못한 사례는 BLOCKED, 관측 부족은 NOT_OBSERVABLE, 관측된 계약 불일치는 FAIL이다.
PASS는 관측된 후보 assertion의 일치이고 과학적 정확도나 Gold 승인이 아니다. 사람 검토와
Gold 승인 대기는 실행 여부·점수와 별도로 유지한다. 첫 단계에서 질문 해석, 성분 부재, 옵션,
멀티턴, 근거 장애 대표 사례를 확인한 뒤 나머지 사례에 확장한다. 해당 시나리오가 서비스에서
지원되지 않으면 근거와 함께 FAIL 또는 BLOCKED를 보고하고 예상값을 임의 변경하지 않는다.

## 알려진 경계

- M02의 현재 재고 `in_stock`은 #229의 실제 Catalog 경로가 제공하지 않는 전제다. 합성 DB에
  입력했다고 현재 재고 확인으로 가정할 수 없다. 서비스 경로의 결과와 대역 경로를 구분한다.
- E03은 단순히 발행본을 비워 두는 것으로 권리 차단이 검증되지 않는다. 격리 `local_only`
  릴리스와 연결된 주장·출처에서 실제 발행·조회 차단을 관측해야 한다.
- M05의 고정 발행 UUID는 실제 자동 생성 UUID와 다를 수 있다. 테스트 생성 시의 결정적 ID
  주입 여부와 출처를 밝히거나 관측된 불일치를 기록한다. 결과를 사후 정답으로 덮어쓰지 않는다.
- I05의 성분 동일성 및 I06의 비교 참조는 응답만으로 역추론하지 않는다. 독립 관측을 얻지
  못하면 NOT_OBSERVABLE이며 I06의 상태 정책은 사람 확인 전 보류다.
- E06은 근거 API 오류가 챗봇 HTTP 200의 `claimStatus=unavailable`으로 변환되는 경로이며,
  M07은 챗봇 HTTP 503 재응답 차단이다. 둘을 혼동하지 않는다.
- Q06의 정확한 영문 성분 문자열과 실제 표준명 사이 불일치는 오라클 후보 문제일 수 있다.
  구현 결함으로 단정하거나 후보 정답을 임의로 바꾸지 않는다.

## 실행 전 확인

실행기·fixture·관측기의 실제 명령과 지원 시나리오는 각 파일의 인터페이스를 확인한 뒤 사용한다.
실제 서비스 호출 결과가 없는 경우 그 사례는 실행했다고 기록하지 않는다. 실패 및 미관측 원인,
각 구성 요소의 실제/대역 여부, 36개 사례·47턴의 분모와 상태별 개수를 별도로 보고한다.


## 이 실행의 명령과 결과

실행기는 이 Windows 환경의 격리 SUT worktree, 기존 두 Python 가상환경 및 승인된 출력
디렉터리 경로를 상수로 사용한다. 다른 PC에서는 이 경로를 명시적으로 구성할 수 있도록
후속 변경이 필요하다. SUT는 `5a11287`이고 추적 파일이 깨끗해야 하며, 평가 데이터와
평가기 코드는 `6acc98e`와 일치해야 한다. API·챗봇 프로세스에 실제 자격증명은 전달하지 않는다.

평가 worktree의 `backend/chatbot`에서 대표 실행 명령은 다음과 같다. 기존 가상환경에 설치된
의존성을 사용하며 패키지 동기화는 하지 않는다. 실행 전에 Docker Desktop과 로컬 이미지의
정상 상태를 확인한다.

```powershell
$env:PYTHONDONTWRITEBYTECODE = '1'
$env:UV_PROJECT_ENVIRONMENT = 'D:\dev\02_TeamProjects\SKN34-Final-Project\backend\chatbot\.venv'
uv run --no-sync python -B -m tests.i3_execution_runner --cases I3-Q01,I3-Q03,I3-I02,I3-O01,I3-M05,I3-E06
# Docker가 정상일 때 전체 후보를 시도한다. 실행할 수 없는 후보는 BLOCKED다.
uv run --no-sync python -B -m tests.i3_execution_runner --cases all
```

독립 해석 계획이 없는 사례, 사전 세션을 실제로 구성할 수 없는 사례 및 M02의 현재 재고
전제는 BLOCKED다. 이 실행에서는 Q01, Q03, I02, O01, E06의 5개 단일 턴을 실제로 관측했다.
E06의 근거 HTTP 503은 격리 API 미들웨어로 의도적으로 주입했고, 모든 해석 계획은 테스트
대역이다. M05 준비·정리 도중 Docker containerd 저장소가 읽기 전용이 되어 나머지를
실행하지 못했다. 단일 턴 5개가 후보 계약에 일치했으나 멀티턴 전체 경로는 검증되지 않았다.

원본 `i3-service-observations.jsonl`, 매핑 후 `i3-service-scoring.jsonl`,
`i3-service-report.json`, `i3-ingredient-mapping.json`은 저장소 외부의 승인된
visualizations 디렉터리에 별도로 저장했다. 실행 기록의 `promptHash`는 테스트 계획의
다이제스트이고 실제 프롬프트의 해시가 아니다. `dataSnapshotHash`는 seed 입력·매니페스트의
다이제스트이며 DB를 읽어 계산한 스냅샷 해시가 아니다. 이후 실행기의
`trace.observedPromptHash`는 실제 해석 대역에 전달된 메시지를 관측한 경우에만 기록한다.

Docker 장애로 해당 실행이 생성한 전용 컨테이너 두 개의 정리 여부를 확인하지 못했다.
Docker를 복구한 뒤 기록된 정확한 컨테이너 ID와 프로젝트·run-id 라벨을 다시 검증하고 그
대상만 정리한다. 공유 Docker 엔진을 임의로 재시작하거나 전역 정리를 실행하지 않는다.
