## 2. 근거 등급과 상태 계약 — 제안

1. **검수된 사실:** 서버가 반환한 동일 룩의 검수 레시피에 `reviewStatus=verified`, 버전, 검수자·근거 ID, 순서별 설명이 있고 출처와 해당 룩의 귀속을 확인한 경우에만 실제 영상 단계라고 설명한다. 단계별 타임코드·영상 근거, 제품·호수 사용 여부는 각 필드가 검수된 경우에만 별도 표기한다. 현재 `ReviewedRecipe`에는 레시피 단위 출처·근거 ID가 있지만 단계별 영상 구간 계약은 없다.
2. **제목·태그 기반 콘셉트 후보:** 실존 `kind/lookId`, 제목·태그의 직접적인 관련성만 제시한다. ‘출근’ 제목을 출근 관련 후보의 근거로 쓸 수 있지만, 영상의 자연스러움이나 눈·립 강도를 확인한 것처럼 말하지 않는다. 근거 없는 후보는 제외하고 부족하면 적은 수 또는 0개를 반환한다.
3. **일반 조언:** 실제 영상 순서·기법이 아닌 범용 안내임을 짧게 밝힌 뒤 사용자의 조건에 맞게 설명한다. 예시 조언과 실제 영상의 단계·사용 제품을 같은 카드나 문장으로 섞지 않는다. 선택한 룩을 그대로 재현한 순서라고 부르지 않는다.
4. **상품 연결:** 목록에 올라온 상품, 서빙 카탈로그 상품과의 연결, 특정 호수 소속, 실제 영상 사용 검수를 각각 따로 취급한다. `mappingVerified` 하나로 영상 사용·호수까지 승격하지 않는다. AR은 기존 제품·호수 귀속, 색·텍스처·부위 검증을 만족할 때만 제공하고 적용 완료라고 추정하지 않는다.

대화 상태는 기존 방의 `ownerKey/generation`, `styleContext`의 `kind/lookId/recipeId/recipeVersion/currentStep`, 후보 목록과 `styleRevision`을 재사용한다. 상황·분위기·눈/립 선호는 공통 대화 상태의 해당 방 범위에 구조화해 최신 명시 수정만 덮어쓰고 나머지는 유지한다. 제안 목록과 선택 룩은 별개이며 이전 목록은 메시지·결과 집합의 참조를 보존한다. 계정 전환·새 상담·명시 초기화 시 기존 소유권/세대 규칙을 따른다. 앱 메모리의 수명과 재시작 후 소실은 현재 구현의 한계다. 장기 기억·새 저장소를 이번 선행 조건으로 추가하지 않는다.

확인 질문이 필요하면 그 대상·후보 집합·상태 버전을 기존 공통 확인 질문 경로를 확장할 수 있는지 살핀다. **현재 `PendingClarification.missing_slot`은 product/shade만 허용하므로 룩 질문을 이미 지원한다고 가정하지 않는다.** 모델의 해석 결과만으로 상태를 확정하지 않고 서버 데이터와 현재 revision을 확인한다.

| **데이터 부족·오류:** “다음 단계 보여줘.” / 조회 실패 **E01** | 단계 없음, 버전 변경, 상품 삭제·잘못된 호수, 빈 검색과 API 실패를 구분. 원본 재조회 실패 시 오래된 데이터로 사실 확정 금지. | “안내할 다음 단계가 없어요.” / “정보를 불러오지 못했어요. 다시 시도해 주세요.” 각각 안내하고 실패 시 재시도 제공. 확정된 이전 선택을 보존하되 변경된 버전·잘못된 연결을 적용하지 않음. |

PR241 원본: `docs/ai-alignment/04_llm_stage4_evaluation/g2_g9_38_cases_L2_CLOSED_NOT_RUN.jsonl`의 **G6-N01** 실존 룩·상황 적합성, **N02** 승인 레시피·단계·영상 근거, **B01** 영상 실제 사용 제품·호수 오인 금지, **E01** 버전 변경·누락·오류 복구. 위 사례는 이 기존 계약과 연결한 구현 예시이며 신규 평가 체계가 아니다. 특히 현재 로컬 자료로 N02의 검수 레시피 전제 충족을 주장하지 않는다.

## 4. 구현 위치와 검증 — 제안

- `backend/chatbot/app/services/style_search_service.py`: 기존 Catalog 조회·ID 중복과 모델 선택 인덱스 검증을 재사용한다. **후보 선택**은 현재 조건과 실제 제목·태그 근거를 입력으로 제한하고, 근거가 부족한 조건은 unknown으로 남긴다. 후보별 인용 가능한 근거와 미확인 조건을 반환한다. 후보 선택과 사용자에게 보여줄 **답변 생성**을 분리한다.
- 답변 생성은 기존 LLM 클라이언트에 검증된 후보·조건·근거 수준만 전달하고, 구조화된 의도/조건 변경/답변 계획과 참조 ID를 받는 방안을 우선한다. 서버가 선택 후보·조건·출처·허용 주장·문장별 사실 참조를 검사하고 유효하지 않은 ID, 영상 사용·강도·순서·호수 주장을 버리거나 재생성 없이 안전한 답변으로 내린다. 일반 조언은 사실 근거와 분리된 별도 블록으로 제한한다. 자유 서술의 모든 주장 진위를 완벽하게 자동 검증할 수는 없으므로 검증할 수 없는 구체 사실을 생성 입력/출력에서 배제하고 대표 응답을 사람도 확인한다. 기존 클라이언트의 타임아웃·모델 오류 시 명확한 재시도와 안전한 최소 응답을 제공한다.
- `backend/chatbot/app/services/style_recipe_service.py`, `app/clients/catalog_client.py`, `app/schemas/style_recipe.py`: 현재의 룩 ID·version·상품 재조회·단계 경계 검사를 유지한다. 실제 검수 레시피 응답이 없을 때는 일반 가이드로만 표시하고, 검수 자료 연동 시 레시피와 단계별 근거가 실제로 서빙되는 계약을 추가한다. 기존 `videoAnalyzed: false`는 모델 입력으로 영상을 직접 분석하지 않았다는 현재 제약을 보존하며 검수된 외부 근거와 혼동하지 않는다. 상품 ID만 있는 연결과 검수된 호수 연결을 구별한다.
- `app/chat.tsx`, `components/chat/StyleRecipeResult.tsx`: 선택 시 발화와 안내가 실제 질문에 답하도록 개선하고, 같은 recipe 카드 중복 방지와 후속 질문 답변을 분리한다. 일반 가이드에 영상 재현 제목을 붙이지 않으며 상품 패널 반복을 줄인다. 카드에 제목·설명·근거 수준을 읽기 쉽게 표시하고, 이미지 URL 부재·로드 실패도 처리한다. 문자열 변경 시 네 언어 사전을 갱신한다.
- `store/chatConversationStore.ts`, `types/chatConversation.ts`, `hooks/useChat.ts`, `types/index.ts`, `backend/chatbot/app/schemas/chat.py`: 현재 방의 조건·후보 집합·선택·확인 질문을 최소 확장하고 owner/generation/styleRevision, 늦은 응답·중복 재시도·세션 초기화 보호를 재사용한다. 기존 제품·성분·AR·`/api/chat` 계약을 보존한다. 일반 상담에서 룩으로 되돌아올 때 대상과 단계는 최신 유효 상태를 기준으로 한다.
- `lib/styleCoaching.ts`와 현재 `style_advice`의 정규식은 명백한 입력에 대한 보조·결정적 단계 번호 처리에는 쓸 수 있다. **새 문장마다 정규식과 고정 답변을 추가하는 방식**은 표현 변화와 조건 정정·복합 의도에 취약하다. 구조화된 의미 해석 + 서버의 ID·상태·근거 검증을 우선하고, 특정 ID/순번과 보안·버전 불변조건은 결정적으로 처리한다. LLM 분류 실패와 구조화 출력 오류도 일반 상담을 망가뜨리지 않도록 처리한다.
- 관련 테스트는 기존 PR241 네 사례에 대화 조건 유지·정정, 선택과 이전 후보 구분, 일반/검수 단계 구분, ID·상품/호수 오류, 버전 변경, 실패 재시도, 늦은 응답 및 기존 상품·성분·AR 회귀를 연결한다. 실제 LLM 소량 확인과 모의 테스트·웹/Expo Go 검증을 별도로 기록한다. 별도 신규 평가셋이나 G단계는 추가하지 않는다.

## 5. 바로 구현 / 자료 준비 / 제품 결정

**바로 구현 가능:** 기존 제목·태그 범위의 후보 설명, 조건 유지·정정, 현재 선택과 과거 후보 구분, 반복 경고·상품 카드 개선, 답변 누락 수정, 일반 안내의 명확한 구분, 로딩·빈 결과·오류 복구, 응답/상태 검증 및 회귀 테스트. 추가 영상 분석이나 전체 데이터 검수를 선행 조건으로 삼지 않는다.

**이번 수정의 실제 범위:** 모델이 후보와 일치 표현, 눈·립 조절 의도를 구조화해 반환하고 서버가 후보 ID와 질문·제목/태그의 일치 표현을 확인한다. 답변 문장과 일반 조언은 현재 정해진 문구를 조합하며, 자유로운 LLM 답변 생성은 아직 적용하지 않았다. 조건은 기존 방의 제한된 최근 사용자 발화를 통해 전달하며 별도의 구조화 조건 상태나 일반적인 조건 삭제 검증은 아직 없다. 따라서 표현이 다른 동의어는 직접 일치 검증에서 빠질 수 있고, 오래된 조건의 명시적 철회 등은 추가 개선·확인이 필요하다.

**자료 또는 연결이 준비돼야 검증 가능:** 검수된 영상의 실제 단계·타임코드·기법, 실제 사용 상품/호수·출처, 실제 눈·립 강도에 근거한 필터, 승인된 영상 분석 근거의 API 제공. 데이터 담당자는 `lookId/videoId`, 상황·분위기·눈/립 표현의 값과 근거·검수 상태, recipeId/version·연속 단계·단계별 설명/타임코드·source/evidenceId·reviewer·검수 일시, 제품 ID·호수 ID·해당 제품 귀속·영상 사용 근거/검수 상태, 영상/이미지 권리·가용성을 제공한다. 기존 테이블·API·검수 프로세스를 먼저 확인하고 누락만 보완한다. 운영 데이터 및 미접근 환경은 확인 전 **미확인**이다.

**2026-11-23 사용자 승인 정책:**

1. 사용자가 방법을 물으면 **일반 가이드임을 분명히 표시하고 바로 답한다.** 선택 직후에도 실제 영상 순서로 오해하지 않게 표현한다.
2. **직접 관련된 텍스트 근거가 있는 후보만 표시하고 없으면 조건을 묻는다.** 영상 적합성·눈/립 강도는 검증 전 확정하지 않는다.

선택된 룩과 이전 추천이 모두 가능한 대명사는 확인 질문, 검수되지 않은 영상 사용 사실은 미확인, AR 적용은 실제 결과 확인 후에만 성공으로 표현하는 규칙은 PR241 근거 계약을 따르는 제안이며 별도 품질평가나 사용자 승인 단계를 만들지 않는다.
