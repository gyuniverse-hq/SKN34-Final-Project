# G8 복합 상담 구현 계약

## 최신 계약 — 마감 2단계 기능 플래그 경계 수정 (2026-11-28)

사용자가 1단계 조사 종료와 대상 10개 파일의 2단계 수정을 승인했다. 아래는 기존 플래그의 실행 경계를 맞추는 구현 결정이다. 기존 ⑤의 6묶음, 14능력/12시나리오, N01/N02/E01/B01 범위는 유지한다. 최종 검증 결과·중간 실패·검증 소스 식별값은 WORKLOG의 마감 2단계 절을 따른다. 최신 develop 통합과 실제 모델·로그인 웹 통합 평가는 후속 단계다.

- **G5:** 공통 `consult_knowledge`는 외부 클라이언트 생성 전에 G5 OFF를 `g5_disabled`로 차단한다. 최초·후속·저장 맥락에서 새 검색 실행과 기존 답변 재표시는 구분한다. 부모의 기존 failed 상태와 reason/limitations에 비활성 사유를 보존하고 재시도하지 않는다. 실행 가능한 상품·룩 결과와 근거는 유지한다. G5 ON의 기존 키·토큰·조회·검증 계약은 유지한다.
- **옵션:** G4의 한국어/G1 활성화 의존성은 유지한다. search/refine의 옵션·현재가/기록가 요구를 수행할 수 없으면 기존 `ProductAssessment(status=partial, outcome=unsupported, limitations=[option_search_disabled])`로 반환한다. 조회한 수는 0이며 정상 no_match/completed로 바꾸지 않는다. 외부 조회 실패, 근거 부족 unknown, 실제 조회 후 조건 불일치 no_match와 구별한다. 조회 전 미지원 답변에는 ‘찾았어요’라는 검색 완료 문구를 합성하지 않는다. 정상 상품·성분 조회 및 G4 ON 판정은 유지한다.
- **G8 OFF 저장 호환:** 최초 계획·ID 실행·중단 부모의 재개 유도·보유 답변 의미 변환을 건너뛴다. 새로운 일반 답변을 먼저 판정하고, 서버가 복원한 유효한 부모 및 관련 룩/상품 협력 맥락은 저장용으로 보존한다. 이전 active/cancelled 상태를 새 답변 상태로 사용하거나 오래된 계획을 자동 실행하지 않는다. ON으로 돌아가도 기존 계획 버전·작업 ID·질문·룩 문맥·권한 검증을 통과해야 한다. 저장 상담 GET 및 기존 답변 조회 계약을 변경하지 않는다.

공개 필드·DB migration·공용 플래그·Agent 구조·제한값을 추가하지 않았다. 과거 복원 실패의 원인은 미확정이며 이번 코드가 그 로딩을 고쳤다고 쓰지 않는다. 현재 복원 양성 및 이번 클릭 대상 오류는 1단계 조사 증거로 구분한다. 앱 인증·복원 소스는 수정하지 않으며 자동 룩 안내 중복은 통합 후 재관찰한다. N02 일반 상담에 검수 레시피를 필수화하지 않고 판매 옵션·영상 기법 근거·AR 경계를 유지한다.

## 최신 계약 — F1~F4 보완과 종료 경계 (2026-11-28)

기존6묶음·14능력/12시나리오·N01/N02/E01/B01을 유지한다. 이번 네 결함의 수정·실제 재검증 결과와 중간실패는 WORKLOG 및 `reports/g8/parent/stage6-remediation-review.json`을 따른다. 최근 상담 앱복원 실패가 남아⑤전체종료/⑥전체통과는 선언하지 않는다.

- 구버전 질문의taskId는 같은 역할의 waiting_user 작업이 유일한 경우만 복원한다. 새 전문질문은 정확한 소유ID와 pendingQuestions에 보존한다. 모호한 복수소유자를 임의선택하지 않는다.
- 같은 작업의 질문답변과 별도 조건변경은 원문·버전·소유자 검증 후 한update로 합친다. 전체작업 보존/철회와 답변의 충돌은 거절하고 미응답 형제질문은 서버가 보존한다. skin workflow는 상황설명과 관련추천을 함께 소유하며 그상황 답변의 예산조건을 독립상품작업으로 떼지 않는다. 실제로 독립한 검색은 별도ID로 유지한다.
- 전문기능의 구조화목표가 아직 없으면 원래 목표와 상황답변을 함께 전달한다. CompoundContext가 생긴 뒤의 예산등 후속은 현재변경만 전달해 불필요한 설명재실행을 피한다. 피부 작업에는 상품/룩화면 라우팅 맥락을 상속하지 않는다.
- 지원하는 읽기는 단일목표도 최초typed계획으로 기존전문기능에 위임한다. 일반대화·보호동작은 기존경계를 유지한다. 실제AR·기억쓰기 명령은 관련안내로 응답하며 권한을 확대하지 않는다. 조건변경·조언의 적용표현을 실제상태변경과 구별한다.
- N02와 기존Style은 일반단계 가이드 함수를 공유한다. 검수설명이 없으면 일반팁, 팁도 없으면 제목만 표시하며None을 사용자문구로 내보내지 않는다. 일반가이드를 검수된 영상기법/대체적합성/AR근거로 승격하지 않는다.
- fresh checkpoint 실행은shared advisory lock, 삭제는exclusive lock으로 보호한다. 중단된 내부호출의 종료대기 때문에 새active요청이503으로 막히지 않게 하되 active owner/request/lease·최종commit검사는 유지한다. 기존checkpoint를 임의복원하지 않는다. 진행중인외부HTTP 강제취소는 보장하지 않는다.

DBmigration·공개필수필드·권한·새timeout/재시도/캐시한도는 추가하지 않았다. 미확인성분/가격시점/부분조회 경계와판매optionId·AR분리는 그대로다. 앱복원불가를PG저장성공으로 대체하지 않는다. 다음범위는 기존묶음5 복원대기의 최소수정이며 새기능확장이 아니다. PR은 만들지 않는다.

## 최신 평가 결정 — ⑥ 실제 웹 평가 및 사람 검토 대체 (2026-11-28)

사용자의 명시적 지시로 G8의 답변 관련성·자연스러움·요청 충족 의미 검토는 **메인 에이전트가 실제 로그인 웹을 실행하고 질문·답변 원문, Tool 입력/결과, PG 저장을 대조하는 평가**로 대체한다. 독립된 사람 승인으로 표기하지 않는다. 원래 14능력/12시나리오와 N01/N02/E01/B01 및 사실·권한 계약은 유지한다. 공용 평가 JSON의 과거 humanReviewRequired 값은 삭제하지 않으며, 이번 G8 실행에는 이 사용자 결정과 `stage6-web-eval-review.json`의 실행별 정책을 적용한다. 실기기 AR/카메라·음성 및 다른 팀의 공동 실행을 웹 문장 평가로 대체하지 않는다.

판정 축은 요청 충족, 사용자 조건, 사실·근거 일치, 자연스러움, 후속/복원 연속성이다. PASS/PARTIAL/FAIL/BLOCKED/NOT_RUN을 구별하며 이전 Mock 또는 실제 PG 통과로 실제 웹 실패를 승격하지 않는다. 재시도는 이번 평가에서 일시 오류의 동일 검색 1회만 수행한 실행 절차이며 제품 정책을 바꾸지 않는다. E01은 검증 도구에서 주입한 Style UpstreamError와 실제 API를 구분한다.

**최신 결과: ⑥ 1차 평가 미통과. 앞선 ⑤ 종료 판정은 보완이 필요하다.** 기존 구현을 유지하면서 ⑤의 1(공통 진입/위임), 3(질문 소유권), 4(중단 직후 교체), 5(응답)에서 깨진 기존 기준을 재개해야 한다. 새 기능 범위가 아니다. 이번 실행은 평가·문서·신규 증빙만 승인됐으므로 제품 코드 수정은 하지 않았다.

- N01/N02의 기존 직접 진입 부모는 question.taskId가 null인 상태를 저장하고, 실제 질문에 대한 모델의 skin/owned_look 참조를 invalid_question_reference로 거절했다. 최초/후속 공통 계약과 구버전 호환을 대조할 결함이다.
- N02는 일반 가이드의 없는 step.description을 그대로 사용해 7개 `None`을 답변에 표시했다. 영상 검수 필요성을 완화하거나 일반 가이드를 금지할 사유가 아니라 기존 구조화 가이드 선택/표시 결함이다.
- delegate 경로에서 상품 상담 중 피부 복합 목표 및 일반 립펜슬/예산 검색을 실행하지 않고 미지원 조건 안내로 반환했다. AR/기억 요청도 매트/가격 안내로 응답했다. 권한 방어와 의도에 맞는 설명은 따로 판정한다.
- 실제 중단 POST는 200이며 구버전 결과 확정은 차단됐다. 그러나 앞선 G5가 끝나기 전 새 검색이 OSError/503으로 실패했다. checkpoint 잠금 경쟁은 코드와 시간상 가능한 가설이며 정확한 예외 프레임을 수집한 확정 원인으로 쓰지 않는다.

실행 원문·실제/모의·실패/재시도·소스/모델/데이터 경계는 최신 WORKLOG와 `reports/g8/parent/stage6-web-eval-*`를 따른다. 이 절은 아래 과거 완료 보고보다 최신이다.


## 최신 계약 — ⑤ 잔여 세 항목 범위 고정 (2026-11-28)

이번 수정은 결과 번호 선택, 답변의 반복·모순, 명시한 상품 종류의 검색 연결만 대상으로 한다. 기존 6묶음 종료 기준 및 14능력/12시나리오/N01·N02·E01·B01은 유지한다. 최종 실행·⑤ 종료 판정은 최신 WORKLOG와 `reports/g8/parent/stage5-three-item-record.json`을 함께 읽는다. 아래 과거 절은 당시 기록이다.

- **결과 선택:** 선택적 `ConsultationIntent.resultPosition`은 현재 `resultSelection`의 1부터 시작하는 위치다. 서버가 버전·범위·원문 번호·충돌하는 ID를 검증해 실제 작업 ID로 변환한다. 작업 배열/상품 카드 번호/보유 질문과 혼용하지 않는다. 모델에는 실제 선택지의 번호·이름·ID를 전달한다. 명시적 show는 전문 조회 없이 원래 결과 범위를 표시하고, 다른 질문은 저장 상태로 보존한다.
- **원문 연결:** 현재 발화의 `utteranceClauses`는 문장 경계에서 잘라낸 원문 복사 후보다. 여러 작업을 함께 보존하는 절은 같은 원문을 재사용한다. 모델이 작업별로 다시 쓴 인용은 계속 거절한다. 기존 미완료 검색을 다시 요청하면 update, 독립 목표면 addition으로 연결한다. 보존 절만 수행하고 읽기 요청을 누락한 실행은 성공으로 세지 않는다.
- **상품 종류:** 기존 피부 세부유형 enum과 별도로 선택적 `name_term`을 공통 상품 요구조건에 보존한다. 명시한 종류 단어가 모델의 인용과 실제 위임 발화에 모두 포함돼야 채택한다. 상위 전체 발화의 인용이 위임 절보다 길어도, 서버는 실제 위임 절에 존재하는 종류 단어만 근거로 연결한다. 현재 발화에 없는 과거 종류는 채택하지 않는다. 예산 변경에서 유지하고 명시 해제에서 제거한다. 기존 후보가 만료돼도 명시적 Catalog 재검색은 사용자 필터만 유지하고 만료된 후보·옵션 참조를 비운 뒤 실제 조회한다. 이전 후보 안에서 고르는 요청의 만료 방어는 유지한다. 실제 Catalog 상품명에 공백·대소문자 정규화를 적용해 종류를 판정하고 다음 옵션 요청의 query에도 연결한다. 이름 근거를 성분·개인 적합성·효능 근거로 확대하지 않는다. 불명확한 종류와 지원하지 않는 효능 조건은 구분한다.
- **답변:** 일반 관리 설명을 개인 진단/특정 제품의 원인 해결 입증으로 바꾸지 않는다. 상품 추천 뒤 효능 미입증 고정 문구를 자동 추가하지 않는다. G8 설명 위임의 미확인 항목은 검증된 필수 요구와 coverage에서 생성하고, 인용된 원문의 적용 범위는 유지한다. 출처가 없는 초안 제한 문구로 다른 전문 작업의 부족함을 다시 끌어오지 않는다. 지원된 조언이 있는 답변에 내부 coverage 미충족 문구를 그대로 덧붙이지 않는다. 상세 limitations/coverage와 partial 판정은 API·PG·앱 상태/근거에 보존하며, 인용된 원문의 적용 범위나 설명 전체 조회 실패는 본문에도 표시한다. Catalog의 실제 가격·성분 미확인 안내는 그대로 유지한다. 근거 원문·인용·실제 조회 실패·미식별 성분은 삭제하지 않는다.
- **표시·저장:** 한 결과를 갱신했으면 그 결과의 카드 범위를 표시한다. 이전 단일 범위 옵션과 새 일반 상품 카드를 섞거나 새 카드를 숨기지 않는다. 순수 일반 상품 복수 결과의 기존 카드 계약은 유지한다. 보존된 다른 작업의 긴 답변/질문을 재출력하지 않고 원래 결과·조건·질문·옵션은 저장한다. 전체 완료·부분·질문·실패 판정은 실제 작업 상태를 따른다.

- **누락 읽기 재계획:** `consultation_intent_service.prepare_turn(..., _repair_omitted=True)`에서 모델이 원문 읽기 절을 quote로 제시했으나 서로 겹치지 않는 보존 절만 실행 계획에 넣은 경우, 그 읽기 절만 동일 부모 해석기로 **최대 1회** 재계획한다. 원래 보존 조건을 합친 뒤 ID·버전·인용·권한 검증을 다시 통과해야 실행한다. 같은 소유자의 targets/질문 답변/완전히 동일한 update 중복은 하나로 정규화하고, 다른 소유자·추가 조건·철회 충돌은 거절한다. 재실패는 확인 질문이며 ‘보존 완료’로 성공 처리하지 않는다.

## 실행 중 중단·교체 앱 계약 — 2026-11-28

⑤ 묶음 4의 앱 연결. 아래 서버 계약은 유지한다. 저장 상담에서 실행 중인 요청에만 ‘답변 중단’을 표시한다. 클릭 즉시 기존 request/attempt 결과 반영을 차단하고, 서버 상태 확인 중에는 새 전송을 막는다. INTERRUPTED 확인 후 초안·서버 버전을 복구하고 새 requestId로 정상 전송한다. 새 전송 시 이전 중단 안내를 지운다. COMMITTED 또는 응답 유실은 기존 요청 상태·상담 조회 경로로 확인하며 임의로 중단 성공 처리하지 않는다. 계정 변경·다른 요청의 늦은 응답은 적용하지 않는다.

로그인 앱에서 실제 모델/G5 처리 중 중단 → 실제 Catalog로 토너·크림 검색 → PG 저장 → 최근 상담 복원을 확인했다. PG에는 INTERRUPTED/COMMITTED 두 요청과 교체된 턴의 메시지 2개만 남았다. 이미 진행 중인 전문 호출은 끝날 수 있으며 외부 모델 비용의 즉시 중단을 보장하지 않는다. 비저장 상담/비로그인 취소, 앱 강제 종료 직후의 별도 기기 복구, 모바일 터치 검증은 이번 완료 범위가 아니다. ⑤ 전체 종료 여부는 고정 6묶음 종료표를 따른다. 실제·모의 증거와 소스 차이는 WORKLOG/common-execution-control-app-* 참조.


## 실행 중 취소·교체 서버 계약 — 2026-11-28

⑤ 묶음 4의 서버 구현이다. 앱 연결과 실행 중단 UI는 별도 미완료다.

- POST /api/chat/conversations/{conversationId}/requests/{requestId}/cancel: 기존 인증 사용자에게 속한 활성 상담의 chat 요청만 처리한다. body 없음. 반환은 requestId, status, conversationVersion. 없는 요청/타인/다른 상담/state_update 요청은 404. ## 질문 소유권·협력 후속 정합성 — 2026-11-27

⑤ 고정 6개 묶음 중 1·2와 3의 연결 보완이다. 질문 무효화는 capability가 아니라 taskId로 판단한다. 구버전 질문에 ID가 없으면 해당 역할이 유일할 때만 소유자를 확정한다. 복수 후보를 임의로 하나에 귀속하지 않는다. 변경하지 않은 질문은 버전만 갱신하고 원래 입력 종류·needId·옵션 범위·레시피 버전 등 전문 메타데이터를 보존한다.

후속 실행에서 같은 scope의 completed/partial/waiting_user 결과를 보존한다. 재사용은 완료 승격이 아니다. 질문은 기존 소유자를 우선하며 다른 작업의 질문은 작업별 결과에 남는다. 질문에 답하면 해당 작업만 변경하고 형제 결과를 재조회하지 않는다. 결과가 필요한 referenceContext binding이 비면 설명 실행을 막고 dependency_unavailable로 남긴다. requires_success=False인 기존 독립 조회까지 일괄 차단하지 않는다.

부모 모델 입력에 dependsOn을 전달한다. 원래 복합 objective에 설명 문구가 남아도 별도로 생성된 설명 작업이 그 목표를 소유한다. 설명 철회+추천 변경은 두 작업의 변경으로 해석하며 서버는 의존 무효화·중복 방지·철회 우선 적용을 유지한다. 최초 계획은 전문 workflow 수와 사용자 목표 수를 구분한다. 문장별 치환이나 별도 문자열 실행 분기는 추가하지 않았다.

실제 모델의 철회 누락 및 최초 delegate fallback 실패를 보존했다. 마지막 실제 PG 실행은 첫 협력→설명만 재시도→설명 철회+예산 변경, 작업 ID·질문 메타데이터 보존·답변 저장 복원 통과. 앱 실행 범위와 마지막 메타데이터 수정의 소스 차이는 WORKLOG 참조. G5 partial은 전체 설명 완료가 아니다. ⑤ 전체, 임의 binding·모든 표현·실행 중 제어 완료를 선언하지 않는다. 새 운영 제한값/권한/DB migration 없음.

## 6개 묶음의 1·2 구현 반영 — 2026-11-27

아래 ⑤ 종료 기준을 변경하지 않는다. 이번에는 최초 공통 진입과 결과 제안의 첫 지원 연결을 구현했으며 모든 협력 종류 또는 ⑤ 완료를 선언하지 않는다.

- prepare_entry는 서버가 빈 계획 ID/버전을 생성하고 기존 의도 검증을 재사용한다. 최초 도구 plan_consultation_entry와 후속 도구 interpret_consultation_change를 구분한다. 독립 단일 목표는 기존 전문 진입으로 위임하고 빈 부모를 남기지 않는다. 후보 세션이 있는 요청은 기존 복원 소유 경로를 우선한다. G8 비활성/미설정/명시 실행 요청 방어는 유지한다.

실제 PG에서 발견한 공백: candidate session을 복원하지 않는 G7 경로에서 _reply가 비교의 기준 상품을 지웠다. 비교 응답에만 preserve_selection을 명시해 이미 선택한 상품/옵션/색 선택을 보존한다. 기존 검색의 선택 정리 규칙은 유지한다. 저장 시 생성된 룩 조건과 응답 문맥으로 scope digest를 계산하므로 시스템이 만든 정상 저장 변화가 다음 턴의 외부 조건 변경으로 오인되지 않는다. 실제 사용자 선택/조건 변경에 대한 scope 방어는 유지한다.

비교는 현재 두 상품 사실을 설명하는 경로이며 기존 추천 카드/번호를 바꾸지 않는다. 비교 성공은 ProductAssessment.evidence의 정확한 두 상품 ID로 검증한다. 비교 뒤 새 검색의 카드/상세는 별도 검증한다. Catalog 복수 일치는 임의 선택하지 않는다. 상품명 중복을 사용자가 해결하기 쉬운 후보 선택 UI와 기존 비교 가격 문구의 자연스러움은 후속 개선 사항이다. 새 운영 제한값이나 외부 권한 변경은 없다.


## 새 검색과 비교 후속의 작업 정체성 — 2026-11-27

⑤ 협력 완성의 공통 부모 계약 보완이다. product 역할과 작업 정체성을 구분하기 위해 ParentTask 및 변경/추가 제안에 선택적 productOperation(search/detail/compare)을 보존한다. 모델은 목표·작업 ID·operation을 함께 해석한다. 알려진 operation을 바꾸는 update는 서버가 거절하며, 독립 검색은 새 ID의 addition으로 실행한다. 비교 철회는 명시적인 요청이 있을 때만 한다. 질문 문구별 검색 예외를 추가하지 않는다.

새 search 작업의 전문 입력에는 이전 화면 상품과 productStyle 비교 문맥을 전달하지 않는다. 해당 검색 작업 자체의 조건/후보는 기존 product_context 계약으로 유지한다. 이전 비교+룩 생산자의 알려진 product 작업은 compare로 복원하고, 저장된 scope가 현재 scope와 일치할 때만 기존 표시 결과를 부모 캐시로 옮긴다. 출처를 알 수 없는 모든 구버전 작업을 문자열로 추측하여 분류하지 않는다. optional 필드는 구버전 저장 호환을 위한 것이며 미분류 과거 작업까지 동일 보호가 검증됐다는 의미가 아니다.

실제 18회 해석 중 기대 분기 16회, 비교 대상 교체 2회 미통과(제안 거절 1, 구체 상품 확인 질문 1)를 보존했다. 거절 원문을 기록하지 않아 첫 거절의 상세 원인은 확정하지 않는다. 확인 질문은 안전한 미진행이며 기대한 자동 update 성공으로 재분류하지 않는다. 실제 모델+Catalog+PG 3턴은 정상 ChatService 비교/룩 시작 → 토너·크림 새 검색 → 크림 예산 변경을 확인했다. Catalog HTTP는 기존 category=skincare 광역 조회이고 종류·예산은 기존 서버 판정으로 적용한다. 서로 다른 종류가 서로 다른 HTTP query라는 주장은 하지 않는다. 로그인 앱과 판매 옵션 양성은 이번 범위에서 미실행이다. 새로운 운영 제한값은 없다.

## 공통 답변 표시 계약 — 2026-11-27

후속 검증: 최근 상담의 일반 상품 카드 복원과 동일 상품 상세 이동을 현재 소스의 실제 로그인 웹 앱에서 확인했다. 아래 복원 미해결 문장은 최초 실행 당시 상태이며 최신 결과는 WORKLOG의 ‘최근 상담 복원·복원 카드 상세 확인’을 따른다. 이번 조사에서 제품 복원/인증 코드 결함을 확정하지 않아 그 코드는 유지했다. 실행 소스·개발 서버·브라우저 준비 상태를 확인한 후 로딩 종료/실제 카드/상세를 검증한다. API 200이나 PG 저장만으로 UI 복원 PASS를 부여하지 않는 원칙은 유지한다.

부모 작업의 objective는 전문 실행 입력으로만 사용한다. 내부의 `현재 변경 요청`, 공통 조건 및 task ID를 최종 답변 제목으로 붙이지 않는다. 독립 상품 결과는 서버가 보유한 ProductAssessment·현재/이전 검색 조건·실제 카드 ID로 IndependentAnswer를 만들고, 보존/예산 변경/종류 해제/후보 수를 설명한다. 특정 질문 문장을 답변 분기로 추가하지 않는다. 기존 N02의 판매 optionId 검증과 지식의 인용 재번호 계약은 유지한다.

부분 결과의 전문 설명·미확인 조건은 삭제하지 않는다. 여러 옵션 범위를 한 응답으로 표현할 수 없어 카드를 숨기는 기존 경로에서는 ‘아래 상품 카드’ 안내도 생략한다. 한국어 상품 문구를 정리한 범위이며 모든 언어의 상담 문체를 검증한 것은 아니다. 표시 정리에 별도 모델 호출을 추가하지 않았지만 목표/조건 해석 모델은 계속 사용한다. 모델 호출 0회를 G8 목표로 삼지 않는다.

실제 모델·Catalog·PG 4턴과 로그인 웹 앱 검증 결과는 WORKLOG/common-answer-app-*에서 구분한다. 로그인 앱에서 자연스러운 크림 예산 답변·카드·상세 이동과 PG 저장은 확인했으나 최근 상담 복원 로딩은 미해결이다. 비교 상담 뒤 ‘토너 찾아줘. 크림도 찾아줘’에서 토너 검색이 기존 비교 작업에 흡수된 사례도 발견했다. 공통 답변의 개선이 목표 해석과 앱 복원의 완료를 뜻하지 않는다. 판매 옵션 카드·복원된 카드의 상세 이동 및 Expo Go 검증은 이번에 완료되지 않았다.

## 최신 구현: 상품 종류·검증 결과·작업 보존 계약 — 2026-11-27

새 상품 실행을 시작하면 직전 ProductAssessment는 비운다. 요구 조건과 검색 context는 유지하지만 실패/취소된 새 조회에 과거 성공 판정을 붙이지 않는다. 재사용으로 실행을 생략한 결과는 보존된 판정을 유지한다.

아래 이전 “미충족 계약”은 발견 당시 기록이다. 이번 구현/검증 범위는 다음과 같다.

- 부모 상품 작업은 ProductRequirement.kind와 세션 토큰을 제외한 이전 BeautyContext를 task ID별로 저장한다. 전문 모델은 기존 조건에 대한 set/keep/clear/unknown 변경을 반환하고, 변경/해제의 quote는 현재 작업 요청에 실제 존재해야 한다. 보습 선호가 종류를 대신하거나 예산 변경만으로 종류를 없애지 않는다. 기존 공개 BeautyFilters/productType을 확장하지 않고 서버 소유 부모/요청 내부 계약으로 연결한다.
- 현재 지원하는 세부 종류는 toner/cream/lotion/serum/cleanser/sunscreen/mask/cleansing_cream/tone_up_cream/eye_cream이다. 이는 운영 횟수 제한이 아니라 Catalog 상품명으로 근거를 설명할 수 있는 최초 지원 어휘다. 기존 lip/cheek/eye/base/suncare와 foundation/cushion 계약은 기존 필드로 유지한다. 새로운 종류는 임의로 기존 종류에 매핑하지 않고 확인 질문/미지원으로 보존한다.
- 상품 분류는 현재 상품명/nameKo의 명시 표기를 사용한다. 증정품 문구를 제외하되 다른 종류를 나타내는 상충 표기를 버리지 않는다. 정보 없음/세트·상충 종류는 UNKNOWN. description에서 다른 제품을 언급했다는 이유로 유형을 확정하지 않는다. 지원 동의어 확장은 Catalog 실제 사례/회귀 근거와 함께 관리하며, 질문 전체에 대한 정규식 분기는 추가하지 않는다. 상품명 근거는 효능·판매 옵션·AR 근거와 별개다.
- ProductAssessment는 matched/no_match/unknown/unsupported와 completed/partial/waiting_user/failed 의미를 구분한다. 추천 후보의 종류 판정 근거와 조회·미확인 수를 보존한다. 가격·성분 등 기존 ConditionCheck에서 미확인인 항목은 완료 판정에서 빠뜨리지 않는다. 부모 어댑터는 완료 상태와 assessment 상태 일치, 표시 상품 ID와 요구 종류의 match 근거 일치를 검증한다. 조회 성공이나 응답 문자열만으로 완료 처리하지 않는다.
- explicit preserve는 같은 결과/조건을 보존하며 도구를 실행하지 않는 공통 작업 변경이다. update/withdraw와 같은 task ID에서 충돌하면 거절한다. 보존 대상이 변경된 선행 작업에 의존하면 구버전 결과를 보존하는 대신 확인을 요구한다. 보존-only는 기존 결과를 유지한다. 모든 capability에 적용하며 특정 한국어 문장용 실행 분기를 두지 않는다.
- 기존 5개 부모 작업·표시 후보 6개·공유 deadline/재시도 제한을 유지한다. 추가 LLM 판정 호출이나 후보별 모델 호출은 만들지 않았다. 이번 새 상태와 함수에 별도 임의 운영 횟수/캐시/보관 한도는 추가하지 않았다.
- 최종 실제 모델·Catalog·PG 고정 4턴 2회와 관련 회귀 통과 범위는 WORKLOG/증빙을 따른다. 인증/최초 부모 seed는 합성, 로그인 앱/G5/전체 G8 평가는 별개다. 상품명 기반 종류 근거를 전 상품의 정교한 용도 분류로 확대하거나 고정 사례 통과를 자유로운 모든 표현의 안정성으로 주장하지 않는다.

## 실제 연결 검증에서 확인한 미충족 계약 — 2026-11-27

common-parent-connected-* 실행은 현행 부모→실제 G5/Catalog→최종 응답 결합을 확인했으나 상담 품질 완료 판정은 실패했다. `보습용 크림` 입력에 토너·클렌징 젤·미스트·마스크·로션을 반환하면서 product가 completed로 저장됐다. 향후 공통 상품 계약은 **상품 종류 같은 필수 조건과 보습 선호 같은 정렬 조건을 분리하고**, 명시적 해제 없는 상품 종류는 후속 변경에도 보존하며 결과가 필수 조건을 충족했는지에 따라 완료/부분/미확인을 판정해야 한다. 이번 기록에서 해당 수정 구현을 완료했다고 주장하지 않는다. 특정 질문을 위한 정규식 추가는 해결 기준이 아니다.

실제 G5는 보습 순서 전체·일반 차단제 덧바르기 질문에 제한된 문헌 주장만 남겨 partial을 반환했다. 근거가 있는 문장이라는 이유만으로 질문 전체에 대한 답변 완료로 승격하지 않는다. 독립 설명+상품 결과의 결합과 N01 지식 조건의 실제 다음 Tool 입력 연결은 별도 검증 항목이다. 이번 실행의 초기 부모 상태는 합성, 전문 서비스/모델/Catalog는 실제이며 PG 대화 저장·로그인 앱은 NOT_RUN이다.

## 최신 B 계약: 새 독립 목표 분해·작업 ID 실행 — 2026-11-27

이 절이 아래 B 단계별 기록의 최신 기준이다. 기존 N01/N02 전문 내부 조회·조건·근거 계약은 유지한다.

- 활성 G8 부모에 additions를 통해 독립적인 knowledge/product/style 조회 목표를 추가한다. 각 항목은 capability, 현재 발화의 정확한 목표 quote, 필요할 때 동일 발화의 sharedQuotes다. 수치·상품 ID를 부모 모델이 만들어 채우지 않는다. 동일 역할의 서로 다른 목표를 허용하며 서버가 `task-<uuid>` ID를 발급한다. 신규 의존 복합 목표를 독립 조회처럼 쪼개지 않는다. 지식→상품 조건 연결은 N01, 보유 룩은 N02의 기존 전문 실행을 사용한다.
- 모델 targets/changes, 부모 수집·대체, 실행 함수/결과 맵, 의존 참조, 질문, 재시도는 taskId 기준이다. 기존 문서의 taskId 없는 행은 goal을 ID로 읽으므로 이전 저장 형식과 호환된다. 역할 이름만으로 복수 작업을 한꺼번에 선택하지 않는다. 같은 역할이라도 실패한 ID만 재시도하고 다른 성공 결과는 유지한다.
- 부모 실행기는 요청 의존성을 위상 순서로 정렬한다. 없는 의존성·순환은 실행 전에 거부한다. 기존 owned_look→knowledge 연결은 앞 결과의 실제 StyleRecipe를 G5 referenceContext로 전달하며 레시피를 G5 문헌 근거로 취급하지 않는다. 보유 확인이 부분 완료여도 독립 설명이 가능한 기존 동작은 유지한다.

## 공통 구조 B: 후속 해석·실행 경계 1차 연결 — 2026-11-27

## E01 상품 비교 + 룩 조회의 부분 성공 계약 (2026-11-27 실제 연결 검증)

## 현재 보완 계약: 선언 범위·옵션 확인 수준·목표 후속·입력 지문 — 2026-11-27

사용자 승인 범위의 구현 결정이며 앞선 상품별 처리 계약 중 선언/질문 해석은 본 절을 우선한다. 전체 6개 묶음 중 **1. N02 결함 보완**에 해당한다.

- **확인 수준:** OwnershipDeclaration.scope는 legacy/zone/product/option이다. 상품명만의 보유 선언은 product이며 정확한 판매 옵션의 보유 확인이 아니다. 정확한 현재 보유 기억, 유일한 옵션 명시 답변, 옵션을 표시한 서버 질문에 대한 답변만 해당 옵션 충족을 뒷받침한다. 상품 미보유는 그 상품의 연결 옵션 미보유로 해석할 수 있으나 다른 상품으로 확대하지 않는다. 기존 scope 없는 양성 선언은 legacy로 복원하고 정확한 옵션 확인으로 승격하지 않는다.
- **후속 질문:** 정확한 옵션 질문은 목록 중복 여부와 무관하게 옵션명/호수를 표시한다. 옵션 이름이 없는 legacy shade는 확인 가능한 ID를 표시하며 임의 호수 이름을 만들지 않는다. ParentQuestion.ownershipScope로 실제 질문의 확인 범위를 저장한다. 과거 질문에 이 필드가 없으면 짧은 긍정 답변만으로 옵션을 확정하지 않고 다시 질문한다. 현재 보유 기억의 다른 옵션은 그대로 보존하고 영구 기억을 자동 수정하지 않는다.
- **조건 해제:** 특정 상품 선언의 해제가 같은 부위 다른 상품의 선언을 지우지 않는다. 기존 부위 전체 선언을 남긴 채 한 상품만 예외 처리하는 복합 범위 연산은 이번 완료 범위가 아니다. 기존 전역/부위 선언 해제와 레시피 변경 무효화는 유지한다.
- **부모 목표 후속:** 활성 owned_look 작업과 같은 선택 룩/서버 맥락이 있을 때, 설명 철회+상품 요청만 있는 후속도 N02 진입을 허용한다. 사용자 문장은 보존하고 서버 전용 route hint로 실행한다. 가격·성분·보유 선언을 유지하며 추가 G5는 실행하지 않고 기존 knowledge 작업은 superseded로 처리한다. 다른 설명 요청이 함께 있으면 그 요청은 유지한다. AR/상태 변경·피부 상담·명시적 지식 요청의 기존 분기는 확장하지 않는다.
- **입력 지문:** N1 입력에 전체 부위 선언, 상품별 선언(scope/현재 확인 여부 포함), 서버 후속 답변(needId/recipeVersion/답변/확인 범위), recipeVersion을 추가한다. 기존 실제 보유 목록과 레시피 입력도 유지한다. 정렬된 JSON으로 지문을 만들므로 선언 map의 삽입 순서만 바뀌면 동일하고, 대상/답변/확인 수준이 달라지면 달라진다. 입력 지문 보완은 미래 캐시 재사용을 승인하거나 구현한 것이 아니다.

검증 완료 범위와 실제/모의 구분은 WORKLOG 및 `reports/g8/parent/n02-scope-*`를 따른다. 새 운영 상한·공개 앱 API·DB 스키마·AR/결제 계약 변경은 없다. 범용 자연어 지시어/생략어 해석, 일반 상품 상담의 선택 옵션 가격 조회, E01/B01·재계획·실행 재개는 후속 묶음이다.


## 현재 보완 계약: 같은 부위의 상품별 처리와 최종 판정 — 2026-11-27

사용자 승인에 따른 **구현 결정**. N02 상품 목록의 동일 부위 항목을 하나로 합치지 않는다. `OwnedLookCoverage`는 recipeVersion·zone·productId·optionId·shadeId(식별 불가 항목은 label 포함)로 안정적인 needId를 만든다. 동일 옵션의 반복 목록은 합치고 확인된 productUsages의 stepOrders는 보존한다. 다른 상품/옵션은 독립적으로 보유·미보유·미확인 상태를 갖는다. 정확한 옵션이 없는 목록 항목도 evidence_missing으로 남겨 다른 상품의 성공에 가려지지 않게 한다.

- **역할과 필수 여부**: 검수된 사용 근거가 있는 항목만 reviewed_usage와 단계 번호를 연결한다. 나머지는 product_listing이며 공동 사용·필수·서로 대체 가능 여부는 unconfirmed다. 검수 근거 부족으로 기존 상품 상담·정확한 옵션 추천을 차단하지 않는다. 목록 대조 완료는 영상 메이크업 재현 방법의 검증 완료를 뜻하지 않는다.
- **입력 연결**: N1의 상품별 coverage를 P1/V1/R1에 전달한다. 상품 조회는 중복 productId를 제거하지만 논리적 needId와 정확한 옵션은 유지한다. 같은 상품의 옵션 A 보유를 옵션 B 보유로 확장하지 않는다. 추천·조건 판정·appliedMemories는 정확한 대상에 결속한다.
- **후속 질문**: 부모 질문에 needId와 recipeVersion을 저장한다. 짧은 “없어/있어”는 해당 항목에만 적용한다. 종전 zone만 있는 저장 질문은 하위 호환한다. 이름/옵션 ID가 유일하게 식별되는 명시 답변은 itemDeclarations에, 부위 전체에 대한 명시 답변은 기존 declarations에 저장한다. 예산 변경은 유지, 상품별/부위별/전체 선언 해제는 해당 저장 선언을 제거한다. 부위 전체 선언을 유지한 채 한 상품에만 예외를 만드는 복합 해제는 후속 범위이며, 룩·레시피 변경은 무효화한다. 상품별 미보유 답변이 저장 기억과 충돌하면 재확인하며, 확인 후에도 영구 보유 기억을 자동 수정하지 않는다. 현재 한국어의 제한된 명시 구문 처리이며 자유로운 모든 지시 대명사·역할 표현 해석은 미완료다.
- **최종 판정**: R1은 owned/recommended/ownership_unknown/evidence_missing/excluded/lookup_failed의 항목별 outcome을 생성한다. 부모는 카드 존재나 추천 전 N1 상태가 아닌 이 최종 요약을 소비한다. 모든 대상의 보유 또는 적합 추천 확인 시 completed, 사용자 보유 답변이 필요하면 waiting_user, 모든 대상이 조회 실패이면 failed, 나머지 미해결이 있으면 partial이다. 제외와 미확인을 실패로 합치지 않는다. 완료 범위는 이번 N02 요청의 상품 대조·추가 후보 확인이며 G8 전체 완료가 아니다.
- **저장·공용 계약**: 기존 G7 서버 JSON 맥락에 itemDeclarations와 부모 질문 대상만 추가한다. 외부 응답의 신규 공개 필드, DB migration, 장바구니/결제/AR 계약 변경은 없다. 실행용 최종 요약은 private response 및 전문 작업 trace에 남고 부모 결과 상태는 기존 맥락으로 저장된다. 클라이언트가 후속 실행 권한을 직접 주입하지 못한다.
- **제한값**: 새 운영 상한은 도입하지 않았다. 기존 기억 20개, 상품 조회당 6개, OptionSearchRequest의 optionScope 42개 및 기존 시간 제한을 유지한다. itemDeclarations는 현재 레시피 needId 집합으로 매 실행 정리한다. 42개를 넘는 동일 상품군의 옵션 묶음 분할은 이번에 검증하지 않았으며 확장 검증 대상으로 남긴다.

검증 구분: 합성 Catalog/영상 사용 근거로 상품·옵션·단계 분리 및 부모 완료/부분 완료를 검증했다. 실제 Catalog의 `XyqUi5HKkX8`에서 하트퍼센트 립펜슬 `A000000183683-001` 보유(합성 사용자 기억)와 롬앤 틴트 `A000000158896-010` 미보유를 구분해 후자만 실제 옵션 조회·추천했다. 실제 영상 사용법의 사람 검수 또는 실제 사용자 보유 확인은 아니다. 격리 PostgreSQL의 정상 Chat API 6턴 저장·복원은 실제 DB/모의 Catalog/인증/모델 구성이며, 실제 외부 모델 호출은 0회다. 상세 결과는 WORKLOG와 n02-needs-* 증빙을 따른다.


## 현재 보완 계약: 부모 후속과 판매 옵션 기억 — 2026-11-27

사용자 승인 범위: 부모 후속 분기·설명 철회 및 판매 옵션의 상담/보유 기억 연결. 기존 구현을 유지하며 다음 계약을 추가한다. 아래는 이번 **구현 결정**이며 범용 재계획·취소/실행 재개 완료를 뜻하지 않는다.

- 부모의 설명 전용 Style 분기는 현재 선택 룩과 저장된 부모 룩이 일치하고, 이전 작업이 owned_look/style인 경우에만 허용한다. skin 부모의 “상품은 됐고 사용 순서만”은 기존 N01 계획 경로에서 처리한다. 실제 부모·전문 그래프와 모의 계획 모델로 목표 유지 및 상품 Tool 무호출을 검증한다.
- N02의 추가 지식 작업은 긍정적 설명 요청에만 배정한다. 설명/원인/주의점/원리를 빼거나 필요 없다고 하는 명시적 철회 절은 제외한다. 다른 절의 설명 요청은 유지한다. 전체 설명 철회 시 이전 knowledge 작업은 superseded로 둔다. 현재 제한된 한국어 구문 처리이며 임의 언어의 완전한 의도 해석이라고 주장하지 않는다.

- 클라이언트 optionId는 신뢰하지 않는다. 기존 Catalog GET /api/products/{productId}/options/{optionId}의 현재 응답으로 상품 소속과 식별자 일치를 확인한다. 없는 옵션은 404/409로 거부하고 조회 실패는 가용성 오류로 처리한다. 기억을 위한 옵션 이름·소속·선택적 AR 연결만 사용하며 클라이언트 가격/이미지를 기억의 사실로 저장하지 않는다.

- 옵션 기억끼리는 productId+optionId로 동일성을 판단한다. 같은 상품의 두 옵션, 옵션 기억과 legacy 상품/색상 기억을 자동 병합하지 않는다. N02 보유 작업은 현재 옵션을 재조회한 뒤 사용한다. 과거 AR 색상이 삭제되어도 판매 옵션이 존재하면 보유 사실을 유지하고 AR shade는 현재 유효한 경우만 남긴다. 옵션이 삭제되거나 조회되지 않으면 미확인으로 유지한다.

| 영상의 구체적 사용법 단정 | 해당 주장에 연결된 사용 근거 | 일반 가이드로 제한. 영상 시청·사람 검수 사실을 만들지 않음 |
| AR 표시·실행 | 기존 AR 색상·부위·제형·권한 계약 | 판매 가능 여부와 별개로 AR 미지원. 옵션 이름으로 색상 생성 금지 |

**구현 결정.** API 영상 상품에 catalogOptionId/catalogOptionSource를 추가하고 catalogShadeId는 별도로 유지한다. 원본 판매 옵션의 상품 소속과 삭제 여부를 확인한다. 명시 optionScope는 (productId, nullable shadeId, optionId) 전체로 처리하여 색상 없는 여러 판매 옵션을 합치지 않는다. 옵션 이름은 OptionCandidate.optionName으로 반환한다. 판매 옵션 확인만으로 전성분 근거를 승인하지 않으며, 성분 조회 실패·미검수·생산 환경의 합성 근거는 UNKNOWN으로 남긴다.

N02는 consultationZone(상담용 분류)과 zone(기존 사용/AR 판단)을 구분한다. 검수된 recipe가 없어도 확인된 옵션의 보유 대조·미보유 후보 조회가 가능하다. 판매 옵션 경로는 조건이 없어도 실제 옵션 조회를 다시 수행한다. 새로운 판매 옵션은 이름으로 추측하지 않고 API가 확인한 식별자만 사용한다. G7 inventory.product의 선택적 optionId는 productId와 함께 보존하며 기존 shadeId 전용 기억도 유지한다. 상품명을 변경하면 기존 식별자는 제거한다.

응답 ownedLookOptions와 저장된 displayPayload는 nullable shadeId 및 optionId를 유지한다. 앱 카드에서 판매 옵션 이름을 표시하고 AR 색상이 없으면 상품 상세로 이동하되 shadeId를 만들어 전달하지 않는다. 기존 shadeName 응답 필드는 호환성을 위해 유지하며 판매 옵션 이름을 담을 수 있다. 구매 화면의 실제 옵션 자동 선택 기능을 새로 구현한 것으로 보지 않는다.

기존 조회당 6개 상품·42개 작업 한도, 저장/동의 정책, AR 렌더러·실행 권한은 유지한다. 새 운영 제한값은 없다. 상세 실행 증거와 미실행 범위는 WORKLOG의 최신 항목을 따른다.

## 판매 옵션의 상세·장바구니 계약 — 2026-11-27

**사용자 확정.** 판매 optionId를 상품 상세와 장바구니까지 보존한다. 이번 범위에서 옵션 결제는 제한하고 기존 상품·shade 구매 경로는 유지한다. PR 생성은 미승인이다.

**구현 결정.** N01/N02 카드 → productHref의 optionId → GET /api/products/{productId}/options/{optionId} → CartItem.optionId로 연결한다. 서버는 raw 옵션의 상품 소속과 상품/옵션 delisted_at을 재확인한다. 잘못된 소속/미존재 옵션은 404이며 다른 옵션이나 상품 대표 값으로 대체하지 않는다. 옵션이 사라지거나 조회가 실패하면 장바구니 항목 자체는 보존하고 사용 불가로 표시한다. 잘못된 옵션 경로를 일반 상품 구매로 바꾸지 않는다.

가격은 해당 옵션의 최신 기록 priceKRW, 기존 공통 기준값 collected_snapshot, observedAt, sourceUrl을 반환한다. 현재 판매가 보장이 아니다. UI는 참고 가격과 기준일을 표시하며 가격 누락은 '가격 확인 필요'로 표시한다. 시간대가 없는 원본 시각에는 UTC/KST를 임의 부여하지 않는다. 가격 미확인 항목이 있으면 합계를 확정 금액으로 표시하지 않는다.

이미지는 같은 상품·옵션의 option → color_chip → color_compare 순으로 선택하고 image.kind를 반환한다. HTTPS 자료만 사용하며 발색/비교 이미지를 실제 제품 사진으로 부르지 않는다. 미연결이면 해당 옵션 이미지 없음을 표시하고 상품 대표 이미지를 정확 옵션 이미지로 대체하지 않는다. 이미지 선택 순서는 의미가 구체적인 자료를 우선하는 구현 결정이며 새 자료 유형 도입 시 재검토한다.

AR용 arShadeId는 기존 raw-to-serving 보수적 해석 함수를 재사용해 별도로 확인한다(옵션 식별자/고유 코드·이름·색상 근거 일치). 경로에 전달된 임의 shade를 판매 옵션의 AR 색으로 사용하지 않는다. 연결이 없으면 상세 판매 옵션 확인/담기는 가능하되 AR 버튼은 제공하지 않는다. 판매 옵션 화면에서 shadePicker로 다른 옵션처럼 바꾸거나 기존 비교 저장소에 옵션을 누락해서 담지 않는다. AR 렌더러·색상 생성·기억/실행 권한은 변경하지 않는다.

장바구니 key는 optionId가 있으면 productId+optionId, 없으면 기존 productId+shadeId다. 동일 옵션은 수량 합산하고 서로 다른 옵션은 분리한다. version 1 저장소에 선택 필드만 추가하므로 기존 항목을 추측해 변환하지 않는다. 서버 가격/이미지 응답은 장바구니에 영구 저장하지 않고 ID로 재조회한다. 최대 수량 20은 기존 정책 그대로다.

판매 옵션 항목이 하나라도 있는 혼합 장바구니는 주문 버튼과 checkout 직접 진입/주문 생성 핸들러에서 제한한다. 기존 진행 중 결제 확인·완료 경로는 유지한다. 옵션을 제외하면 기존 구매 흐름을 사용할 수 있다. 옵션 계약이 없는 비교·장바구니 추천은 판매 옵션 장바구니에서 제한한다. 주문 API/DB를 옵션 결제 지원 상태로 바꾼 것이 아니며 서버 가격 확정·옵션 주문 라인 지원은 별도 후속 범위다.

조회 설정: 서버 no-store, 앱 staleTime=0·retry=false. 옵션 상태를 오래된 성공으로 확정하거나 실패 시 자동 반복하지 않기 위한 구현값이며 기존 공용 API timeout/cache 저장 기간은 유지한다. ID 길이 128은 기존 옵션 검색 입력 계약을 재사용한다. 실제 조회 지연·실패율을 보고 재검토한다. 이번에는 새로운 모델 호출/병렬 수/후보 상한 정책을 만들지 않았다.

**검증 범위.** 실제 Catalog 3옵션과 소속 오류/미존재 2건, 실제 웹 옵션 상세→장바구니 저장·재로드·상세 재진입을 확인했다. 상담 카드는 과거 실제 응답의 재생이며 모델 호출 0회. 옵션 결제 차단/기존 구매·AR 회귀는 모의 검사도 별도로 수행했다. Expo Go 실기기와 이번 변경을 통과하는 실제 로그인 상담 종단은 미실행이다. Aside PNG 캡처는 실패했으며 DOM 증빙만 보존했다.

## 저장과 후속 대화

로그인 상담의 소유권·요청 버전·중복·동의·최종 저장은 `ConversationService`가 맡는다. 최종 상담에 필요한 후보/옵션/목표와 사용자가 본 결과만 허용된 필드로 저장한다. 기존 v1 대화와 이전 앱 응답의 선택 필드를 읽을 수 있어야 한다. G7 checkpoint에는 요청 ID와 실행 상태만 보관한다. 게스트 단기 문맥은 기존 소유권·TTL 검사를 거친다. 게스트의 로그인 이전과 다른 상담방 자동 참조는 제공 범위에 없다. 실행 중 교체·취소·프로세스 재시작 후 미완료 계획 재개, 동의 철회 후 늦은 결과 차단의 완전한 경험은 ⑤에서 검증한다. 기존 명시적 기억 요청의 답변 덮어쓰기도 ⑤에서 다룬다.

## 실행 방법과 현재 구현 범위

로컬 챗봇의 `G8_ENABLED=true`로 일반 `POST /api/chat`의 한국어 피부 복합 경로를 켠다. 기본값은 false이며 이번 작업에서 배포 설정을 변경하지 않았다. G7 로그인 검증에는 기존 로컬 영속 설정 및 DB가 필요하다. 실제 지식 작성에는 G5의 기존 검색·모델 설정과 허용된 원문 전송 범위가 필요하다. 앱 SDK는 58.0.20이다.

위 제안을 사용자 승인 후 구현했다. 영상 상품의 zone/category에서 서로 다른 표준 부위가 둘 이상 나오면 unknown을 유지한다. 해당 메타데이터에 부위가 없을 때만 상품명을 확인하며, 상품명 자체가 복수 부위여도 같은 처리를 적용한다. 같은 부위의 여러 별칭은 하나로 계산한다. 모호함을 Catalog 기본 부위나 특정 영상 예외로 덮어쓰지 않는다. 일반 발화·단계 선택의 기존 source_zone 동작은 유지한다.

정확한 상품/호수의 catalog_valid와 mapping_status=verified는 유지하되 영상 사용 부위와 AR 적합성을 별도로 판단한다. 복수 부위 상품은 ar_eligible=false이며 N02의 정확한 단계 충족/추천 근거로 채택하지 않는다. 기존 coverage의 evidence_missing으로 남기고 다른 유효한 상품 결과는 보존한다. 공개 스키마·운영 제한값·레지스트리는 변경하지 않았다.

합성 검수 영상의 모의 Catalog→N02 검증과 실제 Catalog 메타데이터→현재 부위 해석 함수 검증을 구분한다. 실제 검수 레시피 등록 및 정상 서비스→G7→앱의 실제 룩 양성 검증은 아직 완료되지 않았다.

### 검수 단계별 상품 사용 연결 — 2026-11-26

사용자 승인 후 API ConsultationRecipe와 챗봇 ReviewedRecipe에 선택적 productUsages를 추가했다. 각 항목은 stepOrder/productId/shadeId/evidenceId/source이며 해당 단계의 zone을 참조한다. 존재하지 않는 단계, 중복 단계·상품·호수, 빈 근거는 스키마에서 거부한다. API는 무효 레시피를 서빙하지 않는다. 기존 레시피는 필드가 없어도 동작하며 빈 목록은 응답에서 생략한다.

Style은 검수 레시피의 해당 상품·호수 연결만 선택한다. 정확한 Catalog 상품·호수 존재 및 기존 mappingVerified가 확인되어야 사용 근거를 RecipeProduct.productUsages에 담는다. 기존 복수 부위 후보에 포함된 단일 부위는 이 근거로 해소할 수 있다. 원본의 명확한 부위와 충돌하거나 같은 옵션이 여러 부위에 연결되면 unknown을 유지한다. 동일 상품의 다른 호수 연결은 현재 호수의 근거로 사용하지 않는다. 아직 단일 RecipeProduct.zone 구조이므로 실제 다중 부위 사용을 한 부위로 임의 축약하지 않는다.

기존 영상 예외는 명시적인 검수 연결을 덮어쓰지 않는다. Catalog에 없는 옵션·상품이나 미검수 연결은 확정되지 않으며, 근거만으로 AR 색/제형 검사나 효능·대체 적합성 검사를 우회하지 않는다. 반환 근거는 응답 직렬화에 보존하고 레시피 전체 digest가 변경되므로 근거 변경도 후속 버전 갱신에 반영된다. 실제 PG 저장·앱 시각화 검증과는 구분한다.

새 제한: API/챗봇 스키마의 productUsages 최대 100, 상품/호수 ID 최대 128자. 100은 기존 단계 상한에 맞춘 임시 입력 크기 방어값이며 단계마다 한 상품이라는 정책은 아니다. 초과 입력은 잘라내지 않고 검증 오류로 거부한다(API 레지스트리에서는 해당 레시피 제외). 실제 검수 데이터의 연결 개수·응답 크기·지연을 확인한 뒤 조정한다. 실제 데이터 등록이나 사람 검수 완료 여부는 변경하지 않았다.

### N02에서 Catalog 부위 누락과 검수 사용 근거 구분 — 2026-11-27

사용자 승인 후 최종 추천 판정을 보완했다. Catalog makeupZone이 NULL이어도 검수 레시피의 해당 상품/호수에 연결된 productUsages가 유효한 단계·동일 부위·개별 근거/출처를 모두 충족하면 추천 후보로 유지한다. 명시된 Catalog 부위와 충돌하면 이 예외를 적용하지 않는다. 정확한 호수의 재조회 존재와 기존 가격/성분 판정은 계속 요구한다. AR 가능 여부는 기존 색상·제형·부위 판정 그대로다.

판매 optionId와 AR shadeId 분리는 별도 후속 과업이다. 이번 보완은 색상 없는 판매 옵션을 새로 조회하거나 shade 목록에 추가하지 않는다. 현재 실제 검증 기준 DB는 vishue-postgres-0033/vishue_db이며 현재 작업 소스의 직접 읽기 전용 조회로 확인했다. 오래된 8082 PR233 API의 결과를 현재 전체 데이터 상태로 사용하지 않는다. 실제 검수 레시피 등록 및 N02→G7→앱 양성은 미완료다.

## N01 미식별 지식 조건의 조회 분리 — 2026-11-27 구현 결정

사용자가 명시한 필수/제외 조건은 유지한다. Catalog가 INGREDIENT_CONFIRMATION을 반환하고 미식별 조건 전부가 사용자 필수 조건이 아닌 지식 제안일 때만 해당 제안을 보류하고 같은 상품·판매 옵션·예산으로 다시 조회한다. 사용자 조건도 미식별이면 완화하지 않는다. 지식 제안 충족으로 표시하지 않고 답변에 미적용 조건과 미확인 범위를 남긴다.

KnowledgeSearchState.deferredIngredients에 보류 출처를 별도 보존하고 입력 지문에 포함한다. 예산만 바꾸는 후속에서는 보류를 유지하며, 목표 변경·지식 재평가·해제 시 초기화한다. BatchCoverage.attempt 및 deferredKnowledgeConditions에는 최초/재조회와 실제 입력·응답 범위를 기록한다.

한도: compound_consultation_service.verify에서 정확한 옵션 배치당 추가 읽기 최대 1회, 기존 전체 deadline 안에서만 수행한다. 기존 정책이 아닌 이번 임시 구현값이다. 무제한 재시도를 막고 가능한 조회를 보존하기 위한 값이며, 후속 배치는 보류된 조건을 처음부터 제외한다. 한도/시간 초과 시 UNKNOWN·부분 결과를 유지한다. 실제 재조회 성공률·지연·Catalog 요청량을 측정해 조정한다. 상품 추천 성공과 조건 미확인을 분리하며 실제 미확인 데이터를 테스트 통과 목적으로 충족 처리하지 않는다.
