# G8 복합 상담 구현 계약

## 현재 보완 계약: 부모 후속과 판매 옵션 기억 — 2026-11-27

사용자 승인 범위: 부모 후속 분기·설명 철회 및 판매 옵션의 상담/보유 기억 연결. 기존 구현을 유지하며 다음 계약을 추가한다. 아래는 이번 **구현 결정**이며 범용 재계획·취소/실행 재개 완료를 뜻하지 않는다.

- 부모의 설명 전용 Style 분기는 현재 선택 룩과 저장된 부모 룩이 일치하고, 이전 작업이 owned_look/style인 경우에만 허용한다. skin 부모의 “상품은 됐고 사용 순서만”은 기존 N01 계획 경로에서 처리한다. 실제 부모·전문 그래프와 모의 계획 모델로 목표 유지 및 상품 Tool 무호출을 검증한다.
- N02의 추가 지식 작업은 긍정적 설명 요청에만 배정한다. 설명/원인/주의점/원리를 빼거나 필요 없다고 하는 명시적 철회 절은 제외한다. 다른 절의 설명 요청은 유지한다. 전체 설명 철회 시 이전 knowledge 작업은 superseded로 둔다. 현재 제한된 한국어 구문 처리이며 임의 언어의 완전한 의도 해석이라고 주장하지 않는다.
- 판매 식별자는 (productId, optionId), AR 식별자는 별도 shadeId다. 카드·룩 결과 → 상세 → 상담 URL/entry/screenContext → 서버 StoredProductContext.selectedOptionId → 후속 복원으로 전달한다. 동일 상품 상담방을 재사용하되 다른 옵션 진입은 선택 revision을 갱신한다. 일반 상품/색상 선택 또는 선택 해제는 이전 optionId를 제거한다.
- 클라이언트 optionId는 신뢰하지 않는다. 기존 Catalog GET /api/products/{productId}/options/{optionId}의 현재 응답으로 상품 소속과 식별자 일치를 확인한다. 없는 옵션은 404/409로 거부하고 조회 실패는 가용성 오류로 처리한다. 기억을 위한 옵션 이름·소속·선택적 AR 연결만 사용하며 클라이언트 가격/이미지를 기억의 사실로 저장하지 않는다.
- 상품 상담에서는 **선택 옵션을 명시적으로 기억해 달라고 요청했을 때만** 검증된 inventory.product 제안을 발급한다. “이 옵션을 가지고 있다고 기억해줘”는 현재 서버 선택에 결속한다. 명시 승인 전 저장하지 않으며, 다른 기억 종류·과거 발화 추론으로 범위를 확대하지 않는다. 일반 상품 상담의 자동 기억 적용이나 AR 실행 권한은 추가하지 않는다. 기존 일반 상담에서 검증 옵션을 선택한 경우도 동일한 제안 어댑터를 사용한다.
- 옵션 기억끼리는 productId+optionId로 동일성을 판단한다. 같은 상품의 두 옵션, 옵션 기억과 legacy 상품/색상 기억을 자동 병합하지 않는다. N02 보유 작업은 현재 옵션을 재조회한 뒤 사용한다. 과거 AR 색상이 삭제되어도 판매 옵션이 존재하면 보유 사실을 유지하고 AR shade는 현재 유효한 경우만 남긴다. 옵션이 삭제되거나 조회되지 않으면 미확인으로 유지한다.
- G7의 일반 beauty 후보 필터는 아직 옵션별 소비 계약이 없으므로 검증 옵션 입력이 없는 곳에서 옵션 기억을 상품 전체로 확대 적용하지 않는다. 현재 이번 연결의 실제 소비 검증은 N02다. 향후 일반 상품 추천에서도 옵션별 소유/제외를 쓰려면 별도 작업으로 정확한 옵션 필터 계약을 연결한다.
- 저장은 기존 G7 JSON 맥락·구조화 기억 테이블을 사용한다. 새 DB 스키마·운영 제한값은 없다. 보유 옵션 재조회는 기존 서버 기억 상한 20 및 기존 부모 요청 시간 예산 안에서 수행한다. 판매 옵션 가격·이미지와 AR 색상 계약, 옵션 결제 제한은 유지한다.

검증: 실제 Catalog/격리 PostgreSQL에서 삐아 A000000162667-012 및 -001의 정상 제안·승인·복원·N02 입력 분리를 확인했다. 두 옵션 모두 AR shade 없음. 모델은 FakeLlm 모의이며 실제 외부 호출 0회다. 브라우저/Expo Go, 전체 E01/B01 및 N02 완료 여부는 WORKLOG의 개별 상태를 따른다.

## 2026-11-27 사용자 결정 반영: 일반 상담·판매 옵션·AR 분리

**사용자 확정.** 기존 데이터를 이용한 상담·추천에 영상별 사람 검수 레시피를 필수 조건으로 강제하지 않는다. 아래 기준은 과거 기록의 검수 레시피 필수 조건보다 우선한다. 영상에서 실제 사용한 순서·방법을 단정하는 것과 일반적인 메이크업 가이드는 구분한다.

**구현 결정.** API 영상 상품에 catalogOptionId/catalogOptionSource를 추가하고 catalogShadeId는 별도로 유지한다. 원본 판매 옵션의 상품 소속과 삭제 여부를 확인한다. 명시 optionScope는 (productId, nullable shadeId, optionId) 전체로 처리하여 색상 없는 여러 판매 옵션을 합치지 않는다. 옵션 이름은 OptionCandidate.optionName으로 반환한다. 판매 옵션 확인만으로 전성분 근거를 승인하지 않으며, 성분 조회 실패·미검수·생산 환경의 합성 근거는 UNKNOWN으로 남긴다.

N02는 consultationZone(상담용 분류)과 zone(기존 사용/AR 판단)을 구분한다. 검수된 recipe가 없어도 확인된 옵션의 보유 대조·미보유 후보 조회가 가능하다. 판매 옵션 경로는 조건이 없어도 실제 옵션 조회를 다시 수행한다. 새로운 판매 옵션은 이름으로 추측하지 않고 API가 확인한 식별자만 사용한다. G7 inventory.product의 선택적 optionId는 productId와 함께 보존하며 기존 shadeId 전용 기억도 유지한다. 상품명을 변경하면 기존 식별자는 제거한다.

응답 ownedLookOptions와 저장된 displayPayload는 nullable shadeId 및 optionId를 유지한다. 앱 카드에서 판매 옵션 이름을 표시하고 AR 색상이 없으면 상품 상세로 이동하되 shadeId를 만들어 전달하지 않는다. 기존 shadeName 응답 필드는 호환성을 위해 유지하며 판매 옵션 이름을 담을 수 있다. 구매 화면의 실제 옵션 자동 선택 기능을 새로 구현한 것으로 보지 않는다.

기존 조회당 6개 상품·42개 작업 한도, 저장/동의 정책, AR 렌더러·실행 권한은 유지한다. 새 운영 제한값은 없다. 상세 실행 증거와 미실행 범위는 WORKLOG의 최신 항목을 따른다.

## 판매 옵션의 상세·장바구니 계약 — 2026-11-27

**사용자 확정.** 판매 optionId를 상품 상세와 장바구니까지 보존한다. 이번 범위에서 옵션 결제는 제한하고 기존 상품·shade 구매 경로는 유지한다. PR 생성은 미승인이다.

**구현 결정.** N01/N02 카드 → productHref의 optionId → GET /api/products/{productId}/options/{optionId} → CartItem.optionId로 연결한다. 서버는 raw 옵션의 상품 소속과 상품/옵션 delisted_at을 재확인한다. 잘못된 소속/미존재 옵션은 404이며 다른 옵션이나 상품 대표 값으로 대체하지 않는다. 옵션이 사라지거나 조회가 실패하면 장바구니 항목 자체는 보존하고 사용 불가로 표시한다. 잘못된 옵션 경로를 일반 상품 구매로 바꾸지 않는다.

가격은 해당 옵션의 최신 기록 priceKRW, 기존 공통 기준값 collected_snapshot, observedAt, sourceUrl을 반환한다. 현재 판매가 보장이 아니다. UI는 참고 가격과 기준일을 표시하며 가격 누락은 '가격 확인 필요'로 표시한다. 시간대가 없는 원본 시각에는 UTC/KST를 임의 부여하지 않는다. 가격 미확인 항목이 있으면 합계를 확정 금액으로 표시하지 않는다.

이미지는 같은 상품·옵션의 option → color_chip → color_compare 순으로 선택하고 image.kind를 반환한다. HTTPS 자료만 사용하며 발색/비교 이미지를 실제 제품 사진으로 부르지 않는다. 미연결이면 해당 옵션 이미지 없음을 표시하고 상품 대표 이미지를 정확 옵션 이미지로 대체하지 않는다. 이미지 선택 순서는 의미가 구체적인 자료를 우선하는 구현 결정이며 새 자료 유형 도입 시 재검토한다.

AR용 arShadeId는 기존 raw-to-serving 보수적 해석 함수를 재사용해 별도로 확인한다(옵션 식별자/고유 코드·이름·색상 근거 일치). 경로에 전달된 임의 shade를 판매 옵션의 AR 색으로 사용하지 않는다. 연결이 없으면 상세 판매 옵션 확인/담기는 가능하되 AR 버튼은 제공하지 않는다. 판매 옵션 화면에서 shadePicker로 다른 옵션처럼 바꾸거나 기존 비교 저장소에 옵션을 누락해서 담지 않는다. AR 렌더러·색상 생성·기억/실행 권한은 변경하지 않는다.

장바구니 key는 optionId가 있으면 productId+optionId, 없으면 기존 productId+shadeId다. 동일 옵션은 수량 합산하고 서로 다른 옵션은 분리한다. version 1 저장소에 선택 필드만 추가하므로 기존 항목을 추측해 변환하지 않는다. 서버 가격/이미지 응답은 장바구니에 영구 저장하지 않고 ID로 재조회한다. 최대 수량 20은 기존 정책 그대로다.

판매 옵션 항목이 하나라도 있는 혼합 장바구니는 주문 버튼과 checkout 직접 진입/주문 생성 핸들러에서 제한한다. 기존 진행 중 결제 확인·완료 경로는 유지한다. 옵션을 제외하면 기존 구매 흐름을 사용할 수 있다. 옵션 계약이 없는 비교·장바구니 추천은 판매 옵션 장바구니에서 제한한다. 주문 API/DB를 옵션 결제 지원 상태로 바꾼 것이 아니며 서버 가격 확정·옵션 주문 라인 지원은 별도 후속 범위다.

조회 설정: 서버 no-store, 앱 staleTime=0·retry=false. 옵션 상태를 오래된 성공으로 확정하거나 실패 시 자동 반복하지 않기 위한 구현값이며 기존 공용 API timeout/cache 저장 기간은 유지한다. ID 길이 128은 기존 옵션 검색 입력 계약을 재사용한다. 실제 조회 지연·실패율을 보고 재검토한다. 이번에는 새로운 모델 호출/병렬 수/후보 상한 정책을 만들지 않았다.

**검증 범위.** 실제 Catalog 3옵션과 소속 오류/미존재 2건, 실제 웹 옵션 상세→장바구니 저장·재로드·상세 재진입을 확인했다. 상담 카드는 과거 실제 응답의 재생이며 모델 호출 0회. 옵션 결제 차단/기존 구매·AR 회귀는 모의 검사도 별도로 수행했다. Expo Go 실기기와 이번 변경을 통과하는 실제 로그인 상담 종단은 미실행이다. Aside PNG 캡처는 실패했으며 DOM 증빙만 보존했다.

## 사용자 경험과 책임

**기존 확정.** C01~C14, S01~S12, 한국어 우선, 현재 대화와 동의한 기억, 일반 LLM과 AR 소유권을 유지한다. 사용자는 관리법과 조건부 상품 추천을 한 번에 요청하고 후속 메시지에서 조건을 바꿀 수 있다. 사람의 명시적 변경은 이전 조건에 우선한다. 지식은 일반적인 관리 설명을 뒷받침하고 특정 상품의 가격·성분 사실은 해당 판매 옵션의 조회 근거가 뒷받침한다. AIHub에 대한 기존 사용 결정을 따른다.

## 실행 방법과 현재 구현 범위

로컬 챗봇의 `G8_ENABLED=true`로 일반 `POST /api/chat`의 한국어 피부 복합 경로를 켠다. 기본값은 false이며 이번 작업에서 배포 설정을 변경하지 않았다. G7 로그인 검증에는 기존 로컬 영속 설정 및 DB가 필요하다. 실제 지식 작성에는 G5의 기존 검색·모델 설정과 허용된 원문 전송 범위가 필요하다. 앱 SDK는 58.0.20이다.

비영속 한국어 후속 요청에서 클라이언트의 recentMessages를 사용할 때는 기존 입력 계약상 G1_SUPERVISOR_ENABLED=true도 필요하다. G1 OFF에서는 이 클라이언트 입력이 제거된다. G7 영속 경로는 인증·소유권·버전 확인 후 서버가 PG 대화에서 history를 복원하므로 이 클라이언트 입력 전제를 일반화하지 않는다. 원래 N01의 영속 질문→답변 복원은 G1 ON/OFF 모두 실제 PG와 대역 모델·Catalog로 검증했다. 이는 실제 모델의 의미 판단이나 운영 배포 설정 검증을 뜻하지 않는다.

부모는 `plan → execute → assess → finish`로 진행한다. 같은 세대에 속한 준비된 작업을 동시에 실행하고, 검증 작업은 추천 작업의 후보를 복사해 호출한다. 빈 후보는 옵션 API를 생략하고 일시적 추천 읽기 실패는 남은 예산 안에서만 재시도한다. 입력 참조의 작업 ID·계획 ID·세대가 다르면 거부한다. 이 버전은 완료된 턴에서 조건을 바꿔 새 계획을 시작할 수 있다. 실행 중 다른 턴을 병합하거나 임의의 전문 에이전트가 새 실행을 제출하는 기능은 ⑤ 과제다.

개발 중 G7 체크포인터가 중첩 그래프에 자동 상속되는 것을 실제 DB에서 확인했다. G8 하위 그래프는 `compile(checkpointer=False)`를 명시한다. 최종 결과의 G7 저장과 루트 실행 영수증만 소유권·버전 검사 후 남긴다.

**2026-11-26 사용자 요청과 표시 결정.** 상담은 근거로 뒷받침되는 관리법부터 안내한다. 일반 설명 앞에 ‘검증된 관리 원칙’이라는 수식어를 붙이지 않는다. 본문의 번호와 ‘참고한 자료’를 연결한다. 추천 카드에는 선택한 옵션과 해당 옵션의 금액을 표시한다. 가격을 확인한 시점은 카드의 ‘가격 정보’에 둔다. 예산 판정에는 조회 당시 해당 판매 옵션에 기록된 금액을 사용한다. 상품 상세의 대표 가격을 카드를 채우는 데 쓰거나 실시간 결제 가격을 보장하지 않는다. 실제 판매 가격과 카탈로그 옵션 가격을 동기화하는 정책은 이번 표시 변경 범위 밖이다.

다른 룩 선택·선택 해제·레시피 버전 변경 시 이전 선언을 무효화한다. 비 N02 답변·기억 사용 거부는 N02 상태를 최종 맥락에서 제거한다. 같은 룩의 일시 조회 실패에는 유효한 선언을 보존하며 해제 요청도 적용한다. 질문·타인의 보유·인용·실제 AR/기억/장바구니 요청은 선언으로 처리하지 않는다. 지원 표현은 명시적 한국어 있다/없다·조건 해제/취소 및 짧은 재추천이다. 임의의 모든 의역·구매 완료 표현을 이해한다고 주장하지 않는다. 모델 호출을 추가하지 않는다. 보유 기억의 후속 선택은 N02 진입 조건을 만족하는 요청으로 한정해 무관한 질문에 보유품을 넣지 않는다.

운영값: 부위는 기존 Zone 9개로 닫혀 있어 선언 map이 자연히 최대 9개다. 구절 상한 500자는 owned_look_context.py의 입력 검증값이며 G8 근거 구절 상한과 맞췄다. 초과 입력은 절단하지 않고 스키마에서 거부한다(현재 명시 구문에서 실제 생성 구절은 훨씬 짧음). 추가 후보·시간·캐시·보관 한도는 도입하지 않았으며 G7 대화 보관 정책을 따른다. 레시피 버전 변경 시 재확인이 필요한지는 실제 사용성 검토 후 조정할 수 있으나 현재는 이전 룩 조건 오용 방지를 우선한다.

### N02 예산·성분 및 대체 적합성 계약 — 2026-11-26

구현 결정: ownedLook.filters에 사용자 출처의 예산, 성분 포함/제외, 무향료 및 가격 기준을 저장한다. 같은 룩의 후속 턴에서 예산만 변경하면 성분 조건은 유지하며, 개별 성분 또는 전체 상품 조건을 명시적으로 해제할 수 있다. 레시피 개정 시 보유 선언은 재평가하지만 같은 룩에 대한 명시적 구매 조건은 유지한다. 다른 룩 선택/선택 해제의 기존 상태 무효화 경계를 유지한다. 과거 저장값의 filters 누락은 빈 조건으로 복원한다. 공개 ChatResponse나 DB migration은 추가하지 않는다.

P1 상품 조회 → V1 판매 옵션 조회 → R1 응답 순서로 연결한다. V1은 6개씩 배치하고 실제 effectiveRequest가 요청과 같은지 확인한다. 가격·성분 조건은 추가 추천에 적용한다. 보유품 자체의 성분 적합성을 검증했다고 표현하지 않는다. 검수 레시피의 정확한 productId와 shadeId에 일치하는 ELIGIBLE 옵션만 추천하며, 다른 호수·UNKNOWN·제외·조회 실패를 조건 충족으로 바꾸지 않는다. 전체 옵션 응답의 근거·checkedScope·제한을 작업 결과에 보존한다. 조건이 없으면 불필요한 V1 조회는 생략한다. 표시 가격은 실시간 현재가로 주장하지 않는다.

명시적인 예산 및 성분 이름의 포함/제외를 지원하는 결정적 파서다. 질문·인용·부정·지원하지 않는 가격 범위/질감 등은 추측하지 않고 unsupported로 남긴다. 남은 unsupported는 명시적 전체 상품 조건 해제로 해제한다. 별칭 정규화 후 실제 전송 목록에 Catalog의 최대 6개 조건 제한을 적용하고 초과 시 조회를 강행하지 않는다. 성분 이름 120자 및 예산 최대 1억 원의 기존 파싱/API 경계를 적용한다. 새 반복·캐시·모델 호출 제한은 추가하지 않는다.

대체품 적합성: 검수 레시피의 정확한 상품·호수 일치만 exact_match와 근거 ID를 갖는다. 같은 부위의 다른 보유품은 alternativeProductIds를 보존하되 substitutionStatus=unverified로 표시한다. 부위가 같다는 이유로 대체 가능하거나 반드시 추가 구매해야 한다고 결론내리지 않는다. 다른 제품의 색·제형·사용법 적합성을 확정하려면 해당 검수 근거가 필요하며, 현재 데이터에 없는 근거를 모델로 생성하지 않는다. 일반 대체품 양성 적합성 구현·실제 검증은 미완료다.

검증 구분: 합성 검수 룩에서는 조건 전달·유지·해제·6+2 배치·다른 호수 차단·부분 실패를 검증한다. 실제 Catalog의 가격 양성과 성분 UNKNOWN은 별도로 기록한다. 실제 검수 레시피가 없어 실제 룩→조건 충족 상품 카드의 종단 양성은 BLOCKED이며, 직접 옵션 조회 성공으로 대체하지 않는다.


### N02 조건 순서·가격 기준·공개 옵션 표시 — 2026-11-26 후속 보완

보유 제품 식별과 룩 대체 적합성의 미확인 사유를 구분한다. 상품·호수를 확인한 다른 보유품에는 대체 적합성이 미확인이라고 설명하고, 이름만 알고 정확한 상품·호수를 모르는 선언과 같은 문구를 쓰지 않는다.

## 공통 부모 A–E 첫 연결 — 2026-11-26

사용자 승인 범위는 기존 N01·N02를 유지한 공통 부모 계약·연결·후속 질문·검증이다. 아래는 구현 결정이며 자유로운 전체 목표 계획기나 G8 완료 선언이 아니다. 전체 단계는 ⑤ 협력 완성이다.

- E: 모의 검수 룩의 결과 변경 → 모의 G5 경계의 호출 인자 변경, 지식 실패 → 상품 보존, 실제 PG의 질문 저장 → 짧은 답 복원 → 상품 추천 중단을 검증한다. 실제 G5/모델 연결 검증과 구분하며 기존 공개 답변·레시피·옵션 카드 계약을 그대로 사용한다.
