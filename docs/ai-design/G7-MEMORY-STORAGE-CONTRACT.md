# G7 3-2 기억 저장·호환 계약 검토안

2026-11-25 · 3-1 원문 보존·15분 만료 검증 이후 검토 · DDL 및 배포 승인 대기

G7의 기존 상위 정책 20개와 상세 정책 25개를 적용한다. S-20 A에 따라 기존 승인 기억은 원문형으로 보존한다. S-08 A에 따라 제안은 발급 후 15분 동안 유효하다. 기존 72개 작업과 73개 평가 후보, 미결정 수치는 기존 원장에 따른다. 이번 단계의 산출물은 저장·호환 계약 검토안이며 기존 DB, 코드, Checkpoint는 현재 상태로 유지했다.

## 2. 단일 정본과 저장 필드

기존 챗봇 PostgreSQL의 `chat_memories`에 저장 형식 구분자 `schema_version`을 두는 안을 권고한다. 기존 행과 구형 쓰기에는 상수 기본값 `1`을 적용한다. 검증된 새 형식의 쓰기 경로만 `2`를 명시한다. 저장 형식, 레지스트리 버전, 개별 기억의 CAS 버전은 각각 다른 책임을 가진다.

| 필드 | 원문형 `1` | 구조화형 `2` |
|---|---|---|
| `id`, `owner_id`, `version`, `kind` | 기존 값 유지. 같은 동의 범위의 직접 정정은 기존 버전 비교 방식을 쓴다. | 항목별 ID·소유자·버전. 서버 레지스트리가 의미 키와 허용 `kind`를 대조한다. |
| `registry_version`, `semantic_key` | NULL. 원문을 그대로 읽는다. | 승인된 레지스트리 버전 및 의미 키 필수. 등록된 키와 값 규칙을 서버에서 검증한다. |
| `value_json`, `display_value` | 활성 행의 `{"text": 문자열}`을 그대로 반환한다. 신규 표시 필드는 NULL이다. | 키별로 검증한 JSON 값과 사용자에게 보여주고 승인받은 문구를 저장한다. |
| `strength`, `persistence`, `applicability_json`, `valid_from`, `valid_until` | 신규 필드는 NULL. 기존 동의 범위와 저장 상태를 따른다. | 선호·제약 등의 승인된 강도, 적용 상황·지속성, 필요한 경우 UTC 기간을 저장한다. 시작이 있으면 그 시각부터 적용하고 종료 시각부터는 활용에서 제외한다. |
| `consent_scope`, `confirmed_at`, `revoked_at`, 생성·변경 시각 | 기존 동의와 철회 기록 유지. 이미 철회된 행의 값은 비워진 상태로 보존한다. | 항목별 동의 범위와 시각을 커밋할 때 기록한다. 철회 시 값·표시 문구·값을 담는 적용 조건을 같은 트랜잭션에서 제거하고 철회 상태를 기록한다. |
| `memory_key`와 출처 | 기존 `source:…` 키, 유일 인덱스, `source_message_id`와 메시지 삭제 시 링크 해제를 보존한다. | 기존 비NULL 제약을 재사용하는 권고안은 `structured:<memory UUID>`를 내부 키로 쓰고 실제 의미는 `semantic_key`에 둔다. 검증된 출처는 관계 행으로 연결하고 메시지 원문 복제는 방지한다. |

가령 `makeup.color`가 승인되면 값에 립 부위와 코랄 계열을 담고, 앱에는 사용자가 실제로 승인한 문구를 표시한다. 기존에 같은 내용이 원문형으로 승인돼 있어도 그 행의 값과 버전은 그대로 읽을 수 있다. 17개 레지스트리 후보 중 첫 활성 키와 자세한 값 검증 규칙은 제품·Tool 담당 검토 후 결정한다.

### 저장 제약과 동시성

- 1차 확장은 필드 추가 중심으로 구성한다. 기존 행에 값 변환 `UPDATE`를 실행하지 않는다. PostgreSQL 17은 상수 기본값 컬럼을 추가할 때 기존 행별 쓰기를 생략할 수 있다. 제약 검증과 스키마 잠금 비용은 격리 검증에서 따로 측정한다. [PostgreSQL 17 컬럼 변경](https://www.postgresql.org/docs/17/ddl-alter.html#DDL-ALTER-ADDING-A-COLUMN)
- 기존 `kind` 제약은 원문형에서 유지한다. 구조화형을 받는 후속 제약은 활성 행에 필요한 필드와 JSON 타입을 확인하고, 철회 행에는 제거 대상이 SQL NULL인지 검사한다. `CHECK`가 NULL 평가를 허용하므로 필요한 비NULL 조건을 명시한다. 기존 데이터의 실제 형식과 예외를 검사한 뒤 제약을 검증한다. [PostgreSQL 17 제약](https://www.postgresql.org/docs/17/ddl-constraints.html#DDL-CONSTRAINTS-CHECK-CONSTRAINTS)
- 기존 활성 유일 인덱스는 원문형 중복 규칙을 계속 적용한다. 구조화형의 동일성은 의미 키, 검증된 값, 적용 상황·기간과 의미를 바꾸는 조건을 함께 대조한다. 같은 키의 다른 값·상황·기간은 해당 키 정책이 허용하면 함께 저장한다. 레지스트리 버전이 달라도 동일 의미를 새 항목으로 허용할지는 키별 호환 규칙으로 판단한다.
- 구조화형 쓰기는 기존 owner 행 잠금 안에서 최신 값과 대상 버전을 읽고 중복과 단일값 범위 겹침을 재검증한다. 모든 쓰기 경로가 같은 검사를 거친다. 구조화형 인덱스와 DB 유일성의 추가 범위는 키별 동일성 규칙 및 실제 쿼리 검증 후 확정한다. 모델·Tool 실행은 DB 잠금 밖에서 한다. [PostgreSQL 17 행 잠금](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS) · [부분 유일 인덱스](https://www.postgresql.org/docs/17/indexes-partial.html)
- 승인 트랜잭션은 owner 활성 여부, 기억 설정·세대, 본인 발화와 방의 활성 상태, 제안 버전·만료, 정정 대상 버전을 대조한다. 본인과 본인 방의 사용자 발화만 출처로 연결한다. 방 삭제 후 이미 승인한 기억은 조회할 수 있고 연결된 출처는 해제한다. 미확정 제안은 방·원천이 사라지면 승인할 수 없다.
- 제안과 승인 기억은 각각의 수명을 가진다. 제안의 발급·만료는 같은 UTC 시각을 기준으로 15분 차이이며, 조회·편집·보류는 만료 시각을 유지한다. 만료 시각부터 새 승인을 차단한다. 이미 커밋된 같은 요청의 재시도는 결과 참조를 반환할 수 있으며 철회된 내용은 반환 대상에서 제외한다.

## 3. 구버전 앱과 공존

| 경로 | 계약 검토안 |
|---|---|
| 기존 기억 API 목록 | v1 본인 원문형 목록의 문자열 `value`와 응답 형태를 유지한다. v2 목록은 본인 원문형·구조화형을 저장 형식으로 구분해 제공한다. 각 형식의 전체 관리 경로를 신규 앱에서 제공한 뒤 구조화형 쓰기를 활성화한다. |
| 기존 기억 직접 정정·철회 | v1의 대상 조회와 갱신을 원문형으로 제한한다. 소유권·활성 상태·버전·멱등성을 검사한다. v2는 두 형식의 관리를 지원하며 원문형의 새 의미 키 저장·동의 범위 확대는 새 제안과 승인으로 처리한다. |
| 기존 앱 신규 기억 저장 | 호환 배포에서 기존 제안 흐름을 계속 지원한다. 구조화 전환 시 새 원문 제안 발급을 먼저 멈추고 남은 제안에 원래 만료를 적용한다. 전환 뒤 새 저장은 신규 계약에서 받으며, 구버전에선 필요한 경우 업데이트 안내를 반환한다. 이미 성공한 요청의 재시도는 기존 결과 참조 규칙을 유지한다. |
| 영속 상담 | 현재 원문 조회는 원문형만 전달하도록 정본 조회에서 범위를 명시한다. 구조화형을 자동 개인화·Tool에 제공하려면 4단계에서 각 필드의 근거와 적용 검증을 먼저 완료한다. 설정 OFF 동안 두 형식 모두 자동 추출·검색·개인화·새 저장에서 제외하고 본인 직접 관리를 제공한다. |
| 형식 불일치·삭제 | 알 수 없는 버전·손상된 값을 활성 기억으로 쓰거나 모델에 전달하는 요청은 차단한다. 다른 계정의 기억이나 제안에 대해 내용을 노출하지 않는다. 개별 철회·전체 기억 삭제·탈퇴는 두 저장 형식과 신규 관계·파생 자료의 범위를 대조하고 필요한 정리 완료 이후 확인한다. |

## 4. 적용과 복구 순서

1. 보존 대상 환경마다 읽기 전용으로 형식·동의 범위·버전·철회·출처 집계를 기록한다. 원문 동일성은 제한된 권한에서 테스트 값과 검사 결과로 확인하며 개인정보를 보고서나 로그에 복제하지 않는다.
2. 실제 배포에 쓸 Alembic 계보와 스키마 제약을 대조한다. 일회용 PostgreSQL에서 기준선 빈 설치와 기존 행이 있는 업그레이드를 검증한다. 초기 확장 동안 구조화형 쓰기를 차단한 상태로 호환 코드를 배포한다.
3. 원문 목록·관리·상담 조회·탈퇴가 새 형식을 안전하게 다루는 버전을 모든 해당 실행 경로에 배포한다. 구조화형 관리, 동의, 권한 및 철회/삭제가 함께 검증되고 레지스트리 첫 범위가 승인되면 신규 쓰기를 활성화한다.
4. 장애 시 신규 쓰기와 개인화를 차단한 뒤 두 형식을 인식하는 호환 코드에서 읽기·관리 기능을 복구한다. 이미 구조화형이 저장된 환경에서는 행을 삭제하는 스키마 다운그레이드와 구형 서버의 재활성화를 차단한다. 최신 OFF, 철회·탈퇴 표식, 버전·멱등 기록을 보존한 상태로만 전환한다.
