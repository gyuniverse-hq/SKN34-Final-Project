# AR 추천 ML 모델 및 MLOps 설계서 v1.3

2026-11-23 · 대상 기능은 직접 탐색의 립·블러셔 첫 팔레트 ✨ 추천

**v1.3 결정.** 기본 학습 작업은 `CatBoostRanker(PairLogit)` 후보를 만든다. RandomSearch로 설정 16개를 비교하고 검증 구간의 장바구니 NDCG@3로 고른다. 첫 A/B의 A는 기존 룰, B는 오프라인 기준을 통과한 모델 번들이다. 운영 승격은 추천 세션 대비 구매율로 판정한다.

**v1.2 분류기 학습.** 관찰이 마감된 30일을 첫 학습 기준으로 하고 시간순 70:15:15로 분할한다. 분류기는 `Balanced` 클래스 가중치를 사용한다. 그리드·랜덤·Optuna TPE 비교와 승격 모델의 탐색 방식 재사용은 `--model-type classifier`에서 지원한다.

**v1.1 결정.** 첫 모델은 장바구니 담기를 예측한다. 추천의 사업 성과는 담긴 색이 얼마나 구매로 이어졌는지, 같은 수의 추천을 보여 줬을 때 실제 구매가 늘었는지로 함께 평가한다. 구매 지표의 집계 기준과 필요한 주문 기록은 5.1절에 정의한다.

**추천 점수는 현재 회원이 같은 AR 세션에서 장바구니에 담을 색을 먼저 보여주기 위해 사용한다.** 동의한 구독 회원에게 공통 CatBoost 모델 하나를 제공한다. 같은 색이라도 회원의 과거 활동에 따라 점수가 달라진다. 얼굴 이미지나 피부 분석 결과는 입력에 쓰지 않는다.

## 1. 서비스 범위와 현재 상태

| 구분 | 동작 |
|---|---|
| 현재 운영 기준선 | 첫 방문에는 리뷰 수로 보정한 제품 평점을 사용한다. 같은 부위의 최근 90일 시착·담기 기록이 있으면 색과 제형 선호를 함께 반영한다. 팔레트 필터에 맞는 서로 다른 제품에서 최대 3개 색상을 보여 준다. |
| 현재 수집 | 최신 약관과 AR 수집 동의가 확인된 회원의 직접 시착·담기를 구독 여부와 관계없이 기록한다. 첫 추천 요청·후보·노출은 추천 권한이 있는 회원에게 기록한다. 현재 동의·추천 자격은 서버의 별도 회원 목록으로 관리한다. |
| 모델 적용 범위 | 첫 팔레트의 적격 후보를 CatBoost로 점수화한다. 화면, 최대 칩 수, 제품 중복 제거, 색 계열 다양성 및 후보 자격 조건은 두 방식에 동일하게 적용한다. 신규 회원도 같은 모델에 후보 속성과 제품 평가를 입력한다. |
| 별도 기능 | 기준색을 선택한 뒤 쓰는 ‘비슷한 색·차분한 색·선명한 색’ 등은 탐색 의도가 다르다. 해당 추천 결과는 첫 팔레트의 학습 표본 및 성과 집계에서 제외한다. 동의한 회원의 과거 체험은 이후 선호 이력에 활용할 수 있다. |

로컬 파이프라인에서 기존 서비스 테이블로 담기 학습 데이터를 생성하고, 결제가 확인된 추천 세션의 전환율을 A/B로 집계할 수 있다. 운영 실험은 기준 추천 방식, 후보 번들, 실험 기간을 지정한 뒤 시작한다. [현재 동작 명세](AR_SPEC.md#6-14-행동-이벤트-기록-f15) · [현재 팔레트 순위 계산](../lib/arPalettePicks.ts)

## 2. 학습 데이터 한 행과 수집 경로

**한 행의 단위는 실제로 노출된 첫 추천 색상칩 1개이며, 행 식별자는 `impression_id`다.** 현재 룰 데이터에서는 `strategy IN ('rating', 'personalized')`인 요청을 사용한다. ML 배포 후에는 버전이 확인되는 첫 팔레트 ML 요청도 포함한다.

| 순서 | 기존 테이블 | 행을 연결하는 방법과 용도 |
|---|---|---|
| 1 | `ar_recommendation_requests` | `request_id`로 추천 1회를 식별한다. 회원, 세션, 부위, 전략, 정책 버전과 요청 기록 시각을 얻는다. |
| 2 | `ar_recommendation_candidates` | `request_id`로 연결해 추천한 제품·호수와 원래 순위 `rank`를 얻는다. |
| 3 | `ar_recommendation_impressions` | `candidate_id`로 연결한다. 칩이 팔레트 안쪽에 500ms 표시되거나 직접 선택된 경우의 노출을 사용한다. 노출되지 않은 후보에는 학습 행을 만들지 않는다. |
| 4 | `ar_activity_events` | 같은 회원·세션에서 같은 `impression_id`로 연결된 행동을 찾는다. 연결된 담기가 여러 건이어도 노출 한 행을 유지한다. |

예를 들어 한 요청에서 세 칩이 모두 노출되고 회원이 코랄은 시착만, 로즈는 시착 후 담기, 베리는 보기만 했다면 세 행의 Y는 각각 **0, 1, 0**이다. 일반 팔레트에서 브라운을 따로 담아 `impression_id=NULL`인 경우에는 위 세 칩의 Y가 바뀌지 않는다. [DB 테이블 정의](../backend/api/app/models/ar_personalization.py) · [앱의 노출·담기 연결](../lib/arHistory.ts)

## 3. 입력 X 열 개와 목표 Y 한 개

**원본**은 기존 DB에 저장된 값을 학습 행에 가져오는 컬럼이다. 다른 테이블과 조인하거나 당시 유효한 행을 선택해도 값 자체를 변환하지 않으면 원본으로 분류한다. **파생**은 색 변환, 행동 집계 또는 이벤트 연결로 새로 계산하는 컬럼이다.

| X 컬럼 | 구분 · 자료형 | 출처와 계산 | 선정 이유 |
|---|---|---|---|
| `makeup_zone` | 원본 · 범주 | 요청의 `makeup_zone`. 대상은 `lip`, `blush` | 같은 색을 립과 볼에서 다르게 선택하는 경향을 구분한다. |
| `color_family` | 파생 · 범주 | `shades.hex`에 앱의 `colorFamily()`를 적용해 red, coral, pink, berry, nude, brown 중 하나를 얻는다. | 제품이 처음 등장해도 회원이 기존에 선택한 색 계열과 비교할 수 있다. |
| `lightness` | 파생 · 수치 | `shades.hex`를 D65 기준 CIELAB으로 변환해 명도 L*를 구한다. | 같은 계열 안에서도 밝은 코랄과 어두운 코랄의 차이를 보존한다. |
| `chroma` | 파생 · 수치 | 같은 변환 결과에서 채도 C*를 구한다. | 명도가 비슷해도 차분한 색과 선명한 색의 차이를 표현한다. |
| `texture` | 원본 · 범주 | 후보 제품의 `products.texture` | 색과 별개로 제품 제형에 따라 달라지는 선택을 반영한다. |
| `rating_avg` | 원본 · 수치 | 당시 제품 리뷰 요약의 `raw_oy_review_summary.rating_avg` | 행동 이력이 없는 회원에게도 제품 평가라는 단서가 있다. 평점의 단위는 제품이다. |
| `review_count` | 원본 · 정수 | 같은 리뷰 요약 행의 `review_count` | 같은 평점이라도 리뷰 3건과 300건에서 얻은 평가를 구분한다. |
| `prior_activity_count_90d` | 파생 · 정수 | 추천 직전 90일간 해당 회원·부위의 시착과 담기를 날짜·제품·호수별로 묶은 건수 | 취향을 판단할 이력이 얼마나 있는지 나타낸다. 과거 한 번의 선택과 반복된 선호를 구분한다. |
| `prior_same_family_share_90d` | 파생 · 비율 | 같은 이력 중 후보와 색 계열이 같은 건수 ÷ 색 계열을 확인할 수 있는 이력 건수 | 후보 제품을 쓴 적이 없어도 과거의 색 선호와 맞는 정도를 나타낸다. |
| `prior_same_texture_share_90d` | 파생 · 비율 | 같은 이력 중 후보와 제형이 같은 건수 ÷ 제형을 확인할 수 있는 이력 건수 | 후보와 유사한 제형을 반복해서 선택했는지 나타낸다. |

세 범주형 X는 CatBoost의 `cat_features`로 지정한다. 일자 경계는 한국 시간으로 통일한다. 같은 날 같은 호수를 세 번 시착하고 한 번 담아도 이력에서는 1건이다. 이력이 0이면 활동 건수는 0, 비율은 결측이다. 과거 립 이력 8건 모두 속성을 확인할 수 있고 코랄이 6건, 후보와 같은 제형이 4건이면 코랄 후보의 두 비율은 0.75와 0.50이다. 과거 호수의 색·제형을 복원할 수 없으면 해당 비율의 분모에서만 제외하고, 분모가 0이면 결측으로 둔다. [색 계열 규칙](../lib/colorFamily.ts) · [색공간 변환](../lib/colorDifference.ts) · [카탈로그 컬럼](../backend/api/app/models/catalog.py) · [리뷰 요약 컬럼](../backend/api/app/models/raw_oliveyoung.py)

| Y 컬럼 | 구분 · 자료형 | 계산 | 선정 이유 |
|---|---|---|---|
| `added_to_cart` | 파생 · 이진 0/1 | 같은 회원·세션에서 이 노출에 연결된 `event_type='cart_add'`가 1건 이상이면 1. 관찰이 끝날 때까지 없으면 0. | 서비스 목표인 ‘추천을 통한 담기’를 직접 측정하고 어떤 칩에서 이어졌는지 추적할 수 있다. 시착만 한 경우와 외부 구매는 담기로 집계하지 않는다. |

### 추천 시점과 학습 시점

- **추천 직전에 알 수 있었던 값으로 X를 만든다.** 과거 행동은 당시 서버가 이미 수신한 것만 사용하고, 그 요청에 연결된 시착·담기는 이력에서 제외한다. 리뷰 요약은 대상 제품의 `collected_at`이 추천 시점 이전인 최신 행을 선택한다.
- **과거 입력을 복원할 수 있는 범위를 기록한다.** 기존 `requests.created_at`은 DB에 등록된 시각이라 실제 계산 시각과 차이가 날 수 있다. AR 로그에는 당시의 HEX·제형 스냅샷도 없다. 시점을 확인할 수 없는 행은 평가에서 분리해 건수를 남긴다. 향후 학습·서빙에는 버전이 있는 카탈로그 스냅샷과 추천 계산 시각을 사용한다.
- **진행 중인 세션은 Y 확정을 보류한다.** 추출 시점에 최근까지 활동 중이거나 지연 전송 가능성이 있는 행은 보류하고, 뒤늦게 들어온 담기는 다음 추출에서 같은 노출에 반영한다. 첫 배치의 관찰 마감은 실제 수신 지연 분포와 API의 이벤트 접수 시간 범위를 확인해 정한다.
- **식별자와 표시 위치는 분석용으로 보관한다.** 회원·세션·요청·노출·제품·호수 ID는 연결과 중복 제거에 쓰고, `rank`와 `displayed_position`은 기존 룰의 순위 및 위치별 성과를 볼 때 사용한다. 위 필드들은 X 10개에 포함하지 않는다.

## 4. 첫 학습과 오프라인 비교

1. **시작 조건**은 첫 유효 추천부터 담기 관찰이 마감된 시점까지 30일이다. 기본값은 노출 후 24시간을 관찰하고 수신 대기 24시간을 더한다. 데이터는 관찰이 마감된 이력을 사용하며, 30일 이후 쌓인 유효 데이터도 포함한다.
2. **시간순 분할**은 오래된 추천 요청부터 약 70%를 학습, 다음 15%를 검증, 최근 15%를 최종 평가에 배정한다. 세션이 경계에 걸치면 앞 구간의 해당 세션 행을 제외한다. 각 구간에 담은 칩과 미담김 칩이 함께 노출된 요청이 필요하다. 양성·음성 노출 수, 비교 가능한 요청 수, 고유 회원 수와 부위별 양성 요청 수를 기록한다.
3. **탐색과 학습**은 같은 요청에 노출된 후보를 묶어 `담김 > 미담김` 쌍을 만들고 `CatBoostRanker(PairLogit)`에 전달한다. 같은 칩의 반복 노출은 요청 내 한 후보로 합치고, 한 번이라도 담겼으면 양성으로 본다. RandomSearch는 반복 횟수, 깊이, 학습률, L2 규제의 서로 다른 설정 16개를 비교한다. 담김·미담김이 섞인 검증 요청의 평균 NDCG@3가 가장 높은 설정을 고른다. 동률이면 반복 횟수와 깊이가 작은 설정을 우선한다. 선택한 설정으로 학습과 검증 구간을 합쳐 다시 학습한다.
4. **최종 평가**는 최근 평가셋의 동일한 노출 후보에서 후보 모델과 기준 추천을 비교한다. 최초 기준선은 기록된 룰 순위 `rank`다. 장바구니에 담은 칩이 있는 요청의 NDCG@3와 1위 적중률, 회원 단위 개선 폭의 신뢰구간과 부위별 결과를 보고한다. 사전에 고정한 최소 NDCG@3와 개선 폭을 충족하고 개선 폭의 95% 신뢰구간 하한이 양수면 A/B에 진입할 수 있다. 과거 룰이 보여 준 적 없는 색의 효과는 온라인 실험에서 확인한다.

## 5. 실제 사용자 A/B 테스트와 전환

| 항목 | 설계 |
|---|---|
| 배정 | 수집에 동의한 추천 대상 회원을 실험 ID와 회원 ID로 1:1 확률로 배정하고 실험 기간 동안 고정한다. A는 첫 도입에서 기존 룰 기반 콘텐츠 필터, 이후에는 운영 ML이다. B는 새 후보 ML이다. 양쪽 모두 같은 ✨ UI와 후보 필터를 사용한다. |
| 비교 지표 | 그룹별 전체 추천 세션 → 구매율, 추천 담기 → 구매율, 추천 세션 → 담기율을 함께 집계한다. 전체 세션은 해당 실험의 첫 팔레트 추천 요청이 서버에 기록된 세션이며 룰 대체 응답과 빈 팔레트도 포함한다. |
| 실험 규모 | 기존의 추천 대상 세션 → 구매율, 검출할 최소 개선 폭, 반복 방문, 트래픽을 기준으로 표본과 기간을 정한다. 실험 시작 전에 관찰 기간과 판정 기준을 고정한다. |
| 모델 도입 판정 | 첫 도입과 후속 교체 모두 전체 추천 세션 → 구매율의 개선 폭과 회원 단위 95% 신뢰구간으로 판정한다. 장바구니 → 구매 전환율과 담기율을 함께 보고 어느 단계에서 차이가 생겼는지 확인한다. 추천 실패율·지연과 구매 귀속 누락도 함께 점검한다. 구매 표본이나 개선 근거가 부족하면 현재 추천 방식을 유지한다. |

장바구니 → 구매 전환율의 분모는 그 그룹에서 추천으로 담은 세션이다. 추천 방식이 이 세션의 수와 구성에 영향을 줄 수 있으므로, A/B 보고에는 전체 추천 대상 세션·담기 세션·결제 확인 세션의 건수를 함께 제시한다. 한 세션에서 결제가 여러 번 확인돼도 구매 전환에는 한 세션으로 센다. [Microsoft 실험 지표의 분모 해석](https://www.microsoft.com/en-us/research/articles/patterns-of-trustworthy-experimentation-post-experiment-stage/)

첫 모델 도입의 구매 판정은 A에 실제 룰 응답이 기록되고 B에 고정된 운영용 모델 버전 하나가 관측된 실험에 적용한다. 후속 모델 교체는 A와 B에 각각 서로 다른 운영용 모델 버전 하나가 관측되어야 한다. 같은 그룹에 정상 룰 응답(`rule`)과 모델 버전이 함께 기록되거나 모델 버전이 여러 개면 판정은 `pending`이다. 오프라인의 `train --baseline`은 같은 평가셋에서 운영 번들과 후보를 비교한다.

### 5.1. 추천칩 노출부터 앱 내 구매까지의 전환 지표

A/B 보고서는 두 그룹 모두 **관찰이 끝난 원래 추천 세션**을 기준으로 센다.

| 지표 | 분자 ÷ 분모 | 답하는 질문 |
|---|---|---|
| 추천 세션 → 담기율 (`cart_rate`) | 해당 추천으로 한 번 이상 담은 세션 수 ÷ 전체 추천 세션 수 | 추천을 시작한 세션 중 얼마나 자주 담는가? |
| 담기 → 구매율 (`cart_to_purchase_rate`) | 추천 담기에 연결된 앱 내 결제가 확인된 세션 수 ÷ 추천으로 담은 세션 수 | 추천으로 담은 세션 중 얼마나 자주 구매하는가? |
| 전체 추천 세션 → 구매율 (`session_to_purchase_rate`) | 위와 같은 결제 확인 세션 수 ÷ 전체 추천 세션 수 | 후보로 바꾸면 추천 세션당 구매가 늘어나는가? |

구매 관찰 기간은 귀속된 추천칩의 노출 시각부터 계산한다. 그 안에서 결제하면 결제일이나 체크아웃 화면 진입 시점이 달라도 원래 AR 세션으로 집계한다. 해당 세션의 모든 추천 관찰 기간이 끝났을 때 세 지표의 분모에 편입한다. 분모가 0인 비율은 `null`이다. 학습 Y인 `added_to_cart`는 계속 노출 단위의 AR `cart_add`로 생성한다.

예를 들어 그룹마다 추천 세션이 1,000개이고, A는 담기 세션 100개·구매 세션 20개, B는 담기 150개·구매 24개라면 담기 → 구매율은 A 20%와 B 16%, 전체 추천 세션 → 구매율은 A 2.0%와 B 2.4%다. 도입 판정에는 전체 추천 세션 → 구매율의 개선 폭과 회원 단위 95% 신뢰구간을 사용한다.

**주문·결제 저장.** 장바구니는 실제로 남은 수량의 AR 담기 이벤트 ID를 주문 요청에 보낸다. 서버는 수집 동의와 회원·상품·호수가 일치하고 노출에 연결된 기록을 확인한 뒤, 주문 항목마다 첫 유효 출처로 `user_behavior_events`에 `surface=ar_checkout`인 `cart_add`를 기록한다. 기존 `order_line_id`로 주문 항목을, `context_snapshot`의 `ar_cart_event_id`와 `ar_impression_id`로 AR 출처를 연결한다. 동일 호수가 한 주문 항목으로 합쳐져도 출처는 한 건이다. [주문 데이터 처리](../backend/api/app/repositories/order_repository.py)

서버가 결제 승인을 확인하면 주문 `paid`와 `purchase_confirmed`를 한 트랜잭션에 저장한다. 결제 확인 시각은 `occurred_at`에 기록하며, 기존 고유 제약으로 동일 담기의 재결제 요청이 전환에 중복으로 들어가지 않게 한다. 구매 전환의 측정 범위는 이 연결을 기록한 뒤의 앱 결제다. 예전 주문과 외부몰 주문은 집계에서 제외한다. [결제 승인 처리](../backend/api/app/services/payment_service.py)

## 6. 배포·관측·재학습

| 단계 | 운영 동작 |
|---|---|
| 데이터 준비 | 동의 범위의 기록을 읽어 노출 단위 데이터셋을 생성한다. 수집 마감 시각, 분할 경계, 입력 정의, 카탈로그 버전, 회원·요청·노출·양성 건수를 함께 보관한다. 같은 노출의 재전송 또는 배치 재실행으로 행이 늘지 않게 한다. |
| 모델 등록 | 데이터 버전, 코드 버전, CatBoost 설정, 모델 파일, 오프라인 비교 결과를 한 버전으로 묶는다. 같은 색과 이력을 넣었을 때 학습 배치와 서비스가 동일한 X를 만드는지 확인한다. |
| 추천 제공 | 추천 권한을 확인하고 적격 후보의 담기 점수로 순위를 정한다. 모델 로딩·추론 실패 시 기존 룰로 응답하고 실패와 실제 적용 정책을 기록한다. |
| 운영 추적 | `policy_version`에 실험 ID, 배정 그룹, 실제 제공한 모델 버전 또는 룰 대체 응답을 기록한다. 룰 대체 응답도 원래 배정 그룹에서 평가한다. |
| 재학습·롤백 | 정해진 주기에 신규 양성 요청 수와 데이터 품질을 확인한다. 충분히 누적되면 과거와 신규 데이터를 포함해 후보 모델을 생성한다. 매 회차 최근 동일 평가셋에서 **현재 운영 모델과 새 모델**을 비교한 뒤 A/B를 거쳐 승격한다. 장애·성능 저하 시 이전 운영 버전으로 복귀한다. |

첫 배포 결정 전에 실제 이용량으로 확정할 값은 관찰 마감, 최소 개선 폭, A/B 표본·기간, 재학습 주기와 신규 데이터 기준이다. 운영 흐름은 **기록 수집 → 관찰이 마감된 데이터 추출 → PairLogit·RandomSearch 학습 → NDCG@3 오프라인 평가 → 구매율 A/B → 승격 또는 유지**다.

## 7. 로컬 실행

학습 작업은 기존 API의 Python 3.12와 `recommendation` 의존성 그룹을 사용한다. 로컬 실행과 추후 CI에서 같은 명령을 호출한다. 각 명령은 결과를 JSON 한 줄로 출력한다. 운영 데이터와 모델 산출물은 Git 제외 경로인 `ml/data/ar-recommendation/`에 둔다.

### 합성 데이터로 명령 검증

```powershell
Set-Location backend/api
uv run --group recommendation python -m app.jobs.ar_palette_ml synthetic --output ../../ml/data/ar-recommendation/synthetic.json
uv run --group recommendation python -m app.jobs.ar_palette_ml train --dataset ../../ml/data/ar-recommendation/synthetic.json --output ../../ml/data/ar-recommendation/bundles/smoke
```

출력 번들은 `model.cbm`, `manifest.json`, `metrics.json`으로 구성한다. `manifest.json`의 `model_type`으로 랭커와 분류기를 구분한다. 랭커의 원점수와 분류기의 장바구니 확률은 각각 추천 순서를 정하는 데 사용한다. 모델 경로는 실행마다 비어 있는 새 폴더를 지정한다. `--code-revision`에는 학습 코드를 만든 Git 리비전을 넣을 수 있다. 합성 번들은 로컬·개발·테스트 환경에서만 로드할 수 있고, 해당 번들로 제공한 추천은 실데이터 추출에서 제외한다.

### 기존 DB에서 수집·추출

- 로컬 Compose에 `infra/compose/compose.ar-ml.yaml`을 추가한다. 기존 스택에서 API만 다시 빌드해 시작할 때는 `docker compose -f infra/compose/compose.yaml -f infra/compose/compose.ar-ml.yaml up -d --build --no-deps api`를 사용한다.
- 오버라이드 기본값인 `AR_PALETTE_MODE=collect`에서는 기존 룰로 고른 색을 표시하고 추천 당시의 X를 요청 ID별 파일로 보존한다. 추천 요청·후보·노출·행동은 기존 PostgreSQL에 저장한다. 수집 동의와 추천 자격이 확인된 계정만 서버 순위 API를 쓸 수 있다. 구독·동의 연결 전에는 기존 두 회원 목록을 사용한다.
- 실행 중인 API 컨테이너에서 `python -m app.jobs.ar_palette_ml export --as-of <UTC-기준시각> --output /app/runtime/ar-ml/dataset.json`으로 추출한다. 호스트에서 실행할 때도 동일하며 `DATABASE_URL`과 `AR_PALETTE_DATA_DIR`은 실행 환경으로 공급한다. 추출 작업에는 기존 AR·회원 테이블의 읽기 권한이 필요하다.
- 관찰 기본값은 노출 후 **24시간**, 지연 수신 대기는 **24시간**이다. 기존 로그 중 추천 시점 입력 파일이 없는 행은 `missing_snapshot`으로 집계한다. 첫 유효 요청부터 마감된 기간이 30일 미만이면 `insufficient_collection_days`로 학습을 건너뛴다. 30일이 지난 뒤에도 분할 규칙에 맞는 사례가 부족하면 더 수집한다. 데이터셋과 스냅샷은 로컬 접근을 제한하고 계정 삭제·동의 철회 정책에 맞춰 정리한다.

### 모델 시험 적용과 성과 비교

- 로컬에서 `AR_PALETTE_MODE=model`과 `AR_PALETTE_BUNDLE=smoke`를 설정하면 후보 모델로 팔레트를 시험할 수 있다. A/B 실험은 `AR_PALETTE_MODE=experiment`와 새 `AR_PALETTE_EXPERIMENT`를 설정하고, B는 `AR_PALETTE_BUNDLE`에 후보 폴더명을 지정한다. 첫 도입에서는 `AR_PALETTE_BASELINE_MODEL_DIR`을 설정하지 않아 A가 기존 룰을 사용한다. 후속 교체에서는 A에 컨테이너 안의 운영 번들 경로(예 `/app/runtime/ar-ml/bundles/champion`)를 지정한다. 실험 ID당 추천 방식과 번들 버전을 고정한다. 모델 로딩이나 평가에 실패하면 해당 그룹의 룰 대체 응답으로 기록한다.
- 랭커의 오프라인 판정 기준은 `train --min-ndcg`와 `--min-lift`로 사전에 설정한다. 후속 후보가 운영 ML과 비교할 때는 `--baseline <운영-번들-경로>`를 함께 전달한다. 기준을 지정하지 않은 실행에서는 점수만 보고한다. 1위 적중률 기준이 필요한 학습에는 `--min-hit`을 사용한다.
- `train`의 기본값은 `--model-type ranker --search-method random`이다. 검증 점수와 설정별 결과는 `metrics.json`, 모델 종류와 선택한 탐색 방식은 `manifest.json`에 기록한다. 기존 분류기를 다시 학습할 때는 `--model-type classifier`를 사용하고 Optuna로 탐색할 때는 `--search-method optuna`를 지정한다.
- 첫 실험과 후속 실험의 구매 A/B 집계는 `experiment --id <실험-ID> --start <시작> --end <종료> --as-of <기준시각> --purchase-window-hours <구매-관찰시간> --min-sessions <그룹별-표본> --min-lift <최소-개선폭> --output <보고서-경로>`로 실행한다. 개선 폭은 비율 차이로 지정한다. 예를 들어 `0.01`은 1%p다. JSON의 `purchase_metrics.session_to_purchase_lift`가 판정에 사용한 B−A 차이이고, 최상위 `lift`는 담기율 차이다. 구매 관찰 시간을 생략하면 담기 지표를 확인할 수 있으며 판정은 `pending`이다. 운영 전환은 검토 후 버전 경로를 변경하고, 롤백은 이전 경로나 `legacy` 모드를 사용한다.
- RDS에서는 DB 연결과 읽기 권한을 실행 환경에 맞춰 설정한다. 추천 API와 학습 작업이 같은 입력 스냅샷을 볼 수 있도록 접근 제한된 영속 저장소를 연결한다. GitHub Actions는 같은 명령을 예약 실행하고, MLflow는 모델·입력 계약·평가 지표를 등록하는 단계로 붙인다. 실사용 원시 데이터셋과 회원별 행은 학습 작업의 저장 경계 안에서 관리한다.
