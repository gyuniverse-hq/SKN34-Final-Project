# AR 제어툴 1차 설계안

작성일: 2026-11-15 · 상태: 1차 구현 및 단일 채팅 검증, Expo Go 실기기 확인 대기

## 목적과 범위

Luna가 사용자의 표현과 현재 화면 상태를 함께 해석하고 `ar_control` 하나를 호출해 직접 탐색 화면을 조작한다. 채팅과 파일 전사 음성에서 직전 강도 조절을 이어가거나 이번 AR에서 발라본 제품·호수를 순서로 다시 적용할 수 있다.

실제 노출되는 선택지는 화면 상태와 카탈로그에 따라 다르다. 기존 강도·스타일 명령을 사용하는 구버전 클라이언트는 기존 경로를 유지한다. 현재 AR 채팅은 아래의 단일 툴 경로를 사용한다.

**한국어 모바일 음성 대화 (2026-11-16)** 가운데 마이크 버튼으로 대화를 시작한다. 발화 후 약 1.2초간 조용해지면 녹음을 `POST /api/chat/ar-control/transcribe`에 보낸다. 녹음 한 구간은 최대 30초이며 무음 구간은 기기에서 폐기한다. 전사문은 당시 AR 상태와 함께 Luna에 자동으로 전달된다. 기기 TTS가 최종 답변을 읽는 동안 마이크를 닫고, 재생이 끝나면 다시 듣는다. 가운데 정지 버튼이나 화면 이탈로 대화를 종료한다. 텍스트 입력창은 개발 빌드에서 테스트용으로 열 수 있다. 각 요청은 기존 단일 요청 계약을 사용한다.

## 동작 흐름

1. 사용자가 채팅으로 자연스럽게 요청한다.
2. Supervisor가 채팅 또는 전사된 `ar_command` 요청을 AR 에이전트 Luna에 전달한다. Luna는 현재 화면에서 허용한 `ar_control` 조작을 선택하거나, 조작이 필요 없는 질문에 바로 답한다.
3. 앱이 실제 제품·호수, 현재 상태와 사용 가능 여부를 검증하고 화면에 적용한다.
4. 툴이 확인된 결과를 반환하면 Luna가 메이크업 아티스트처럼 자연스럽게 답한다. 질문이나 불분명한 표현에는 필요한 정보를 알려주거나 되묻는다.

현재 화면의 적용 색, 팔레트 가운데 색, 주변색 탐색의 기준색은 각각 구분한다. 필터 변경만으로 색을 적용하지 않는다. 립 컬러와 립오일·립밤은 별도 레이어다. 팔레트 스와이프가 새 색에 멈추면 해당 색이 적용된다.

## 공통 결과

| 필드 | 제안 |
|---|---|
| `status` | `OK` 조회 성공, `APPLIED` 적용 확인, `NO_CHANGE` 동일 상태, `REJECTED` 거절, `FAILED` 실패, `UNKNOWN` 결과 미확인 |
| `data` | action별 조회 결과나 실제 선택된 제품·호수, 화면 상태 |
| `before`, `after` | 변경 전후 확인된 상태. 해당하는 조작에만 포함 |
| `reason` | 미지원, 대상 없음, 상태 변경, 적용 실패 등 사유 |
| `displayMode` | 얼굴 AR 또는 색상표 등 실제 표시 상태 |
| `renderPending` | 얼굴 추적을 기다리며 제품과 호수만 먼저 선택한 경우 `true` |

렌더가 필요한 action은 앱의 적용 확인 이후 `APPLIED`를 반환한다. 실패 또는 미확인을 성공으로 표현하지 않는다. 사용자 수동 조작으로 처리 중 상태가 바뀌면 이전 상태를 전제로 한 명령을 재검증한다. 제품과 호수는 실제 카탈로그에서 확인한다.

`?`는 선택 입력을 뜻한다. 아래 답변과 호출은 결과가 해당 예시와 일치할 때의 예시이며 고정 문구가 아니다.

| `restore_makeup` | `source=look_original`, `zone` | 수정된 부위를 현재 룩의 원래 값으로 복원. 부위와 복원 값 반환 | “눈화장은 이 룩 원래 느낌으로 해줘.” → “섀도를 이 룩의 원래 색과 발색으로 돌려봤어요.” |

| `reapply_try_on` | `choice=reapply_try_on/<scope>`, `ordinal` | 이번 AR 세션에서 실제로 체험한 순서를 조회하고 같은 제품·호수를 재적용 | “아까 두 번째로 발라본 립 다시 발라줘.” → 실제 체험 이력에 해당하는 호수 안내 |

| `navigate` | `destination=product\|store\|cart\|similar_products\|back` 또는 `choice=navigate/recommendation/<kind>/<rank>` | 현재 제품 또는 직전에 표시한 추천 후보의 정확한 상세로 이동. 목적지와 대상 반환 | “방금 추천한 두 번째 제품 상세 열어줘.” → 실제 목록의 두 번째 제품 상세 열기 |

| `control_practice` | `operation=start\|next\|previous\|go_to\|peek_on\|peek_off\|exit`, `step?` | 현재 메이크업의 따라 그리기 시작·이동·종료. 룩이 없으면 직접 탐색과 동일하게 첫 안내부터 시작 | “지금 보이는 대로 따라 그려볼래.” → “같이 해봐요. 첫 단계는 {실제 단계}예요.” |
| `set_look_strength` | `direction=up\|down` 또는 `value` | 조절이 제공되는 영상 룩의 전체 강도 변경. 전후 강도 반환 | “전체적으로 조금만 덜 진하게 해줘.” → “룩 전체의 발색을 한결 가볍게 잡아봤어요.” |
| `control_camera` | `operation=request_access\|open_settings\|swatches_only\|retry` | 카메라 권한·화면 상태에 따라 동작하고 결과 반환 | “얼굴은 안 비추고 색만 구경할래.” → “색상표로 볼게요. 마음에 드는 색을 골라보세요.” |
| `retry_catalog` | 없음 | 체험 상품 목록 재조회. 로딩·성공·실패 반환 | “색상이 안 뜨는데 다시 불러줄래?” → 성공 시 “색상표가 다시 열렸어요.” |

직접 탐색의 부위는 립, 블러셔, 아이섀도, 아이라이너, 하이라이터, 쉐딩, 눈썹, 파운데이션이다. 립 색상 계열·제형 필터 등은 현재 화면이 제공하는 값만 사용한다. 섀도 표현과 아이라인·하이라이터 프리셋도 실제 선택지로 제한한다. 현재 쉐딩은 턱과 코를 함께 처리한다. 영상 룩 강도, 따라 바르기, 판매처 링크는 해당 조건에서만 제공한다.

추천 목록은 같은 AR 화면에서 사용자에게 보여준 제품·호수의 순서를 보관한다. 순번 선택 시 목록을 다시 계산하지 않으며, 부위·탐색 필터·카탈로그 또는 계정이 바뀌면 이전 후보를 적용하지 않는다. 개인화 결과는 회원 동의와 기존 추천 권한을 확인하고 직접 탐색의 추천 데이터를 사용한다. 체험 이력과 추천 목록이 모두 있고 사용자가 어느 쪽인지 말하지 않으면 확인 질문을 한다.

### 직접 탐색과 음성 대화의 동등성 검증

| Action | 시작 상태와 사용자 요청 | 기대 화면·반환 |
|---|---|---|
| `set_shadow_point` | 베이스 섀도 A 적용 중. “눈꼬리에 {실제 호수} 얹어줘.” 다음에 “방금 눈꼬리에 더한 색만 빼줘.” | 각 렌더 확인 후 `APPLIED`. 베이스의 제품·호수·발색은 유지. 섀도가 비어 있으면 `REJECTED`. |
| `get_recommendations` → `apply_recommendation` | 피부색 측정과 카탈로그가 준비됨. “내 피부색에 가까운 것들 좀 볼래.” 다음에 “두 번째 추천 발라줘.” | 첫 요청은 `OK`와 순서가 있는 후보 및 기존 얼굴 유지. 후속 요청은 두 번째 항목과 동일한 제품·호수 ID를 렌더 후 `APPLIED`로 반환. |
| `get_recommendations/personalized` → `navigate/recommendation/personalized/2` | 직전 립의 개인화 목록을 보고 “두 번째 제품 상세 볼래.” | 같은 두 번째 호수의 상세로 이동. 값이 사라진 경우 거절하며 다른 항목으로 대체하지 않음. |
| `set_palette_filter` | 주변색 탐색의 기준과 방향을 선택한 상태. “여기서 보송한 제형만 보여줘.” | 기준·방향 유지, 요청한 제형만 적용한 후보와 개수 반환. |
| `set_style` | 하이라이터 프리셋 적용 중. “광대에 광을 켜줘.” | 직접 탭한 것과 동일하게 프리셋 해제와 활성 부위 반영. 실제 설정이 바뀌면 `APPLIED`. |
| `set_view` | 마이크를 켠 상태. “거울 열어줘.” 다음에 “이제 닫아줘.” | 같은 음성 세션에서 열고 닫기 모두 `APPLIED`. 도구·상품·안내 시트에서도 닫기와 마이크 정지가 가능. |
| `control_practice`, `add_to_cart/fit_product` | 직접 시작한 따라 그리기 또는 상품 상세에서 고정 시착으로 진입 | 해당 화면에서 음성 시작이 가능하고 기존 단계 안내·고정 호수에 맞는 조작을 실행. |
| `apply_shade` | 카메라는 켜져 있으나 잠시 얼굴을 놓친 상태. “다른 립 하나 골라줘.” | 실제 호수를 선택하고 `OK`·`renderPending: true`를 반환. 얼굴 추적 복구 시 같은 호수 표시. Luna 응답은 호수 선택 상태를 안내. |

같은 색을 연하게 하는 조작과 다른 차분한 호수로 바꾸는 조작은 구분한다. “보여줘”는 조회나 팔레트 변경이며, “골라서 발라줘”는 찾기와 적용을 한 요청 안에서 순서대로 수행할 수 있다. 같은 호수 `apply_shade` 재호출은 지우기가 아닌 `NO_CHANGE`로 취급하고, 제거에는 `clear_layer`를 쓴다. 기존 텍스트 강도 변경에 대한 Undo는 원래 룩으로 복원하는 동작과 의미를 구분해 연동 여부를 결정한다.

## 응답과 평가 예시

대화 모드는 맨얼굴에서 시작할 수 있다. 사용자가 제품 종류를 지정하면 직접 탐색의 8개 부위 중 해당 부위에 한 호수를 적용한다. 부위를 생략하면 현재 부위를 쓴다. 립 오일과 립밤은 각각 `apply_shade/lip/oil`, `apply_shade/lip/balm`으로 맨입술 위에도 올릴 수 있다. 피부색에 맞춰 발라 달라는 요청은 `apply_shade/foundation/skin_match`로 기기에서 측정한 피부색을 사용한다. 측정 대기 중이면 적용을 보류한다. 대화 화면은 적용을 확인한 부위와 제품을 표시한다.

색 선택을 맡기는 `pick`에서 립·블러셔·섀도는 화면에 표시하는 다른 부위의 색을 발색 강도로 가중해 기준색을 만든다. 립과 볼의 비중이 가장 크고 섀도가 그다음이다. 블러셔는 기준색보다 조금 밝고 부드러운 색을 목표로 삼아 실제 호수를 비교한다. 참고할 색이 없으면 부위별 기본색(립은 로즈, 볼은 로지 누드, 섀도는 뉴트럴 브라운)에 가까운 호수를 고른다. 그 밖의 부위의 일반 `pick`은 카탈로그 순서를 쓴다. 조화 추천 성공 시 `matchedTo`에 실제 참고한 부위와 색 계열을 돌려준다. 사용자가 분위기를 지정하면 Luna가 `by_color`의 조건을 고르고, 립스틱·틴트·글로스를 명시하면 `lipType`으로 카탈로그 상품 분류도 제한한다. 유효하지 않은 제안은 실행 전에 한 번 재해석하고 같은 검증을 거친다.

색 조건은 `apply_shade/<부위>/by_color`와 조회 전용 `find_shades/<부위>/by_color`가 공유한다. Luna가 발화에서 유추한 필드만 채우며 하나 이상 필요하다.

| 입력 | 허용값 | 실제 호수 선택 기준 |
|---|---|---|
| `family` 색 계열 | red, coral, pink, berry, nude, brown | 직접 탐색과 같은 계열 분류 |
| `lightness` 밝기 | light, medium, deep | 제품색의 CIELAB L*. 45 미만은 deep, 65 이상은 light |
| `chroma` 채도 | muted, medium, vivid | 제품색의 CIELAB C*. 38 미만은 muted, 55 이상은 vivid |

모든 조건을 만족하는 호수만 남긴다. 계열이 있으면 기준색의 밝기·채도 중 지정한 축만 바꾸고 CIEDE2000으로 순위를 정한다. 계열을 생략하면 요청한 밝기·채도 축의 목표값까지 거리를 비교한다. 구간과 목표값은 앱의 카탈로그 탐색 기준이다. 제품 원래 색과 적용 강도는 이 계산으로 바꾸지 않는다. 제형 또는 유효한 색이 없는 제품, 임시 색, 립케어는 색 추천에서 제외한다. 일치 호수가 없으면 `OK`와 `applied:false`를 반환하고 기존 상태를 유지한다. “지금 것보다 조금 차분한 걸 추천해줘”처럼 착용색이 비교 기준이면 주변색 순위를 쓴다. 얼굴 렌더가 확인되기 전에는 적용 완료로 답하지 않는다.

**Luna에게 주는 지시와 앱 코드의 경계**

| 단계 | 입력과 역할 |
|---|---|
| AR 에이전트의 도구 선택 (`ArControlAgent.plan`) | 사용자 문장, 언어, 현재 AR 상태 및 부위와 화면이 허용한 조작 키를 받는다. 색을 골라 달라는 추천, 유무 조회, 목록 탐색을 구분한다. 명시한 부위를 따르고, 모호하면 되묻고, 금지한 변경은 하지 않는다. 표현별 응답표는 없다. |
| 앱의 선택과 실행 | 모델이 제품명·호수를 지어내지 않는다. 앱이 카탈로그에서 한 호수를 고르고 프레임의 완료 여부를 확인한다. 빈 결과나 실패는 성공으로 바꾸지 않는다. |
| AR 에이전트의 답변 (`ArControlAgent.answer`) | 앱이 반환한 결과와 에이전트의 메이크업 아티스트 지침을 바탕으로 답한다. 한 호수를 추천해 적용했다면 실제 브랜드·제품명·호수명과 확인된 색감을 설명한다. 색상표에서 선택했거나 얼굴 추적을 기다리는 중이면 그 상태를 알려준다. |

Luna는 확인된 제품명과 실제 결과를 바탕으로 친근한 존댓말을 생성한다. 색이나 발색을 조율할 때 의견을 묻고 매번 같은 질문을 반복하지 않는다. 적용 실패, 상품 없음, 미확인도 실제 상태에 맞게 말한다. 문장마다 action이나 답변을 하드코딩하지 않는다.

| 사용자 입력 | 현재 화면 상태 | 기대 동작 |
|---|---|---|
| “이거 조금만 연하게 해줘.” | 립 탭에 립 적용 | 현재 립 강도 조절 후 “립 색은 살리고 발색만 살짝 덜어냈어요.” |
| “이거 조금만 연하게 해줘.” | 블러셔 탭에 블러셔 적용 | 블러셔 강도 조절 후 “볼에 올라온 색을 조금 부드럽게 풀어봤어요.” |
| “이거 조금만 연하게 해줘.” | 립 탭에 적용 색 없음 | 임의로 색을 바르지 않고 대상 확인 |
| “음, 이거 좀 진한가?” | 립 적용 | 현재 상태를 유지하며 조정 의사 확인 |
| “이 립보다 덜 쨍한 색 하나 골라서 발라줘.” | 립 적용 및 주변색 탐색 가능 | 실제 호수를 찾아 적용 확인 후 “조금 더 차분한 {호수명}을 발라봤어요. 이쪽 느낌은 어때요?” |

## 1차 action별 검증 기준

각 행은 독립된 단일 채팅 테스트다. 시작 상태는 앱에 준비하고 Luna에는 실제 화면 상태와 채팅만 전달한다. A·B는 검증자가 카탈로그에서 선택한 실제 제품·호수 쌍이다. 표의 상태명은 최종 `status`, 뒤의 값은 `data` 또는 `before`·`after`에서 확인할 내용이다. 아래 결과는 구현 후 판정에 사용할 설계 기준이다.

### 색 조회와 팔레트

| Action | 시작 화면 상태 | 사용자 채팅 | 기대 화면 변화 | 반환값과 통과 조건 |
|---|---|---|---|---|
| `get_state` | 립 A를 착용하고 중앙에는 B가 보임 | 지금 입에 바른 거 이름이 뭐야? | 조회만 수행 | OK · 착용=A, 중앙=B. A의 이름으로 답한다. |
| `get_state` | 립 컬러 미적용, 중앙=B | 지금 입에 바른 거 이름이 뭐야? | 조회만 수행 | OK · 착용=null, 중앙=B. 아직 컬러를 바르기 전이라고 안내한다. |
| `select_zone` | 립 탭, 눈썹 탭에 호수 2개 | 눈썹도 좀 볼래. | 눈썹 탭과 팔레트가 열림 | APPLIED · 활성=brow, 표시 2개. 기존 립 A 유지. |
| `select_zone` | 이미 눈썹 탭, 눈썹 상품 0개 | 눈썹도 좀 볼래. | 빈 눈썹 팔레트 유지 | NO_CHANGE · 활성=brow, 표시 0개. 고를 색이 있다고 답하면 실패. |
| `find_shades` | 립 탭, 등록된 분홍색 2개, 착용=A | 분홍 계열도 있어? | 얼굴·필터·중앙 그대로 | OK · 일치 2개와 실제 제품·호수 ID. 한 호수라도 임의 적용하면 실패. |
| `find_shades` | 같은 조건에서 분홍색 0개, 조회 완료 | 분홍 계열도 있어? | 화면 그대로 | OK · 빈 목록, 개수 0. 데이터 로딩 실패는 빈 결과와 구분. |
| `set_palette_filter` | 립 A 착용, 전체 보기, 보송한 제형 칩 제공 | 반짝이는 거 말고 보송한 것만 볼래. | 해당 제형으로 팔레트 좁힘 | APPLIED · 활성 필터, 일치 개수. 착용=A. |
| `set_palette_filter` | 각 칩은 있지만 선택한 두 조건의 교집합이 없음 | 핑크 중에 보송한 것만 보여줘. | 빈 팔레트 표시, 얼굴 유지 | APPLIED · 두 조건 활성, 개수 0. 다른 제형을 대신 보여주면 실패. |
| `apply_shade` | 립 A 착용, 중앙=B | 가운데 있는 거 입에 올려봐. | 얼굴에 B 적용 | APPLIED · A→B와 실제 제품·호수. B가 이미 착용색인 조건에서는 NO_CHANGE, B 유지. |
| `apply_shade` | 팔레트 0개, 중앙색 없음 | 가운데 있는 거 입에 올려봐. | 새 색을 바르지 않음 | REJECTED · 중앙 호수 없음. 지금 발라볼 색이 없다고 안내. |
| `apply_shade/by_color` | 립 탭, 맨입술 | 여리여리한 느낌으로 추천해줘 | 특정 계열을 강제하지 않고 밝고 저채도인 실제 호수 한 개 적용 | APPLIED · 실제 모델 실행에서 어뮤즈 듀 틴트 ‘도토리’ 선택 |
| `apply_shade/by_color` | 같은 카탈로그, 맨입술 | 쨍한 핑크 말고 차분한 핑크로 해줘 | 핑크와 저채도 교집합에서 한 호수 적용 | APPLIED · 실제 모델 실행에서 잉가 워터 글로우 립 틴트 ‘스플래쉬’ 선택. 조건에 맞는 호수가 없는 카탈로그에서는 OK · applied=false |
| `apply_shade/<부위>/pick` | 대화 탭, 모든 부위 미착용, 기본 탭은 립 | 오늘은 아이라이너부터 그려줘 | 아이라이너에만 실제 호수를 적용하고 현재 제품 행에 해당 호수 표시 | APPLIED · 립은 빈 상태 유지. 일반 첫 적용은 직접 탐색 8개 부위에서 같은 기준으로 검증 |
| `step_shade` | 팔레트 중앙=A, 오른쪽 이웃=B | 오른쪽 것도 발라볼래. | 중앙과 착용색이 B로 이동 | APPLIED · 도착 호수=B. 중간 색은 적용하지 않음. |
| `step_shade` | 호수 1개, 이미 착용 중 | 오른쪽 것도 발라볼래. | 현재 호수 유지 | NO_CHANGE · 이웃 없음. 빈 팔레트라면 REJECTED · 이동 대상 없음. |
| `clear_layer` | 립 A 위에 오일 적용 | 립은 두고 오일만 빼줘. | 오일만 제거 | APPLIED · 립케어=null, 립=A. |
| `clear_layer` | 립 A 착용, 립케어 없음 | 립은 두고 오일만 빼줘. | 현재 립 그대로 | NO_CHANGE · 립케어가 이미 비어 있음. 립 색을 지우면 실패. |

|---|---|---|---|---|

### 모든 사례에 적용하는 판정 규칙

- **Luna의 해석**을 확인할 때는 정확한 문장 일치 대신 의미를 판정한다. “볼 색 바꾸지 마”에는 변경 호출이 없어야 하고, “이거 좀 진한가?”에는 의견을 묻거나 조정을 제안할 수 있다. 이때는 변경 action의 반환값 자체가 없다. 무효한 인자로 변경 툴을 호출했을 때의 `REJECTED`와 구분한다.
- **실행 결과**는 처리 직전과 직후의 화면·상태를 비교한다. 실행 전에 사용자가 다른 호수로 바꿨으면 `REJECTED`와 상태 변경 사유를 반환하고 새 호수를 유지한다. 렌더 오류가 확인되면 `FAILED`, 완료 여부를 확인할 수 없으면 `UNKNOWN`이다. 둘 다 적용 완료로 답하면 실패다.
- **응답**은 확인된 변화와 일치해야 한다. `APPLIED`일 때는 “볼 색을 살짝 덜어봤어요”, `NO_CHANGE`일 때는 “지금이 가장 은은한 발색이에요”처럼 결과에 맞춘다. 색상표에서는 선택한 호수를 말하고, 얼굴에 발랐다는 표현은 얼굴 AR에서 적용이 확인됐을 때만 쓴다.
- **한 요청 안의 조회 후 적용**은 단계별로 판정한다. ‘덜 쨍한 립 하나 골라 발라줘’에 실제 매칭 호수가 없으면 조회 결과 0개를 안내하고 적용 호출을 생략한다. 호수를 찾았어도 렌더 확인이 실패하면 조회 성공을 적용 성공으로 보고하지 않는다.

## Redis를 사용하는 후속 강도 조절

채팅과 파일 전사 음성 모드는 같은 AR 세션을 사용한다. 일반적인 상대 강도 조절은 0.10씩 움직인다. 후속 요청에서는 직전에 화면에서 실제로 바뀐 강도 폭의 50%를 같은 방향으로 적용한다. 매번 0.01 단위로 반올림하고 최소 한 칸을 사용한다. 부위별 슬라이더 한계에서 멈추며 다음 요청의 기준은 실제로 움직인 폭이다.

1. 앱이 강도 조절 결과를 확정하면 기존 ACK에 부위와 실제 변경 전후 값을 포함한다. 서버는 발급한 제안과 사용자·세션·부위·방향·상태 버전을 대조한 뒤 기존 `ChatSessionRepository`의 Redis와 TTL(기본 600초)에 저장한다. 기록은 명령별로 만료되며 ACK 재시도로 수명이 늘어나지 않는다.
2. 다음 요청에는 같은 사용자의 AR 세션 ID와 직전 조절 명령 ID를 보낸다. 진행 중인 ACK가 있으면 먼저 전송을 확인한다. 적용 버전과 현재 화면 버전이 일치할 때만 서버가 직전 변화를 Luna에게 제공한다. 손으로 다른 제품을 적용했거나 기록이 만료됐으면 해당 근거를 제공하지 않는다.
3. Luna가 발화 의미를 보고 새 조작인지 이전 조작의 연속인지 고른다. 확인된 직전 조작이 있으면 `ar_control` 안에 `continue_intensity/<부위>/<방향>` 선택지가 생긴다. 서버가 후속 `adjust_intensity`를 제안하면 앱은 해당 명령 ID로 확인한 직전 폭의 절반을 계산한다. 부위나 방향을 새로 명시한 요청에는 기존 조작을 사용할 수 있다. 이력 없는 생략형 요청은 되묻도록 지시한다.

이 Redis 기록은 직전 강도 변화를 참조한다. 제품 착용 순서는 아래와 같이 AR 화면에서 관리한다.

## 구현된 호출 형식과 검증 방법

### 카탈로그 호수명과 색감 요청 구분

앱이 이번 발화에 등장한 실제 카탈로그의 호수명을 찾아 `arContext.catalogNameMatches`로 제품 ID, 호수 ID, 부위와 이름을 보낸다. 검색에는 유니코드 표기, 대소문자, 띄어쓰기를 정규화한 카탈로그 이름을 사용한다. Luna는 적용 의도와 이름 근거를 함께 보고, 특정 호수 요청이면 `apply_shade/product_shade`로 두 ID를 고른다. “차분한 레드”처럼 원하는 색감을 설명하면 `apply_shade/lip/by_color`의 색 계열·밝기·채도를 고른다. 동일한 호수명이 여러 제품에 있으면 브랜드·제품 정보로 구분하거나 되묻도록 지시한다. 금지 표현과 조회 의도도 Luna가 해석한다.

실행 시 앱이 현재 카탈로그에 두 ID가 모두 있는지 다시 확인한다. 특정 문장이나 호수명을 소스 코드의 조작 조건으로 등록하지 않는다.

### 이번 AR에서 발라본 호수 다시 적용하기

AR 화면에 들어오면 기기에 새 착용 이력을 연다. 제품 상세에서 특정 호수를 착용한 채 들어오면 해당 호수부터 센다. 직접 탐색과 대화 모드를 오가면서 실제 착용 상태가 새 제품·호수로 바뀔 때마다 부위, 제품 ID, 호수 ID를 순서대로 추가한다. 이미 입힌 호수를 그대로 두거나 강도만 바꾸는 경우, 팔레트 조회, Luna의 실패한 렌더는 횟수에 포함하지 않는다. 다른 색을 거쳐 다시 입힌 호수는 새 체험으로 센다. 화면을 나가거나 사용자 계정이 바뀌면 이력을 비운다.

Luna는 화면에서 부위별 체험 횟수를 보고 `reapply_try_on/lip`처럼 범위를 고른 뒤 `ordinal`에 1부터 시작하는 순번을 준다. `all`은 전체 착용 순서이며, 립 컬러와 립케어는 각각 `lip`, `lipCare`로 센다. 앱이 그 위치의 두 ID를 현재 카탈로그에서 조회해 같은 호수를 적용한다. 없는 순번이거나 해당 호수가 카탈로그에서 빠졌으면 `REJECTED`를 반환하고 현재 착용을 유지한다. 이미 착용한 호수는 `NO_CHANGE`, 적용 성공은 `APPLIED`와 실제 제품·호수 이름을 반환한다.

2026-11-16 앱 화면과 실제 Luna를 연결해 확인했다. 손으로 롬앤 04호 번트하트를 고르고, Luna가 블러셔를 바른 뒤 선명한 레드 립으로 롬앤 12호 앤셜리를 골랐다. 손으로 헤라 립을 바꿔 입힌 뒤 “아까 두 번째로 발라본 립 다시 발라줘”를 보내자 롬앤 제로 벨벳 틴트의 `productId=oy-a000000120880`, `shadeId=12`가 다시 적용됐다. 첫 립을 요청하자 같은 제품의 `shadeId=04`로 돌아갔다.

### 요청과 결과 전달

1. 앱은 `POST /api/chat`에 채팅 문장, `requestType: ar_command`, 요청 ID와 `arContext`를 보낸다. `control.summary`는 현재 화면의 JSON 문자열이고 `control.choices`는 이 화면이 처리할 수 있는 조작 키다. 원본 얼굴 영상·사진이나 직전 채팅을 모델에 보내지 않는다.
2. Luna에게 공개하는 함수는 하나다. `ar_control({choice:"apply_shade/lip/by_color",family:"pink",chroma:"muted"})`처럼 `choice`에 **action/대상/옵션**을 담고 해당 조작에 필요한 필드만 함께 보낸다. 사용자 입력은 채팅 문장뿐이다.
3. 앱은 제안이 만들어진 상태와 현재 상태를 대조하고 조작한다. 라이브 얼굴에서 색·강도·표현을 바꾸는 경우에는 같은 렌더러에서 해당 프레임의 완료를 받은 뒤에만 상태를 확정한다. 색상표에서의 선택과 얼굴에 바른 결과를 구분한다. 사용자가 다른 호수를 먼저 고르면 예전 제안으로 덮어쓰지 않는다.
4. `/api/chat/acks`는 실행 상태를 접수한다. `POST /api/chat/ar-control/reply`는 같은 사용자에게 발급한 제안 ID와 앱의 결과를 받아 **이번 요청의** Luna 답변을 만든다. 착용색 질문에는 팔레트 중앙색을 답변 근거로 사용하지 않는다. 이 요청은 새 대화 턴이 아니며 이력 DB가 필요하지 않다. 로컬 개발 서버의 기존 요청 중복 방지 정책을 사용한다. 영속적인 AR 요청 저장소가 없는 운영 환경에서는 기존 차단 정책을 유지한다.
5. 상대 강도를 올리거나 낮추거나 절반으로 줄이는 제안에는 Luna가 생성한 `onAppliedReply`가 포함될 수 있다. 앱은 `APPLIED` 결과에서 조작 부위의 변경 전후 강도가 요청 방향과 일치할 때만 초안을 표시하고 음성 모드에서 읽는다. 이때 ACK는 보내고 추가 답변 호출은 생략한다. 초안이 없거나 결과가 조건과 다르면 4번 경로로 실제 결과를 설명한다. [음성 지연 비교](AR_VOICE_COMPARISON.md)

| 확인한 경로 | 확인 방법과 관찰 결과 |
|---|---|
| 실제 Luna의 해석 | `backend/chatbot/tests/test_ar_control.py`의 실모델 사례: 같은 “이거 조금만 연하게 해줘”를 립에서는 립, 볼에서는 블러셔 조절로 해석. 분홍 계열 유무는 조회, “좀 진한가?”에는 변경 없음. |
| 채팅 입력 → 서버 → 앱 → 답변 | `__tests__/arIntegration.test.tsx`의 선택 실행 사례는 로컬 FastAPI와 실제 모델을 연결한다. 립 0.65에서 채팅 입력 후 0.55 프레임을 확인한 뒤 답변이 표시됐다. 립을 지운 뒤 이름을 물으면 중앙 호수가 있어도 “지금 입술에는 바른 색조가 없어요”라고 답했다. 문장은 고정하지 않는다. |
| action별 동작과 예외 | 같은 화면 통합 테스트 및 `__tests__/arControl.test.ts`는 모델 제안과 기기 신호를 제어해 최솟값·빈 레이어·빈 필터·정상/실패 렌더·카메라 권한 거절·장바구니 중복 등을 재현한다. 이 테스트는 한국어 이해나 기기의 영상 품질을 판정하지 않는다. |
| 실기기 확인 대기 | Expo Go에서 **AR → 채팅**으로 들어간다. 립을 손으로 고른 뒤 “이거 조금만 연하게 해줘”, 바른 립을 지운 뒤 “지금 입에 바른 게 뭐야?”를 각각 입력한다. 화면의 실제 발색, 중앙색과 착용색 구분, 권한 창·판매처 열림을 기기에서 확인한다. |

기본 앱 테스트는 API 키를 쓰지 않는다. 설정된 모델로 재검증하려면 로컬 챗봇에 `LLM_API_KEY`와 `LLM_MODEL`을 설정하고, `backend/chatbot`에서 `RUN_AR_LIVE=1` 환경변수로 `uv run pytest tests/test_ar_control.py`를 실행한다. 화면까지 연결할 때는 같은 챗봇을 로컬에 띄우고 루트에서 `AR_CONTROL_TEST_PORT`를 해당 포트로 설정한 뒤 `npm test -- --runInBand arIntegration -t "uses real Luna"`를 실행한다.

현재 설정된 GPT-6 Luna는 Chat Completions에서 함수 호출 시 `reasoning_effort: none`을 요구한다. AR 조작을 선택하는 호출에만 이 설정을 붙인다. [OpenAI Docs: GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna)

## 초기 설계에서 확인 대상으로 둔 사항

- LLM 담당자와 단일 `ar_control` 호출 형식, 기존 `/api/chat` 요청·제안·앱 실행·ACK에 연결하는 방식, 응답 페르소나 담당을 합의한다.
- 각 action의 현재 화면 지원 조건과 실제 입력 범위, 필수 필드, 실패 이유를 코드 및 실기기 기준으로 확정한다. 선택한 제품이 없을 때와 룩 색만 있을 때를 포함한다.
- 첫 조절의 적용 방식과 경계값, 후보가 여러 개일 때 선택 기준, 사용자 요청이 모호할 때 되묻는 기준을 정한다.
- 한 발화에서 조회 후 적용처럼 여러 action을 수행하는 순서와 중간 실패·사용자 수동 조작·중복 요청 시 결과 처리를 정한다.
- 자연스러운 발화, 부정·질문, 상태별 동일 발화, 실패·미지원, 카메라·카탈로그 오류를 포함한 평가 사례와 통과 기준을 만든다.
- 기존 로컬 규칙과 서버 명령의 중복 적용을 막는 라우팅을 정하고 실제 기기의 화면 반영과 ACK를 확인한다.
