2026-11-12 구버전 정리: 현재 정책11·서빙 모델·최종 재학습 자료는 보존했다.
아래 과거 실험의 상세 JSON·그림·전용 실행기는 일부 폐기했으며,
[공유 아티팩트 인계·변경 요약](recommendation-v2-artifacts.md) 및
[현재 재학습 방법](../scripts/data/recommendation/README.md)을 기준으로 실행한다.

지속 개선을 위한 추천 요청·후보·실제 노출·사용자 반응 기록은
[V2 개선용 ERD·명세](recommendation-v2-feedback-erd.md)에 정리했다. 2026-11-13부터
로그인한 개발 비교는 0020의 요청·후보·노출·반응 테이블에 연결한다. 정책11의 순위 계산은 유지한다.

추천 V3의 모델·manifest·설명서는 Git에 포함한다. 학습 원문과 실험별 산출물은 로컬 자료다.
새 clone에서는 동봉된 추천 번들을 사용하고 기존 DB·카탈로그와 피부 분석 실행 환경을 준비한다.
모델 설명과 평가 결과는 [V3 번들 설명서](../ml/runs/recommend-cat-v3/bundle/README.md)에 있다.

기존 AI추천 화면의 `/api/recommendations/skincare`를 그대로 호출하는 V1과, CatBoost 핵심 성분 → COSING 확장 → 제품 후보 → 고민별 리뷰 보정을 수행하는 V2를 비교한다. 원본 얼굴 사진은 전송하거나 저장하지 않는다. 현재 작업 공간의 V1 코드와 실행 중인 Docker V1의 스키마가 다르므로, 로컬 V1 함수를 대신 사용하거나 DB 스냅샷을 변형하지 않는다. 실행 중인 V1 HTTP 응답과 V2가 읽은 `dataVersion`이 같아야 동일 스냅샷 비교로 표시한다. 실제 AI탭의 화면 성분 예시는 평가 대상으로 사용하지 않는다.

## 실행

저장소 루트 PowerShell에서 실행한다. Docker의 기존 `vishue` 스택이 켜져 있어야 한다.

루트 `.env`에서 피부 분석과 추천 모델을 각각 선택한다.

```dotenv
SKIN_ANALYSIS_MODEL=skin-analysis-v4
RECOMMENDATION_MODEL=recommend-cat-v3
# 별도 서버 볼륨을 사용할 때만 지정 (기본: 저장소/ml/runs)
# RECOMMENDATION_MODELS_DIR=/models
```

추천 V3는 pull 시 아래 위치에 배치된다. 피부 분석 원본은 기존 별도 인계 방식을 따른다.

```text
ml/runs/
  skin-analysis-v4/bundle/   # 기존 피부 분석 원본
  recommend-cat-v3/bundle/
    model.cbm
    manifest.json
    README.md
```

비교 실행기는 피부 모델 설정과 같은 순서로 `.env`, `.env.development`, `.env.local`,
`.env.development.local`을 읽는다(뒤의 파일 우선, 셸 환경 변수가 최우선).
`NODE_ENV=production`이면 development 대신 production 파일을 읽지만 운영 비교 API는 계속 비활성이다.
V3는 기존 7개 범주형 입력에 모공·주름·색소 수치 점수 3개를 추가한다. 서비스는 manifest에 따라
V2의 7입력과 V3의 10입력을 구분한다. 요청 형식과 80성분 ID 계약은 유지한다.
다른 모델로 바꿀 때는 지원되는 입력·성분 계약의 번들을 `ml/runs/<모델 이름>/bundle/`에 배치하고
`RECOMMENDATION_MODEL`을 변경한 뒤 **비교 API를 재시작**한다. 이름은 영문 소문자·숫자·하이픈을 사용한다.
manifest의 `version`도 모델 이름과 같아야 한다. 파일 누락·이름/해시 불일치는 V2 오류로 표시하며 다른 모델로 자동 전환하지 않는다.
FastAPI를 직접 실행할 때는 `backend/api/.env` 또는 프로세스 환경 변수에 같은 설정을 넣는다.
`RECOMMENDATION_MODELS_DIR`의 상대 경로는 저장소 루트 기준이며, Docker처럼 API만 배포한 경우 API 루트 기준이다.
추천 모델은 서버에서만 로드하므로 앱의 `skin:prepare`나 모바일 에셋에 포함하지 않는다.

```powershell
# 최초 1회 또는 의존성 변경 시. 추천 모델은 저장소에 있어 내보내기가 필요 없다.
uv sync --project backend/api --group recommendation

# 비교 API. 로그인한 비교의 추천·반응 이력을 로컬 DB에 저장한다.
uv run --project backend/api --group recommendation python scripts/data/recommendation/run_v2_comparison.py --docker-local

# 다른 터미널: PC 로컬 비교 화면
npm exec expo start -- --web --port 8083 --localhost
```

백엔드 기본 모델은 V3다. 기존 환경변수에 V2가 지정되어 있으면 V3로 바꾼 뒤 API를 재시작한다.
`--docker-local`은 실행 중인 컨테이너 설정을 메모리에서 읽어 PostgreSQL의 로컬 공개 포트에 연결하며, 접속 문자열을 출력하지 않는다. 기존 Docker를 사용하지 않을 때는 backend의 `DATABASE_URL`, `RECOMMENDATION_V1_URL`, `RECOMMENDATION_MODEL`을 설정하고 해당 옵션을 생략한다.

앱에서 피부 분석 → 결과 화면 하단 **V1 / V2 추천 비교**로 진입한다. 또는 개발 웹에서 `/dev/recommendation-comparison`을 연다. 연령대와 성별만 입력하고 저장된 v4 분석을 사용한다. 고민 선택 화면은 없다. 버튼을 누른 시점의 입력이 결과에 함께 표시되며 입력 수정만으로 이전 결과가 새 입력의 결과인 것처럼 바뀌지 않는다.

PC에서는 `http://localhost:8083/dev/recommendation-comparison`으로 접속한다. 기본 비교 API는 Metro와 같은 호스트의 8082 포트이며 실행기는 `127.0.0.1`에만 바인딩한다. 따라서 휴대폰에서의 접근은 아직 지원하지 않는다. 다른 개발 API가 준비되면 `EXPO_PUBLIC_RECOMMENDATION_COMPARE_URL`로 주소를 지정할 수 있다. 웹 CORS는 기본 localhost/127.0.0.1의 8081·8083을 허용하며, 다른 주소는 `CORS_ORIGINS`로 명시한다. 개인 개발 환경에서만 실행한다. API는 `ENV=local/development/test`와 `RECOMMENDATION_COMPARISON_ENABLED=true`가 모두 필요하며 production에서는 404다. 개발 실행기는 access log를 끄며 요청 본문은 저장하지 않는다. 결과 JSON은 화면에서 확인·복사할 수 있다.

로그인 이력 저장에는 같은 Supabase 프로젝트의 `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`,
약관 동의가 완료된 회원과 DB 마이그레이션 `0020`이 필요하다. `--docker-local`은 실행 중인 API에서
공개 인증 설정 두 개도 읽어 온다. 관리자 secret key는 가져오지 않는다. 실행기 자체가 마이그레이션을
적용하지는 않으므로 다른 환경은 기존 배포 절차로 준비한다. 위의 "요청 본문 미저장"은 비회원 비교와
접근 로그에 해당하며, 로그인한 비교는 검증된 숫자·범주 입력을 `input_snapshot`에 저장한다.
8082가 다른 프로세스에 사용 중이면 `--port`와 앱의 `EXPO_PUBLIC_RECOMMENDATION_COMPARE_URL`을 함께 맞춘다.

## 실제 입력 계약과 제한

현재 v4 분석은 0~5등급의 단순 정규화가 아니라 **주의 여부에 대한 보정되지 않은 sigmoid 점수**다. 최댓값으로 고민을 선택하는 것은 개발 정책이며, 서로 다른 모델 간 심각도 비교가 검증됐다는 뜻은 아니다. 동점은 모공 → 색소 → 주름 순으로 처리한다. 여드름은 현재 입력에 포함하지 않으며, 추후 모델 계약과 함께 추가해야 한다. 누락 점수, 범위 밖 점수, 이전 분석 버전은 실패로 표시한다.

선택한 CatBoost 입력은 `age_group, gender, skin_type, primary_concern, pore, wrinkle, tone`이다. 마지막 세 값은 숫자가 아닌 **양호/주의**다. 제공된 x_metadata의 5,653행에서 `score >= 0.5 → 주의`가 해당 범주와 모두 일치함을 확인했다. 모공·색소는 양 볼 평균, 주름은 양 눈가 평균을 사용한다. 이마·미간 값은 학습 메타데이터의 해당 특성에 없으므로 합치지 않는다.

학습 자료는 `skin-analysis-v4`, `occlusion_anchored_visible_roi_v2`로 생성됐다. 모바일 ROI·전처리와 동일성이 검증된 것은 아니다. 피부 타입도 학습에서는 원본 라벨, 모바일에서는 분석·설문 보정 결과이므로 입력 분포 차이가 있다. 또한 학습 당시 대상 고민은 원본 지정값이며 현재 자동 최댓값 정책과 다를 수 있다. 이 한계는 비교 결과에 표시한다. 기존 P0/W2 코드를 임의로 번역하지 않는다.

V1에는 동일 입력 중 지원하는 피부 타입·자동 대상 고민·자극 신호만 전달한다. 복합성은 V1 스키마에 없어 unknown으로 전달한다. 공통 비교를 위해 보조 고민은 비우고 양쪽 모두 최종 5개를 요청한다. 기존 화면의 개인 선택·보조 고민까지 그대로 재현하는 실험은 아니다.

## 후보·정렬 정책 `v2-empirical-survey-7`

- ML 상위 5개는 그대로 사용한다. 성분 ID는 학습 메타데이터의 MFDS ID다. 모델 재학습은 하지 않는다.
- 대상 고민 → `function_concern` → `ingredient_function`으로 모든 관련 성분을 후보로 찾는다. ML과의 태그 교집합, 제품 존재 여부, 기존 발행 성분 매핑, 후보 개수는 후보 생성의 제한 조건이 아니다. 핵심 성분은 중복 확장하지 않는다.
- 후보의 근거를 `ml_direct`(핵심 직접 포함), `ml_shared_tag`(현재 고민의 태그를 ML과 공유), `concern_only`(고민 태그로만 연결)로 구분한다. 세 경로의 제품을 합쳐 한 점수로 경쟁시키며 그룹별 절대 우선순위나 강제 할당은 없다.
- 제품은 기존 판매 가능·식별 확인 조건을 유지한다. 카탈로그 분류가 얼굴용 leave-on 후보군(toner/essence/serum/ampoule/lotion/cream)과 다르면 제외한다. 상품명의 목주름·넥크림·바디로션·핸드크림 등 명시적인 다른 부위 표현도 제외한다. 얼굴 겸용 문구가 있으면 이 부위 규칙으로 제외하지 않는다. 근거 필드와 일치 문구를 기록한다. 이는 상품명 기반 초기 필터이며 상세 사용설명 검증이 아니다. 용도 미확인은 임의로 적합/부적합 판정하지 않는다.

### 성분 개수와 독립적인 점수

각 ML 성분 i에 대해 제품의 연결 강도 m_i를 직접 포함이면 1, 간접 연결이면 `0.5 × 고민 관련 태그 Jaccard 유사도` 중 최댓값, 연결이 없으면 0으로 둔다. 여러 확장 성분이 같은 ML 성분에 연결돼도 중복 합산하지 않는다.

- ML 연결점수 M = `Σ(ML 점수_i × m_i) / Σ(ML 점수_i)`.
- 고민 태그 점수 C = `제품의 후보 성분들이 가진 고유 고민 태그 수 / 해당 고민 전체 태그 수`. 성분 함량이나 효능 강도를 뜻하지 않는다.
- 피부타입 점수 T = 출처(`labelSource`)가 있는 제품 피부타입 목록과 사용자 타입이 일치하면 1, 그렇지 않으면 0. 현재 실제 카탈로그에는 이 출처가 없어 이 항목은 모두 0이다. 출처가 없는 타입 적합성을 만들어내지 않는다.
- 기본점수 = `0.75M + 0.20C + 0.05T`. 위 계수와 간접 연결 0.5는 검증된 최적값이 아닌 초기 실험 정책이며 응답에 노출한다.
- 전체 확장 성분 수는 분모에 들어가지 않는다. 제품에 없는 후보가 늘어도 기존 제품의 기본점수는 변하지 않는다.

### 주·보조 고민 선택 및 성분 점수 결합 (현재 정책11)

주 고민은 기존 분석점수 최댓값으로 유지한다. 동점순서 pores→pigmentation→wrinkles도 동일하다. 나머지 중 가장 높은 항목이0.5 이상이면 보조 고민으로 활성화한다. 이는 기존 모델 입력의 양호/주의 분기값을 재사용한 초기 정책이며, 서로 다른 분석모델의 점수가 같은 관리 필요성을 뜻한다는 검증은 없다. 보조 미활성 시 기존 단일고민 결과를 그대로 유지한다.

같은 나이·성별·피부타입·모공/주름/톤 상태에서 대상 고민만 변경하여 CatBoost를2회 추론한다. 각각 핵심5성분 및 고민별COSING확장을 생성한다. 원본 학습의 대상 고민이나 성분Y는 변경하지 않는다. 보조 추론 결과를 원본의 다른 대상 고민Y와 비교해 정확도를 주장하지 않는다.

제품 후보와 용도 필터는 주 고민 경로만 사용한다. 보조 전용 제품을 추가하지 않고, 주 고민 후보의 각 옵션을 보조 성분과도 대조한다. 각 고민의 점수는 기존식 `I_g=0.75M_g+0.20C_g+0.05T`를 사용하고, 활성 시 `I=0.75I_primary+0.25I_secondary`로 결합한다. 이75/25는 각 고민 점수 안의ML/태그 비중과 별개의 관리 우선순위다. 검증된 최적 가중치는 아니다.

최상위 `coreIngredients`, `expandedIngredients`, 제품의 `directIngredientIds`, `expandedIngredientIds`, `mlScore`, `concernScore`는 주 고민의 근거를 유지한다. 보조 모델·핵심성분·확장은 `secondaryRecommendation`, 제품의 보조 성분 일치와 점수는 `secondaryIngredientEvidence`, `primaryIngredientScore`, `secondaryIngredientScore`, `goalWeights`에 기록한다. `ingredientScore`는 두 고민 결합 점수다. 최종5에 주3개/보조2개 같은 개수할당은 하지 않는다.

### 리뷰 및 최종 목록

현재 정책은 `v2-primary-secondary-11`이다. 주·보조 고민 선택은 아래 절을 따른다. 고민과 사용자 피부타입의 응답비율을 먼저 하나의 적합도로 결합하고, 그 점수로 보수적 평점의 반영률을80~100%로 조절한다. 이전 정책9의 두 가산항은 적용하지 않는다.

- 평점 A_raw: 940상품 별점분포에서 추정한 디리클레–다항 사전분포(K=34.8735087293, 평균4.7986336567)를 사용한 사후평점 하위10%. 반올림된 별점 비율을 복원하며 유효 분포가 없으면 같은 사전분포의 하위10%와 명시적 사유를 사용한다. 고정seed100,000회·건수별캐시이며 평점 추정은 요청마다 재학습하지 않는다.
- 정규화 평점 A = `(A_raw−1)/4`.
- 각 항목의 보정된 비율 p = `(n×r + K×μ)/(n+K)`. n은 사용자 확인에 따른 응답자 수=리뷰 수. 고민별/피부타입별 K·μ는 아래 추정 기록의 고정값이다. 이전의 `(r−μ)` 가감값을 기하평균에 넣지 않는다.
- 활성 시 고민 비율 p_concern = 주/보조의 EB사후비율75/25 가중평균. 미지원 설문은 제외한 뒤 지원 항끼리 가중치를 재정규화한다. 주름·색소가 같은 brighteningFirming 답변을 공유하면 해당 답변을 한 번만 사용하고 두 고민의 가중치만 합한다. 중복 증거를 만들지 않는다.
- 사용자 적합도 U = `sqrt(p_concern×p_skin)`. 이는 주변 응답비율의 결합 점수이지, 해당 타입이면서 해당 고민을 가진 사람의 효과 확률이 아니다.
- 모공·중성처럼 설문 자체가 미지원이면 해당 항을 제외한다. 지원 항이 하나면 그 p를 사용하고, 둘 다 미지원이면 U=null·반영률1. 지원되는 항의 제품 응답누락/리뷰0은 사전평균 μ를 사용하고 `posteriorSource=prior_only`로 구분한다. 관측 응답을 만들어내지 않으며, 누락으로 보정을 우회하지 않는다.
- 반영률 = `0.8 + 0.2U`. λ=0.2는 사용자가 정한 초기 정책값이며 최적화 결과가 아니다.
- 리뷰 점수 R = `A×반영률` (0~1). 총점이 아닌 리뷰 부분의 영향력을 최대20% 줄인다.
- 최종 점수 = `0.80×기본점수 + 0.20×R − 유사도 감점`.
- `adjustedRating`은 보수적 평점, `normalizedRating`은 A, `suitabilityScore`는 U, `ratingRetention`은 반영률, `normalizedScore`는 R이다. `rawCombinedScore=1+4R`은 진단용 환산값이며 실제 평점이 아니다. `surveyBonus`와 `skinTypeBonus`는0이다.
- 이전 정책9 비교: `review_policy="additive"`. 그 경로에서만 `A_raw+0.05Q+0.05S`와 범위[0.90,5.10]을 사용한다. `skin_review=False`는 정책8 비교에 해당하며 범위[0.95,5.05]를 사용한다. V1은 변경하지 않는다.

원본의 모든 문항·답변을 대조했으며 ‘모공에 좋아요’ 같은 항목은 없다. 세정력·보습력·피부타입을 모공 개선 효과의 대리 응답으로 사용하지 않는다. 피부타입 보정은 별도의 사용자 타입 적합성 신호다. 색소와 주름은 원본에서 통합된 답변이라 따로 분리해 해석하지 않는다. 피부타입은 ML 입력·출처 있는 제품 라벨 점수·실제 피부타입 설문 보정에서 사용하며, 라벨 점수와 설문 보정의 근거를 별도로 표시한다.

위 가중합으로 정렬하고, 동일 제품은 한 옵션만 고른다. 이미 고른 제품과 같은 분류이고 전체 성분 ID 집합의 Jaccard 유사도가 0.85 이상이면 `0.02 × 유사도`만큼 선택 점수를 낮춘다. 최대 5개를 순차 선택하며, 관련성이 크게 떨어지는 제품을 다양성 때문에 강제로 넣지 않는다. 최종 선택 점수·감점·비슷한 선행 제품 ID를 기록한다. 브랜드·제형 다양성은 확인할 데이터가 없거나 별도 정책이 필요하므로 강제하지 않는다.

`beforeReviewMatches`는 같은 용도 필터·중복 완화 조건에서 리뷰만 0으로 둔 결과다. `beforeDiversity`는 통합 리뷰 혼합 0.20(설문 계수 0.05)을 유지하고 중복 완화만 끈 결과다. `rankBeforeReview`는 상위 5개 선택 후 나머지 후보를 기본점수 순으로 둔 진단 순위다. 상위5 밖 순위는 전체 후보에 다양성 선택을 끝까지 적용한 순위가 아니다.

현재 비교 V1 기본 `/skincare` API는 별점 보정을 사용하고, V2로 가져온 비율 보정 함수는 V1 hybrid/profile 경로에 있다. 따라서 전체 순위 공식을 동일하다고 주장하지 않는다.
