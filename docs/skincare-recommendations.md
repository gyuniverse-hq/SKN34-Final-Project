# 기초 화장품 추천

앱은 기기에서 선택한 목표와 감지된 고민을 구분해 `POST /api/recommendations/skincare/v2`로 보낸다.
기존 앱은 `POST /api/recommendations/skincare`를 계속 호출한다.
기존 `/skin` API는 별도로 유지한다. 목표는 보습·진정·미백·탄력·모공·유분·트러블이며
종합 TOP 5는 선택 목표·유의 고민·피부 특성을 고정 비율 없이 섞으며, 제품 적합도와 목록 보완도를 함께 본다.
v4는 양호/유의 이진 결과이고 이전 등급 결과만 4 이상을 유의로 해석한다.
초기 목적 규칙과 정렬은 검증되지 않은 휴리스틱이다.

사용자에게는 유수분 밸런스, 민감·진정, 트러블, 모공, 톤·잡티, 주름의 여섯 분류를
보여주고 내부의 일곱 고민 코드는 유지한다. 유수분 선택은 보습(`dryness`)과 유분
(`oiliness`) 두 코드를 하나의 표시·점수 그룹으로 묶는다. 유분이 유의하면 유분을,
피부 타입이 건성이면 보습을 우선한다. 두 조건이 모두 성립하거나 모두 없으면 동등하다.
주목표 유수분에서 우선 신호가 있으면 해당 고민에 일치한 제품을 먼저 정렬한다.
개별 코드의 `byConcern`과 `coverage`는 그대로 두고 합친 결과는 `balanceMatches`로 제공한다.
기존에 저장된 `oiliness` 우선순위도 유수분 밸런스로 표시한다.

## v2 입력과 목록 구성

현재 전략은 `skincare-hybrid-v2-cosing-only-v1`이다. 사용자 확인에 따라
전체 리뷰 수를 설문 응답비율의 분모로 사용한다. 반올림된 비율에서 계산한 인원은 추정치다.
현재 리뷰 요약과 수집 시각이 같은 완전한 설문 선택지 집합만 사용한다.
비율 범위는 0~100이고 합계는 반올림 오차 ±2 이내여야 한다.

리뷰 점수는 `보정 평점 + 0.05 × 응답비율 보조값`이다. 종합 목록은 아래 프로필 적합도와
목록 보완도를 더하고 이미 선택한 제품과의 성분·근거 중복을 감점한다.
고민별 목록은 해당 고민에 맞는 옵션을 따로 정렬한다.
응답비율로 인한 상품별 점수 변화는 이론적으로 ±0.05점 범위다.
점수 상한은 순위 이동 상한과 다르다. 합산값은 표시용 별점이나 효능 확률이 아니다.
0.05는 기대순위 정책 사례 117건에서 모두 일치한 가장 작은 실험값으로 사용자가 선택했다.
117건에는 동일 상품쌍의 프로필별 반복이 포함되며 고유 상품쌍은 59개다.
실제 사용자 만족도를 학습한 최적값은 아니다.
상품별 평균비율 C는 유효한 해당 응답을 가진 서빙 상품의 리뷰 수 가중 평균이며
옵션이 여러 개여도 상품은 한 번만 센다.
상품의 보조값은 `n/(n+207) × (p-C)`다. 리뷰가 없거나 응답이 없으면 0이다.
207은 2026-11-06 로컬 추천 상품 956개의 리뷰 수 중앙값으로 사용자와 선택한 고정 정책값이다.
리뷰 207개에서 상품 응답비율 반영 비중이 50%이며, 그 이상에서도 100%를 향해 완만하게 증가한다.
통계적으로 검증된 최적값은 아니다. 별점 보정의 기준값 20은 별도로 유지한다.
건성·지성에는 대응 타입 응답, 주목표에는 보습·진정·주름/미백 응답을 선택하고,
자극 주의에는 순함의 양수 편차와 자극의 음수 편차를 사용한다.
선택한 신호별 편차를 평균한다. 여러 신호가 있는 상품이 단순 합산으로 유리해지지 않도록
분모는 요청에서 선택한 신호 수로 고정한다. 없는 응답은 중립이다.
복합성은 현재 요청에서 unknown이며, 중성에 해당하는 리뷰 선택지가 없어 타입 응답을 쓰지 않는다.
별도 응답이 없는 모공·유분·트러블 주목표에는 목표 응답 신호를 만들지 않는다.

요청 예시는 아래와 같다. 설문 미작성·분석 결과 없음은 빈 고민 목록과 `unknown`으로 처리한다.

```json
{"primaryGoal":"dryness","secondaryGoals":[],"detectedConcerns":[{"goal":"pores","sources":["analysis"]}],"skinType":"unknown","irritationSignal":"unknown"}
```

`detectedConcerns`에는 결과 화면에서 `care`(유의)인 항목만 넣는다. 설문 원답이나 선택한 목표만으로
결과 화면에서 양호·미확인인 항목을 유의 고민에 추가하지 않는다.

추천 필요 집합 U는 선택 목표, 유의 고민, 피부 특성에서 도출한 케어 목표의 합집합이다.
건성은 보습, 지성은 유분 관리, 자극 주의는 진정으로 연결하며 unknown·중성은 타입 목표를
추측하지 않는다. 피부 특성으로 생긴 매칭 출처는 `skinProfile`이며 분석에서 감지된 것으로 표시하지 않는다.
세 관점에서 같은 고민이 생겨도 U에서는 한 번만 센다. U 중 하나 이상에 활성 근거와 같은 옵션의
성분 일치가 확인된 후보만 사용한다. 리뷰 응답만으로 후보 자격을 만들지 않는다.

종합 목록을 한 자리씩 선택한다. 흔한 성분 하나만으로 여러 고민에 완전한 가점을 받던 현상을
줄이기 위해 후보 자격과 순위의 변별력을 구분한다. 후보 자격 검사는 그대로 유지한다.

판매 가능한 검증 옵션을 가진 전체 상품 수를 T, 성분 i를 포함한 상품 수를 df(i)라 하면
`w(i) = -ln(max(df(i)/T, 0.05)) / -ln(0.05)`이다. 상품별 옵션 중복을 제거한다.
전 상품에 있는 성분은 0, 5% 이하의 상품에 있는 성분은 1이며 그보다 희귀해져도 더 올리지 않는다.
이는 카탈로그 안에서 제품을 구분하는 값이며 효능·연구 신뢰도·성분 품질 점수가 아니다.

성분 i가 활성 매핑으로 연결된 서로 다른 고민 수를 b(i)라 한다.
고민 g에 대한 옵션의 변별값 s(g)는 통과한 매핑 중 `w(i)/b(i)`의 최댓값이다.
같은 고민의 성분 개수를 합산하지 않는다. 여러 고민에 걸친 성분이 고민마다
온전한 가점을 중복해서 받지 않도록 한다. 현재 CosIng 매핑은 성분 하나를 기준으로 한다.

후보의 일치 고민 집합을 M, 앞서 뽑힌 대표 옵션 중 고민 g에 맞는 수를 c(g)라 할 때:

`F = Σ[g ∈ M ∩ U] s(g) / |U|` (프로필 적합도)

`N = Σ[g ∈ M ∩ U] s(g)/(1+c(g)) / |U|` (목록 보완도)

두 옵션의 유사도는 아래 성분 중복도 중 최댓값이다. 성분은 w로 가중한 Jaccard
`교집합 가중치 합 / 합집합 가중치 합`을 사용하며 빈 분모는 0이다.

- 스냅샷에 정규화되어 있는 성분 코드 전체의 중복도(원천 전체 성분표와는 다름)
- 이번 프로필에서 추천 근거로 실제 사용한 성분 코드의 중복도

Q는 이미 선택한 제품 각각과의 유사도 중 최댓값이며 첫 자리에서는 0이다.
제품에 다른 성분이 추가되어 있어도 같은 추천 근거의 반복이 감춰지지 않게 한다.

`선택 점수 = R + 0.05D + 1.0F + 1.0N - 0.5Q`

현재 PROFILE_WEIGHT와 COMPLEMENT_WEIGHT는 각각 1.0이다. 각 항의 최대 영향 범위를
평점 1점 단위로 둔 초기 정책값이며, 사용자 평가로 최적화한 값이 아니다. 기존 20·207·0.05의
선정 근거가 이 두 새 계수까지 검증한 것은 아니다. 계수는 서비스 상단에 모아 둔다.
REDUNDANCY_WEIGHT=0.5는 중복 감점의 최대 크기다. 0·0.25·0.5·1.0을 비교해 아래 절충으로
선택한 초기 정책값이며 사용자 만족도로 검증한 최적값은 아니다.
COMPLEMENT_WEIGHT=0이면 목록 보완 효과가 빠지고 REDUNDANCY_WEIGHT=0이면 중복 감점이 빠진다.
1/(1+c)는 첫 일치의 가치를 1,
같은 고민 두 번째는 1/2, 세 번째는 1/3로 낮춘다. 낮은 평점을 무시하고 빈 관점을 강제하지 않는다.
점수가 같으면 아래 개인 적합도 순서로 해소한다. 따라서 관점별 개수와 포함 여부는 보장하지 않는다.
다중 고민 제품은 각 고민을 커버하지만 상품은 한 자리만 차지하며, 서로 다른 옵션의 성분을 합치지 않는다.
후보가 부족하면 적은 수만 반환한다. 매 단계의 탐욕 선택이며 전역 최적 조합을 보장하지 않는다.

개인 적합도: 사용자가 선택한 주목표 → 선택한 보조 목표 일치 수 → 앞에서 세지 않은 감지 고민 일치 수
→ 출처가 있는 제조사 민감 피부·피부 타입 표기 → 보정 평점 + 0.05 × 응답비율 보조값
→ 리뷰 수 → 상품·옵션 ID 순으로 정렬한다.
`byConcern`은 각 고민에 검증된 전체 옵션을 피부 특성 표기, 해당 고민 기준 보정 리뷰 점수,
리뷰 수, 상품·옵션 ID 순으로 정렬한다. 다른 선택·유의 고민의 일치 여부는 이 순서에 반영하지 않는다.
`balanceMatches`는 보습·유분에 맞는 후보를 합치고 우선 신호가 있으면 해당 고민에 맞는 상품을 먼저 둔다.
선택 목표·유의 고민·피부 특성의 케어 목표를 위한 그룹을 제공하며, 각 목록은 상품별 대표 옵션 하나를 선택한다.
고민별 최대 5개이며 `reasons`에는 선택·분석·설문·피부 타입 출처가 포함된다.
각 이유에 실제 일치한 `ingredientCodes`와 `evidenceLevel: ingredient_presence`를 추가한다.
현재 추천은 제품별 농도·제형에 따른 효능을 검증하지 않는다. 앱 네 언어 안내에도
이 한계를 명시한다. 이 필드는 성분 존재 근거의 수준 표시이며 제품별 검수 완료를 뜻하지 않는다.
`coverage`는 운영 가능 매핑 부재와 적용 가능한 판매 옵션 부재를 구분한다.

## v0.3 추천 지식과 발행

추천에 사용하는 성분 연결은 CosIng만 사용하며 `oy_mfds_ingredient_map`과 `cosing_ingredient_lookup`,
`ingredient_function`, `cosing_function`, `function_concern`을 같은 옵션 기준으로 읽는다.
CosIng 조회가 단일 후보로 확인된 `accepted` 성분만 쓰며, 식약처 영문명이 수집 당시
검색어와 달라진 경우 제외한다. 원본명·괄호 일반명 정규화 일치는 출처에 구분해 기록한다.
사용자가 지정한 태그–고민 분류는 별도 `CosingMapping`이며 연구 논문으로 표기하지 않는다.
후보 선정과 변별력 계산에는 CosIng 연결만 사용한다. v2 응답의
`evidenceSources`는 `cosing_function`이다. 기존 연구 기반 매핑과 근거 자료는 DB에 보존하지만 추천과 발행 스냅샷에는 포함하지 않는다. 이는 성분에
분류된 기능이 있다는 표시이며 제품의 효능이나 사용 결과를 검증한 것은 아니다.

0018은 추천 원천을 8개 테이블로 교체한다. 개편 전 추천 테이블과 `skincare_serving`을
먼저 백업한다. 데이터가 있는 DB에서는 `alembic -x replace_recommendations=v0.3 upgrade 0018`
명령을 명시적으로 사용한다. 기존 발행기를 먼저 중지하고 새 API를 배포한다. 되돌릴 때는
기존 추천 스키마와 데이터를 백업에서 복구하고 버전에 맞는 API로 전환한다.

0019는 CosIng 조회 결과, 기능 태그, 성분–기능과 기능–고민 연결을 위한 테이블을 생성한다.
마이그레이션을 적용한 로컬 DB에 식약처 성분을 먼저 적재하고, 별도 전달받은
`cosing_ingredients.csv`와 `cosing_function_tags.csv`를 같은 디렉터리에 둔다.
`DATABASE_URL`을 로컬 PostgreSQL로 설정한 뒤 `backend/api`에서 실행한다.

```powershell
uv run python ../../scripts/data/recommendation/load_cosing.py --input-dir <CosIng CSV 디렉터리>
```

미리보기 결과를 확인하고 `--apply`를 추가하면 빈 CosIng 테이블에 적재한다. 그다음 추천 발행을 실행한다.

2026-11-05 누적본은 `backend/api/seed/recommendation_v03/dataset.json`에 있다.
기존 S001·S002 등의 옵션별 승인 기록은 백업에 남는다. 새 규칙은 고민·성분 구성 및
적용 범위별로 한 행이며, 각 연구의 지표·조건·한계는 별도로 보존한다. 연구 편수는 순위 가중치에 포함하지 않는다.
이 연구 기반 규칙과 운영 스위치는 현재 추천에 영향을 주지 않는다.

`identity.json`에서 허용한 유일한 정규화 이름과 검증 별칭만 로컬 성분 ID에 연결한다.
이름에서 농도나 괄호를 제거하지 않는다. 추천 표시는 성분 구성의 일치를 의미한다.
새 원천 성분과 옵션이 들어오면 자동 갱신 작업이 CosIng 옵션 연결과 서빙 스냅샷을
동일 트랜잭션에서 갱신한다. 연구 기반 연결 테이블은 갱신하지 않는다. 분류·판매·재고·가격 검사는 기존 발행 기준을 따른다.

`backend/api`에서 `uv run python -m app.jobs.review_skincare`로 고민별 수량과 차단 사유를 확인한다.
이 도구의 `--mapping`과 `--state`는 보관 중인 연구 기반 매핑의 상태만 바꾼다.
운영 환경의 주기 발행은 기본적으로 꺼져 있으며
검증 후 `SKINCARE_REFRESH_ENABLED=true`로 켠다.

## v1 동작과 추적

주목적 일치 → 보조 목적 수 → 제조사 민감 피부 표기(자극 신호 시) → 제조사 피부 타입 일치
→ 리뷰 보조값 → 리뷰 수 → 상품·옵션 ID로 정렬한다. 리뷰 prior는 20이며 현재 순위의
효능이나 정확도를 의미하지 않는다. 복합 성분은 동일 옵션 포함 여부만 개발 추적에 남긴다.
v1은 피부 타입·자극 리뷰 비율을 순위에 쓰지 않는다.

요청은 primaryGoal/secondaryGoals/skinType/irritationSignal/goalPolicyVersion/limit이다.
원본 설문·모델 점수·사진 필드는 거부한다. 목적별 mapping_unavailable/no_matches/ok를 반환한다.
includeTrace=true는 서버 env가 local/development/test일 때만 처리한다.
개발용 최신 기록은 기기 AsyncStorage에 1건만 저장하며 일반 리포트에는 표시하지 않는다.
서버는 개인 요청·추천 이력을 저장하지 않고 응답은 no-store다.
