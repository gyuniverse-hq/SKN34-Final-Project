# AR 추천 MLOps v1.1 목업 데이터 검증 보고서

**검증일** 2026-11-19 · **코드 기준** `ec81372` · **검증 환경** 격리된 로컬 PostgreSQL 17 및 CatBoost CPU

추천 요청 1,000건 중 유효 담기 요청이 **499건이면 학습을 건너뛰고**, **500건이면 시간순 분할 후 첫 후보 모델을 생성**하는 것을 확인했다. 첫 후보는 오프라인 1위 적중률이 45%에서 55%로 올라갔지만, 개선 폭의 95% 신뢰구간에 0이 포함돼 미통과했다. 별도로 실행한 A/B에서도 기존 룰을 유지한다는 판정이 나왔다. 현재 구현은 추출·학습·평가·실험 집계를 실행하는 명령과 모델을 적용하는 설정을 제공한다. 예약 실행과 운영 전환은 별도 단계다.

## 1. 검증 환경과 목업 구성

임시 DB에 저장소의 마이그레이션을 `0026`까지 적용했다. 추천 결정은 실제 `ArHistoryService`와 PostgreSQL 저장소를 호출해 저장했고, 노출과 시착·담기 이벤트는 통제된 시각으로 만들어 같은 스키마에 넣었다. 그 뒤 제품 코드의 `export`, `train`, `experiment` 명령을 그대로 실행했다. 테스트 데이터·모델 번들은 Git이 무시하는 로컬 경로에 저장했다.

| 항목 | 구성 |
|---|---|
| 카탈로그 | 저장소 카탈로그에서 추출한 실제 립·블러셔의 HEX·제형·가격 분포를 사용했다. 제품 식별자와 이름은 가상으로 만들었다. 립 45개, 블러셔 30개, 색상 303개를 사용했다. |
| 평점 | 평균 평점 4.09~4.99점, 리뷰 수 14~14,000건을 생성했다. 리뷰 수가 고르게 퍼지기보다 일부 상품에 집중되도록 구성했다. |
| 회원·세션 | 가상 회원 420명을 만들었다. 첫 데이터는 이 중 282명의 추천 요청 1,000건, 세션 835개였다. 세션 670개는 추천을 한 번, 165개는 두 번 받았다. |
| 첫 방문과 재방문 | 선행 자유 시착 2,298건을 넣었다. 이후에는 같은 회원의 직전 시착·담기도 순위 입력에 반영됐다. 첫 데이터의 노출 2,590행 중 542행은 해당 부위의 이전 행동이 없었다. |

첫 구간의 요청 대비 담기율 50%는 사용자가 지정한 경계 조건이다. A/B의 행동은 그룹별 양성 건수를 고정하지 않고 같은 반응 규칙으로 생성했다. 두 구간 모두 실제 서비스 전환율이나 모델의 실사용 효과를 추정하는 데에는 사용할 수 없다.

## 2. 룰 추천 저장과 학습 데이터 추출

`collect` 모드로 2026-09-01부터 10-04까지의 탐색을 재생했다. 실제 추천 서비스가 평점·리뷰 수와 추천 전 90일 내 활동을 조회했다. 추천 요청 1,000건 중 평점 추천은 212건, 개인화 룰 추천은 788건이었다. 요청·후보는 DB에, 당시 사용한 10개 입력과 카탈로그 해시는 요청별 스냅샷 파일에 기록했다.

1. 추천 요청과 후보를 `request_id`로 연결했다. 노출과 행동 귀속의 기준은 각각 `candidate_id`, `impression_id`다.
2. `export`에서 동의 조건을 확인하고, 노출 후 24시간 내에 발생하고 노출 후 48시간 안에 수신된 담기를 양성으로 표시했다. 관찰 기간과 수신 대기를 모두 마친 노출만 포함했다.
3. 실제로 노출된 색 2,590행을 추출했다. 후보 3,000개 중 나머지 410개에는 학습 행이 생성되지 않았다. 요청 시점 스냅샷을 연결하지 못해 제외된 행은 0건이었다.

| 의도적으로 섞은 사례 | 건수 | 확인 결과 |
|---|---:|---|
| 같은 노출에 이미 유효한 담기가 있는 추가 이벤트 | 11 | 양성 노출과 양성 요청을 추가로 세지 않았다. |
| 같은 요청에서 다른 노출의 색도 담은 경우 | 10 | 양성 노출이 10행 늘었고, 학습 시작 기준인 양성 요청 수는 그대로였다. |
| 추천 노출에 연결되지 않은 담기 | 63 | 해당 추천 요청의 양성으로 집계되지 않았다. |
| 24시간 뒤 발생한 담기 | 43 | 해당 추천 요청의 양성으로 집계되지 않았다. |
| 제때 발생했지만 48시간을 넘겨 수신된 담기 | 43 | 해당 추천 요청의 양성으로 집계되지 않았다. |

양성 요청 500건의 부위별 분포는 립 360건, 블러셔 140건이었다. 두 색을 담은 10건이 있어 양성 노출은 510행이었다. **학습 시작을 판단할 때는 유효 담기가 연결된 서로 다른 추천 요청 수를 센다.**

## 3. 499건과 500건에서 학습 시작 확인

같은 1,000개 추천 요청과 같은 노출 목록을 두 번 추출했다. 첫 추출에서 유효 담기 하나를 보류하고, 두 번째 추출 전에 추가했다. 두 실행 모두 추출 기준시각은 2026-10-10 00:15 UTC다.

| 케이스 | 전체 추천 요청 | 노출 행 | 양성 노출 | 양성 요청 | 실행 결과 |
|---|---:|---:|---:|---:|---|
| 경계 직전 | 1,000 | 2,590 | 509 | 499 | `skipped` · `insufficient_positive_requests`. 모델 폴더 미생성. |
| 경계 도달 | 1,000 | 2,590 | 510 | 500 | `candidate_created`. 모델·manifest·지표 파일 생성. |
| 세션 경계 대조 | 1,000 | 2,590 | 510 | 500 | `skipped` · `insufficient_training_classes_or_requests`. |

경계 도달 실행에서 2026-09-29 00:15:16 UTC를 기준으로 개발 2,075행과 평가 515행으로 나뉘었다. 개발에는 양성 요청 **400건**, 평가에는 **100건**이 남았다. 미담기 노출도 양쪽에 포함됐다.

세션 경계 대조에서는 복사한 데이터에서 개발 쪽 마지막 양성 요청을 평가 쪽 첫 세션과 동일한 회원·세션으로 만들었다. 모델이 같은 세션 활동을 학습과 평가에서 동시에 보지 않도록 개발 쪽 행이 제외됐고, 개발용 양성이 400건 아래로 내려가 학습을 건너뛰었다. 따라서 500건은 첫 번째 기준이며, 분할 후 개발 데이터가 충분한지도 확인한다.

## 4. 첫 후보와 현행 룰의 오프라인 비교

양성 요청 100건에서 **같은 노출 후보**를 사용했다. 룰의 기존 1위와 후보 CatBoost가 다시 고른 1위가 실제 담긴 색인지 비교했다. 실험 전에 목업용 기준으로 1위 적중률 42% 이상, 룰 대비 +5%p 이상, 회원 단위 부트스트랩 95% 신뢰구간 하한이 0보다 클 것을 정했다.

| 평가 범위 | 양성 요청 | 기존 룰 | 첫 후보 | 차이 |
|---|---:|---:|---:|---:|
| 전체 | 100 | 45.00% | 55.00% | +10.00%p |
| 노출 후보가 2개 이상 | 91 | 39.56% | 50.55% | +10.99%p |
| 립 | 80 | 46.25% | 51.25% | +5.00%p |
| 블러셔 | 20 | 40.00% | 70.00% | +30.00%p |

전체 개선 폭의 95% 신뢰구간은 **−2.08~+22.33%p**였다. 두 점수 조건은 충족했지만, 이 표본으로 개선 방향을 확정할 수 없어 `offline_pass=false`로 기록됐다. 블러셔 결과는 양성 요청 20건에서 나온 값이다.

## 5. A/B 운영 흐름 재생

첫 후보의 오프라인 결과와 별개로, **실험 모드 자체를 점검**하기 위해 격리된 로컬 설정에서 그 모델을 사용했다. 2026-10-13~10-30의 후속 기간을 잡고, 실제 추천 서비스가 실험 ID와 회원 ID로 그룹을 고정해 A에는 룰, B에는 후보 모델을 적용하게 했다. 추천 요청은 실험 세션당 한 번씩 발생시켰다. 종료 후 48시간 대기, 그룹당 최소 250세션, 최소 개선 폭 +3%p를 적용했다.

| 그룹 | 고유 회원 | 세션 | 담기 세션 | 세션 담기율 | 룰 대체·빈 응답 |
|---|---:|---:|---:|---:|---:|
| A · 기존 룰 | 149 | 344 | 203 | 59.01% | 0 |
| B · 후보 모델 | 164 | 376 | 200 | 53.19% | 0 |

B에서 첫 후보 모델 한 버전만 사용됐고, 집계에 등장한 313명은 그룹 간에 겹치지 않았다. 종료 24시간 뒤는 `pending`, 종료 72시간 뒤는 `retain_baseline`이었다. 담기율 차이는 **−5.82%p**이고 95% 신뢰구간은 **−13.36~+1.22%p**였다. 그룹당 500건의 담기를 기다리는 조건은 적용되지 않았다. 구매 지표는 `unmeasured`로 반환됐다.

## 6. 후속 재학습, 같은 평가셋 비교, 모델 적용

후속 행동을 합쳐 재추출한 결과는 4,445노출 행, 양성 요청 903건이었다. 첫 번들 경로를 `--baseline`으로 지정하고 재학습했다. 첫 후보는 이 단계에서 **기존 ML과 비교하는 경로를 점검할 기준 모델**로 사용했다.

| 항목 | 결과 |
|---|---|
| 개발 · 평가 | 개발 3,966행·양성 요청 803건, 평가 479행·양성 요청 100건 |
| 동일한 최신 평가셋의 1위 적중률 | 첫 ML 52%, 재학습 후보 50% |
| 개선 폭 · 95% 신뢰구간 | −2.00%p · −13.21~+10.31%p |
| 출력 | 첫 번들과 구분되는 새 버전의 후보가 생성됐고 `offline_pass=false`가 기록됐다. |

로컬 `model` 모드에서 각각의 후보 경로를 지정해 두 모델 버전 모두 3개 칩을 반환하는 것을 확인했다. 같은 요청을 재전송했을 때 같은 후보 ID가 반환됐다. 운영 조건을 적용한 격리 실행에서는 오프라인 미통과 모델이 거부됐고, 경로가 없는 경우에도 기존 룰로 3개를 반환했다. 두 실행에서 DB의 정책 값은 `fallback`이었다.

## 7. 통과 조건 대조 테스트

성공 시 처리도 확인하기 위해 같은 1,000건을 복사했다. 유효 담기가 있던 요청마다 밝기가 가장 높은 노출에 담기를 배정해, 모델 입력에 강한 신호가 들어가도록 의도적으로 구성했다. A/B 판정 함수에는 별도로 그룹당 320세션을 만들고, A의 담기를 144건, B의 담기를 195건으로 설정했다. 이 두 대조 테스트의 수치는 조건 검증용이다.

| 단계 | 확인 결과 |
|---|---|
| 오프라인 학습·판정 | 룰 35%, 후보 81%. 개선 폭의 95% 신뢰구간은 +36.08~+57.58%p로, `offline_pass=true`를 기록했다. |
| 운영 조건에서 모델 로딩 | 테스트 DB를 그대로 사용하면서 운영 환경 조건과 통과 번들 경로를 지정했다. 실제 랭킹 서비스가 모델로 추천 칩 3개를 만들고 정책에 모델 버전을 기록했다. |
| A/B 판정 함수 | A 45.00%, B 60.94%. 개선 폭 +15.94%p, 95% 신뢰구간 +8.44~+23.75%p로 `passed`를 반환했다. |

## 8. v1.1 검증 당시 흐름

```text
평점·리뷰 수로 추천 → 활동이 생기면 룰에 취향 반영
        ↓
추출 실행 → 유효 양성 요청 500건 + 분할 후 개발 양성 400건
        ↓
후보 학습 → 같은 평가셋에서 현재 룰 또는 운영 ML과 비교
        ↓
오프라인 통과 시 A/B 실험 시작 → 기간·표본·개선 폭 검토
        ↓
승격 결정 후 운영 모델 경로 변경 → 새 데이터로 재학습·재비교
```

- **첫 모델의 비교 상대**는 기록된 룰 순위다. 운영 ML이 생긴 뒤에는 그 번들을 `--baseline`으로 지정해 같은 최신 평가셋에서 새 후보와 비교한다.
- **500건은 v1.1 검증에서 학습 실행을 판단한 기준**이다. 후속 설계는 관찰이 마감된 30일을 기준으로 한다. [현재 학습 기준](ar-recommendation-mlops-v1.0.md)
- **A/B 통과와 모델 전환은 별도**다. `experiment`는 판정만 파일로 남긴다. 실험 시작과 전면 적용에는 모델 경로·모드 설정 변경이 필요하다.
- 운영 모델 적용 대상을 자동 계산하는 구독·동의 연동, 실제 이용자의 전환율, 앱 화면·지연과 구매 귀속은 이 검증 범위 밖이다.

## 9. 검증 당시 실행 조건

격리 DB의 접속 정보는 환경 변수 `DATABASE_URL`로 전달했고, API와 추출 명령은 같은 `AR_PALETTE_DATA_DIR`의 스냅샷을 읽었다. 순서와 옵션은 아래와 같다.

| 순서 | 실행 | 사용한 주요 옵션 |
|---|---|---|
| 1 | `uv run --frozen alembic upgrade head` | 임시 PostgreSQL, 스키마 `0026` |
| 2 | 목업 재생 스크립트 | 시드 `20261119`, 최초 `collect`, 후속 `experiment` |
| 3 | `python -m app.jobs.ar_palette_ml export` | `--as-of`, `--output`, 기본 `--window-hours 24 --grace-hours 24` |
| 4 | `python -m app.jobs.ar_palette_ml train` | `--dataset`, `--output`, `--min-hit 0.42 --min-lift 0.05` |
